## 1. ノート粒度

**章単位（1章＝1ノート）。COLUMN も1本＝1ノート。**

理由: この本は節番号を持たず、**1章が電子版1〜4ページで1つの原則またはテクニックを完結させる構成**である。章より細かく割ると1ノートが10行に満たず、章より粗く割るとテクニックを名前で引けなくなる。vault設定「ノート粒度の既定」は節単位だが、同設定は「思想・読み物寄りの本は章単位に落とす」と例外を認めており、これに従う。

- 1ノートの目安: **40〜80行**（既存ノートの中央値78行に合わせる）
- 例外1: **本文が130行を超える章**（`ch10` `ch39` `ch50` `ch06` `ch09` `ch11` `ch34` `ch20` `col07` `ch17` `ch61`）は**100〜140行まで伸ばしてよい。分割はしない**
- 例外2: **部の扉の導入と、目次にある節グループの「概要」**は、章ノートにせず**部ごとに1本の `00_第N部の概要.md` にまとめる**（下の「9. この本に固有の注意」を参照）
- 例外3: **`謝辞` と `電子版奥付` はノートにしない**（人名の列挙と書誌情報のみで、業務判断に使う内容が無い。書誌情報は各ノートの `source` に入る）

## 3. 命名規則

| 対象 | 形 | 例 |
|---|---|---|
| 部フォルダ | `<2桁連番>_第<N>部` | `01_第1部` / `04_第4部` |
| 前付・後付のフォルダ | `00_前付` / `99_後付` | — |
| 章ノート | `<2桁章番号>_<章タイトル>.md` | `10_プロダクトマネジャー.md` |
| COLUMNノート | `COLUMN_<タイトル>.md` | `COLUMN_必要最小限の製品.md` |
| 部の概要ノート | `00_第<N>部の概要.md` | `00_第3部の概要.md` |
| 深掘りノート | `_deep/<内容を表す名前>.md` | `_deep/製品発見のテクニック早見表.md` |

- 章タイトルは**原文の文言をそのまま使う**（要約した見出しに置き換えない）
- **ファイル名では記号を落とし、`title` には原文どおり残す**（vault設定の実例に従う）
  - 落とす記号: `\ / : * ? " < > | （ ） 「 」 『 』 ？ ！ 、 。 〜`
  - `_` に置き換える記号: `―`（ダッシュ）と `／`（全角スラッシュ）
  - 例: `title: 第5章 エンタープライズ（成熟期）企業 ―常に製品のイノベーションを図る―`
    → ファイル `05_エンタープライズ成熟期企業_常に製品のイノベーションを図る.md`
- **ファイル名に空白を入れない**（全角空白も詰める）。例: `プロフィール Google のジェーン・マニング` → `15_プロフィールGoogleのジェーン・マニング.md`
- 英数字は**半角**（`OKR` `MVP` `A／Bテスト` の `AB` など）
- **ファイル名は「8. 章 → ノートの割り当て」の表に全部書いてある。Phase 2 は表から写すだけでよく、この規則を自分で適用する必要はない**

## 5. 本文の骨格

```markdown
# <title と同じ見出し>

<ナビ行>

## <原文の小見出し>

<原文の要点。箇条書きが既定>

## 要確認リスト        # そのノートに2件以上ある時だけ

## 関連
```

- **ナビ行の形**: `← [[<前のノート>]] | ↑ [[INSPIRED_MOC]] | → [[<次のノート>]]`
  - 前後は**「8. 章 → ノートの割り当て」の表の順**（章とCOLUMNが混ざった読み順）で1つずつ前・後のノート
  - **部をまたぐときは部を添える**。例: `→ 第2部 [[00_第2部の概要]]`
  - 先頭ノート（`00_前付/第2版への序`）は `↑` と `→` のみ、最後のノート（`99_後付/監訳者あとがき`）は `←` と `↑` のみ
  - リンクは**ファイル名から `.md` を外した形**で書く（`[[10_プロダクトマネジャー]]`）
- **見出し（`##`）は、原文の小見出しか、原文の文に辿れる構造用の見出しのどちらかにする。**
  **新しい主張を加える見出しを作らない。**（2026-09-21 Phase 3 の検収で改訂。改訂の理由は下記）
  - この本の原文の小見出しは、抽出テキストでは**本文と同じ平文の行**として現れる（Phase 0 で `##` を付けていない）。**前後の文脈で小見出しと判断できる行は `##` にする**
  - それとは別に、**原文の文に辿れる構造用の見出し**（例: 原文「まとめると、…重要なことは4つある」に対する `## まとめ`、原文「この手法の10の大きな問題点」に対する `## この手法の10の大きな問題点`）は**使ってよい**
  - **禁止するのは、原文に無い主張を見出しの形で持ち込むこと。** 見出しは必ず、直後の本文の原文に対応していなければならない

> **改訂の理由（2026-09-21）。** 当初この項は「見出しを創作しない」と書いていたが、
> Phase 3 の検収で、**この vault の既存2冊（要件定義のセオリー29本・しっかり学ぶ数理最適化93本）が
> すでに構造用の見出しを常用している**ことがわかった
> （実例: `## 章の導入（p.11）` `## 読み方メモ` `## 果たすべき目的とは？（結論）` `## 表記法について`。
> 1ノートあたりの見出し数は120本の中央値で6）。
> **当初の項は vault の実際の慣習より厳しく、そのままでは既存2冊と体裁が揃わない。**
> ユーザーの判断（選択肢C）により、指示書を既存慣習に合わせて改訂し、生成済みノートは作り直さない。
  - 例（`ch10.md`）: `主な責任` / `顧客に関する深い知識` / `データに関する深い知識` / `自分のビジネスについての深い知識` / `市場と業界についての深い知識` / `頭がよく、創造的で、粘り強いこと` / `プロダクトマネジャーのプロフィール`
  - **小見出しが1つも見当たらない短い章では `##` を作らず、`# 見出し` → ナビ行 → 箇条書き → `## 関連` の形にする**
- 本文は**箇条書きで要点を抽出する。** 原文の段落をそのまま写さない（規律5）
- 原文が**番号付きの列挙をしている箇所は番号を保つ**（例: `ch10` の「働き方3つ」、`ch25` の「製品ビジョンの10の原則」）
- **`## 関連` は必ず最後。** 各行は `- [[ノート名]] — 一言説明`（裸のリンクを並べない）

## 9. この本に固有の注意

### 9-1. 節グループの「概要」は部の概要ノートに集める

目次には、部の中に**章番号を持たない節グループ**がある
（`製品開発チーム` / `スケールアップに必要な人々` / `製品開発ロードマップ` / `製品ビジョン` /
`製品の目標` / `製品のスケールアップ` / `製品の発見` / `発見のフレーミングテクニック` /
`発見のプランニングテクニック` / `発見のアイディエーションテクニック` /
`発見のプロトタイピングテクニック` / `発見のテストテクニック` /
`トランスフォーメーションのテクニック` / `スケールアップにおけるプロセス` の14個）。

原文ではそれぞれの先頭に**`概要` という小見出しの導入**が付いている。
**Phase 0 の分割では、この `概要` ブロックが「直前の章のファイルの末尾」に入っている。**

| `概要` ブロックがあるファイル | 末尾の `概要` が導入している節グループ |
|---|---|
| `part2_intro.md` | 製品開発チーム |
| `ch15.md` | スケールアップに必要な人々 |
| `part3_intro.md` | 製品開発ロードマップ |
| `col08.md` | 製品ビジョン |
| `ch27.md` | 製品の目標 |
| `ch29.md` | 製品のスケールアップ |
| `part4_intro.md` | 製品の発見 |
| `ch34.md` | 発見のフレーミングテクニック |
| `col13.md` | 発見のプランニングテクニック |
| `ch40.md` | 発見のアイディエーションテクニック |
| `ch44.md` | 発見のプロトタイピングテクニック |
| `ch49.md` | 発見のテストテクニック |
| `ch57.md` | トランスフォーメーションのテクニック |
| `ch60.md` | スケールアップにおけるプロセス |

**扱い方。**

- **章ノートには、その末尾の `概要` ブロックを書かない**（次の節グループの導入であって、その章の内容ではない）
- 代わりに、**その節グループが属する部の `00_第N部の概要.md` に `## <節グループ名>` として書く**
- 部の概要ノートは `## 部の導入`（`partN_intro.md` の冒頭部分）＋ 節グループごとの `## <節グループ名>` という構成にする
- 第5部には節グループが無い。`00_第5部の概要.md` は `partN_intro.md` の導入だけで作る（13行なので**20〜30行の短いノートになってよい**）

### 9-2. 抽出の読み順が崩れている箇所（`[要確認]`）

Phase 0 で3件に `[要確認]` を付けてある（`col01` `col09` `col20`）。
**いずれも「COLUMN 末尾の文の続きがページ先頭に回り込んだもの」で、`<!-- 抽出の読み順の崩れ -->` のコメントが直前に入っている。**

- ノートには**その断片を要点として書かない**（文の途中なので意味が取れない）
- 代わりに、**ノート末尾に `## 要確認リスト` を作って1件記録する**（書き方は下の 9-4）
- **同じ崩れが他の章にもある。** 例: `ch10.md` の電子版 p.33 で、箇条書き
  `・あなたのユーザーや顧客の専門家になることから始める…` の先頭部分が
  `や企業で頼られる人になる。` として前に飛んでいる。
  **読んでいて文が途中から始まる・箇条書きの先頭が欠けていると気づいたら、
  直さずに `[要確認]` を付けて残す**（原文の並びに戻すのは判断になる）

### 9-3. OCR由来の誤字を直さない

本文に誤字が散在する（`私の念であり`＝信念、`頼関係`＝信頼関係、`確さ`、`頭著な`、
`1Q`＝IQ、`かってない`、`ロジェクトマネジャー`＝プロジェクトマネジャー、`しベル`＝レベル、
`給介`＝紹介、`画期的`＝画期的/画期的、`「T業界`＝IT業界 など）。

- **ノートに引くときは、意味が明らかな誤字は正しい語で書いてよい**
  （例: `信念` `信頼関係` `IQ` `プロジェクトマネジャー` `レベル`）。
  これは**原文の主張を変える補完ではなく、文字の復元**である
- ただし**意味が取れない箇所は復元しない。`[要確認]` を付けて原文の字面のまま残す**
- **章タイトルのダッシュ（`―`）は OCR が `ー` `一` に読み違えている。**
  「8. 章 → ノートの割り当て」の表と「4. Frontmatter」の `title` は
  すでに `―` に直した形で書いてある。**表から写せばよい**

### 9-4. `[要確認]` の書き方

- 本文中は**バックティック付きのインライン**: `` 文の途中から始まっている `[要確認]` ``
- そのノートに**2件以上**あるなら、**ノート末尾（`## 関連` の直前）に表でまとめる**

```markdown
## 要確認リスト

| # | 箇所 | 内容 |
|---|---|---|
| 1 | 電子版 p.21 冒頭 | 抽出の読み順の崩れ。COLUMN 末尾の文がページ先頭に回り込んでいる `[要確認]` |
```

### 9-5. 「プロフィール」の6章は人物紹介である

第15・21・32・40・57・63章は、実在のプロダクトマネジャーの事例（Google・Adobe・BBC・
Microsoft・Netflix・Apple）である。**テクニックの章と同じ体裁で書く**が、
`keywords` には**製品名・企業名と、その事例が示しているテクニック名**を入れる。
**人物の経歴を年表にしない**（本書の関心は「何を貢献したか」にある）。

### 9-6. 原文が他章を明示的に参照している箇所

原文に `CHAPTER 6「製品開発が失敗する根本的原因」で述べたような` `Chapter 44で述べたように`
のような**明示の参照がある場合だけ**、その章のノートへ `[[リンク]]` を張る。
**Phase 2 が自分で関連を探して張らない**（章をまたいだ整理は深掘りノートの仕事）。
