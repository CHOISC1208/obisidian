# Obsidian Vault — コンサルティング・ナレッジベース

このリポジトリは Obsidian の Vault そのものです。クライアントごとの企業構造・業務・システム棚卸などの調査結果を、あとから検索・接続できる形でストックしていくためのナレッジベースとして運用します。

## 使い方

- Obsidian でこのフォルダを Vault として開く（`.obsidian/` はすでに存在）。
- 同期は `.obsidian/plugins/obsidian-git` プラグイン経由で行う想定。
- 単発の資料（PDF・議事録の書き起こしなど）を渡されたときは、この Vault 内の Markdown ノートに変換して残す。**HTML レポートや Artifact のような「見せる用」の成果物は作らない**。正本（source of truth）は常にこの Vault の Markdown だけに置く。

## トップ階層

番号つきの4フォルダで、**内容の種類ごと**に分ける（2026-09-16 にこの構成へ移行）。

```
/
├── README.md          ← この Vault 自体の説明（このファイル）
├── 01_engineering/    ← クライアントを問わず使える技術ノウハウ・設定手順
├── 02_resume/         ← 自分の職務経歴。どこで何をしたか
│   ├── AGC株式会社/    ← 本業。人事評価15年分・受賞歴・取り組み内容
│   └── フリーランス/    ← フリーランス各社での取り組みの要約
├── 03_freelance/      ← クライアント案件の作業記録（日々の正本）
│   ├── 03-01_greenearth/
│   ├── 03-02_ケーテック/
│   └── 03-03_緑茶園/
├── 04_knowledge/      ← 学会・読書会など、案件に紐づかない学びのストック
│   ├── 学会/
│   └── 読書会/
├── _templates/        ← ノートのテンプレート（Vault 共通）
└── _tasks/            ← 作業指示・進捗・移行ログ。ノートではなく作業そのものの記録
```

各フォルダの `00 MOC.md` が入口：[[01_engineering/00 MOC|01_engineering]] ／ [[02_resume/00 MOC|02_resume]] ／ [[03_freelance/00 MOC|03_freelance]] ／ [[04_knowledge/00 MOC|04_knowledge]]

- **番号は並び順を決めるためのもので、優先度ではない。** 増えたら `05_` を足す。
- **`02_resume` と `03_freelance` は役割が違う。** 03 が日々の作業の正本、02 はそれを職務経歴として要約したもの。案件の状況が変わったら**まず 03 を更新**してから 02 へ反映する。
- クライアントが増えたら `03_freelance/03-0X_<短い名前>/` を追加する。

## クライアントフォルダの構成ルール

`03_freelance/03-0X_*/` の中は次の形を基本にする。

```
03-0X_<クライアント名>/
├── 00 MOC.md               ← そのクライアントの入口ノート（Map of Content）
├── _未確定事項.md          ← 打ち合わせをまたいで更新し続けるトラッカー。`_` 始まりで番号つきフォルダより上に並ぶ
├── 10-事業体/              ← 先方が何者か。会社・グループ・拠点ごとのプロフィールと、グループ全体を対象にした常設ノート（資本構造・沿革・理念・システム棚卸など）
├── 20-案件/                ← 期限のあるコンサル・開発案件。`<案件名>/` または `PRJ-NN-` 形式
│   └── <案件名>/
│       ├── <案件名> - 00 概要.md   ← その案件の入口
│       └── <案件名> - ....md
├── 30-プラットフォーム/     ← 自分が構築・運用するプロダクトと、そのインフラ・設計史・移植元
│   ├── <プロダクト名>/      ← プロダクトが2つ以上ならプロダクト名で分ける（1つなら直下フラット）
│   └── ...
├── 40-ツール/              ← 先方の業務で使われているシステム（先方所有・外部ベンダー製品・その調査・先方のIT環境）
├── 50-打ち合わせ/          ← 実施した打ち合わせ。1回1フォルダ（`YYYY-MM-DD/`）に議事録・事前アジェンダ・先方提供資料をまとめる
├── 60-テーマ/              ← 課題テーマごとの検討ノート（＝まだ答えが決まっていない論点）。任意
└── 70-〜/                  ← クライアント固有フォルダ（例：`70-ECモール/`）
```

- 各クライアントフォルダの `00 MOC.md` が唯一の入口。まずここを開けば全体像とリンク先が分かるようにする。
- **フォルダには番号プレフィックスを付けて並び順を固定する。** 数字は並び順で、優先度ではない。該当するノートが無いフォルダは作らない（例：先方の会社ノートが無ければ `10-事業体/` は作らない）。
- **フォルダは「読むため」ではなく「新しいノートの置き場所に迷わないため」に切る。** 読む導線は `00 MOC.md`（と案件・プラットフォームの入口ノート）が担うので、MOC のセクションをフォルダで再現しない。ノートが増えていく軸だけをサブフォルダにする。
- **直下に残すのは「どのフォルダにも属さないもの」だけ。** 調査時点のスナップショット（資本構造・沿革・理念・システム棚卸）は先方が何者かを書いたノートなので `10-事業体/` へ、1回の打ち合わせに紐づくもの（事前アジェンダ・先方提供資料）は `50-打ち合わせ/<日付>/` へ入れる。**打ち合わせをまたいで更新し続けるトラッカー**（要確認事項・課題一覧）は特定の日付に属さないので直下に置く。
- サブフォルダ内のノートには番号を付けない（`テーマ1 - ...` のようにタイトル自体が並び順を持つ場合、番号は二重になる）。議事録は `YYYY-MM-DD` 始まりのファイル名で日付順に並べる。**例外は次の2つ。** ①案件・プラットフォームの入口ノートは `<案件名> - 00 概要.md`（クライアントフォルダの `00 MOC.md` と同じ「入口」の役割。連番としての番号ではない）。②**連番で読むシリーズノートは番号を付けてよい** — `<名前> - NN …` / `PRJ-NN-` / `NN 名前` の3形式（例：`platform - 01 …`、`PRJ-01-商品マスタ構築`、`10-事業体/01 資本・ブランド構造`）。番号は `00 MOC.md` の一覧に載せた読む順序を表すもので、優先度ではない。
- **`60-テーマ/` と `20-案件/` は階層が違う。** テーマ＝まだ答えが決まっていない論点、案件＝そのうち1つを具体化してこちらが手を動かすもの。**案件は必ず親テーマにぶら下げ**、フロントマターに `親論点` と `フェーズ`（提案・要件定義／開発中／運用中）を書く。テーマ側にも `## 配下の案件` から逆リンクを張る。
- **`20-案件/` と `30-プラットフォーム/` も階層が違う。** 案件＝**期限のある**コンサル・開発の単位。プラットフォーム＝**期限なく構築・運用し続けるプロダクト**と、それを支えるインフラ・設計史・移植元。プロダクトが2つ以上あるクライアントはプロダクト名のサブフォルダに分ける。
- **`40-ツール/` に入れるのは「先方のシステム」だけ。** 先方が使っているツール・検討中のベンダー製品・先方のIT環境（例：クロスモール、kintone、M365テナント）。**自分が作る／作り直すものは、たとえ先方の業務を支える基盤でも `30-プラットフォーム/` か `20-案件/` に置く**（2026-09-21 に、それまでの「自作含めて `ツール/` に集約」を上書きした。自作と先方のものが同じ棚に並ぶと見分けられなくなったため）。同じテーマの下に自社案とベンダー案が並ぶときは、比較表はテーマ側に置く。
- **`40-ツール/` と `70-ECモール/` も分ける。** `40-ツール/` は先方が業務で使う道具、`70-ECモール/` は先方が出店している販売先（例：Amazon、LINEギフト、Shopify）。モールのAPI仕様や認証情報の取得手順は、それを使うツールが作り直されても変わらないので、案件・プラットフォーム側ではなく `70-ECモール/` に置く。
- **クライアント配下に「メモ」「未分類」フォルダは置かない。** 「メモ」は内容ではなく出自による分類で、置き場所として機能しない。内容で上のどれかに振り分ける。作業そのものの記録（移行ログ・作業指示）は Vault 共通の `_tasks/` へ。
- **案件・プラットフォームのノートには実装リポジトリを明記し、書く前にコードを確認する。** vault の記述は実装より遅れる。「関連リポジトリ」表にあるものは、状態を書き換える前に必ず現物を見る。

> [!note] 2026-09-21：3社を統一した
> それまで `03-01_greenearth` だけ `01-企業/` `02-案件/` `03-議事録/` `04-メモ/` `05-プラットフォーム/` という別体系だったが、上のルールに寄せた。**03-01 のノート命名 `PRJ-NN-` と frontmatter の `type:` は、上の例外②の範囲内としてそのまま維持している。** 各クライアントの `00 MOC.md` 末尾の「変更履歴」に、フォルダごとの移動先がある。

## 全フォルダ共通のルール

- ノート間の関連は `[[Wikilink]]` で必ず双方向につなぐ。参照するだけでリンクを張らない、ということはしない。
- 図解が理解を助ける箇所（資本関係、業務フロー、組織のハブ構造など）は Mermaid で描く。画像や外部ツールへの貼り付けは避け、Markdown 内で完結させる。
- **Mermaid は縦（`flowchart TD`）を既定にする。** 横並び（`LR`）は要素が3つ4つを超えると画面幅に収まらず読めなくなる。またノード内の日本語は空白が無く自動改行されないため、**`<br/>` で明示的に改行を入れる**（`timeline` 図は日本語が箱からはみ出すので使わない）。
- フロントマターに `tags` / `client` / `created` / `updated` を付け、後から `tags:` 検索やグラフビューで辿れるようにする。

## 新しい資料が来たときの手順

打ち合わせの議事録、先方からの共有資料、ベンダーの提案書など、あとから届くものは**既存ノートに足すのではなく、既存ノート全体を見直すきっかけとして扱う**。新しいノートを1本作って終わりにしない。

1. **先に既存ノートを読む。** 差分を取るために読むのであって、書き始める前に読む。
2. **資料は Markdown に変換して Vault に残す。** PDF や画像そのものは持ち込まない。図はMermaidで描き直し、表は表として書き起こす。
3. **既存の記述と突き合わせて、3つに仕分ける。**
   - *裏付けが取れたこと* — 既存の見立てが正しかった。そのまま残す
   - *新しく分かったこと* — 既存ノートに無い事実。該当ノートに反映する
   - *食い違うこと* — ここが最も重要
4. **食い違いは黙って上書きしない。** 元の記述を消して新しい情報に差し替えると、「なぜそう判断していたか」が失われる。`> [!warning]` で前提が動いた可能性として併記し、**確定するまでその領域の扱いは暫定**と明記する。どちらが正しいかは次のヒアリングで決める。
5. **影響のあるノートを全部更新する。** 資料1本が5〜10ノートに波及するのが普通。新ノートからのリンクだけでなく、**既存ノート側からの逆リンクも張る**（双方向のルール）。
6. **埋まった要確認事項にはチェックを入れ、何によって確定したかを書く。** `- [x] ~~項目~~ → **確定内容**（出典）` の形で、消さずに残す。
7. **呼称は正式名称に統一する。** 書き起こしの表記ゆれ（例：EasySystem→easyECS）は対応表として資料ノートに残し、検索性を保つ。
8. **読み取りや解釈が不確実な箇所は 〔 〕 で明示する。** 推測を断定として書かない。裏取りしていない製品機能は「先方の理解として記録」と但し書きを付ける。
9. **最後にリンク切れを確認する。**
