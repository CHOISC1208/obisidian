# Obsidian Vault — コンサルティング・ナレッジベース

このリポジトリは Obsidian の Vault そのものです。クライアントごとの企業構造・業務・システム棚卸などの調査結果を、あとから検索・接続できる形でストックしていくためのナレッジベースとして運用します。

## 使い方

- Obsidian でこのフォルダを Vault として開く（`.obsidian/` はすでに存在）。
- 同期は `.obsidian/plugins/obsidian-git` プラグイン経由で行う想定。
- 単発の資料（PDF・議事録の書き起こしなど）を渡されたときは、この Vault 内の Markdown ノートに変換して残す。**HTML レポートや Artifact のような「見せる用」の成果物は作らない**。正本（source of truth）は常にこの Vault の Markdown だけに置く。

## フォルダ構成のルール

```
/
├── README.md              ← この Vault 自体の説明（このファイル）
└── <クライアント名>/        ← クライアント単位のトップフォルダ
    ├── 00 MOC.md           ← そのクライアントの入口ノート（Map of Content）
    ├── 01 ... , 02 ...     ← 番号つきノート＝MOCに沿った読む順序（調査時点の常設ノート）
    ├── 事業体/             ← 法人・ブランドごとのプロフィール
    ├── ツール/             ← ツール横断ハブノート（先方が使っている／検討中の既存ツール）
    ├── テーマ/             ← 課題テーマごとの検討ノート（＝まだ答えが決まっていない論点）
    ├── 案件/               ← こちらが手を動かす個別の開発物。案件ごとにサブフォルダ
    │   └── <案件名>/
    │       ├── <案件名> - 00 概要.md   ← その案件の入口
    │       └── <案件名> - ....md
    └── 打ち合わせ/          ← 実施した打ち合わせの議事録（`YYYY-MM-DD ...`）
```

- クライアントが増えたら、ルート直下に新しいフォルダを追加する（`緑茶園グループ/` はその最初の例）。
- 各クライアントフォルダの `00 MOC.md` が唯一の入口。まずここを開けば全体像とリンク先が分かるようにする。
- ノート番号（`01`, `02`…）は Obsidian のファイルエクスプローラでの並び順を制御するためのもので、内容の優先度ではない。
- **フォルダは「読むため」ではなく「新しいノートの置き場所に迷わないため」に切る。** 読む導線は `00 MOC.md` が担うので、MOC のセクションをフォルダで再現しない。ノートが増えていく軸（事業体・ツール・テーマ・打ち合わせ）だけをサブフォルダにし、数が固定されているもの（沿革・理念など調査時点のスナップショット）は番号つきノートのままルート直下に置く。
- サブフォルダ内のノートには番号を付けない（`テーマ1 - ...` のようにタイトル自体が並び順を持つ場合、番号は二重になる）。議事録は `YYYY-MM-DD` 始まりのファイル名で日付順に並べる。**例外は案件フォルダの入口ノートだけで、`<案件名> - 00 概要.md` とする**（クライアントフォルダの `00 MOC.md` と同じ「入口」の役割。連番としての番号ではない）。
- **`テーマ/` と `案件/` は階層が違う。** テーマ＝まだ答えが決まっていない論点、案件＝そのうち1つを具体化してこちらが手を動かすもの。**案件は必ず親テーマにぶら下げ**、フロントマターに `親論点` と `フェーズ`（提案・要件定義／開発中／運用中）を書く。テーマ側にも `## 配下の案件` から逆リンクを張る。
- **案件フォルダに入れるのは「こちらの成果物」だけ。** 先方がすでに使っているツールや、比較検討中のベンダー製品は `ツール/` に置く（例：『店舗アップ♪』は案件ではなくツール）。同じテーマの下に自社案とベンダー案が並ぶときは、比較表はテーマ側に置く。
- **案件ノートには実装リポジトリを明記し、書く前にコードを確認する。** vault の記述は実装より遅れる。「関連リポジトリ」表にあるものは、状態を書き換える前に必ず現物を見る。
- ノート間の関連は `[[Wikilink]]` で必ず双方向につなぐ。参照するだけでリンクを張らない、ということはしない。
- 図解が理解を助ける箇所（資本関係、業務フロー、組織のハブ構造など）は Mermaid で描く。画像や外部ツールへの貼り付けは避け、Markdown 内で完結させる。
- **Mermaid は縦（`flowchart TD`）を既定にする。** 横並び（`LR`）は要素が3つ4つを超えると画面幅に収まらず読めなくなる。またノード内の日本語は空白が無く自動改行されないため、**`<br/>` で明示的に改行を入れる**（`timeline` 図は日本語が箱からはみ出すので使わない）。
- フロントマターに `tags` / `client` / `created` / `updated` を付け、後から `tags:` 検索やグラフビューで辿れるようにする。

## 新しい資料が来たときの手順

打ち合わせの議事録、先方からの共有資料、ベンダーの提案書など、あとから届くものは**既存ノートに足すのではなく、既存ノート全体を見直すきっかけとして扱う**。新しいノートを1本作って終わりにしない。

1. **先に既存ノートを読む。** 差分を取るために読むのであって、書き始める前に読む。
2. **資料は Markdown に変換して Vault に残す。** PDF や画像そのものは持ち込まない。図はMermaidで描き直し、表は表として書き起こす。
3. **既存の記述と突き合わせて、3つに仕分ける。**
   - *裏付けが取れたこと* — 既存の見立てが正しかった。そのまま残す
   - *新しく分かったこと* — 既存ノートに無い事実。該当ノートに反映する
   - *食い違うこと* — ここが最も重要
4. **食い違いは黙って上書きしない。** 元の記述を消して新しい情報に差し替えると、「なぜそう判断していたか」が失われる。`> [!warning]` で前提が動いた可能性として併記し、**確定するまでその領域の扱いは暫定**と明記する。どちらが正しいかは次のヒアリングで決める。
5. **影響のあるノートを全部更新する。** 資料1本が5〜10ノートに波及するのが普通。新ノートからのリンクだけでなく、**既存ノート側からの逆リンクも張る**（双方向のルール）。
6. **埋まった要確認事項にはチェックを入れ、何によって確定したかを書く。** `- [x] ~~項目~~ → **確定内容**（出典）` の形で、消さずに残す。
7. **呼称は正式名称に統一する。** 書き起こしの表記ゆれ（例：EasySystem→easyECS）は対応表として資料ノートに残し、検索性を保つ。
8. **読み取りや解釈が不確実な箇所は 〔 〕 で明示する。** 推測を断定として書かない。裏取りしていない製品機能は「先方の理解として記録」と但し書きを付ける。
9. **最後にリンク切れを確認する。**
