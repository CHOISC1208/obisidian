# 『店舗アップ♪』（株式会社日本ビジネス・サポート）

親: [[00 MOC|緑茶園グループ MOC]] ／ 検討文脈: [[テーマ1 - 受注チャネル統合とツール複数人化]] ／ 突き合わせ先: [[12 現行の受注フロー（先方提供資料）]]

> [!info] 出典
> ① 提案資料（PDF、2026年版）／② **受注管理ソフト『店舗アップ♪』要件書（2026年1月22日、株式会社日本ビジネス・サポート → 株式会社緑茶園様宛、全16ページ）**。
> ②は宛名入り・要件番号つきの正式な要件定義書であり、**すでに具体的な導入検討が進んでいた**ことを示す。

> [!warning] この要件書が示す最大の事実 — easyECSの置き換えが前提になっている
> 要件No.12「過去データ移行」に「**現行ソフト『EasyECS』の過去データを取り込めるようにします**」と明記されている。
> つまり本製品は easyECS の周辺補完ではなく**置き換え**として提案されており、しかもそれが **2026年1月時点**の話。[[2026-08-30 初回打ち合わせ]] の「easyECSを別システムへ変更したい」という発言は突然出たものではなく、**年初から進んでいた検討の続き**と読むべき。→ [[06 触らない領域]] の「easyECS＋クロスモールは残す」という前提の再確認が必要。

## 処理概要（9ステップ）

注文データ取り込み → 注文内容確認 → サンクスメール一斉送信 → 出荷日案内メール送信（予約注文） → 伝票処理（出荷作業＆出荷依頼） → お問い合わせ番号取得 → 出荷確認 → 出荷メール一斉送信 → 管理画面への出荷報告。

[[12 現行の受注フロー（先方提供資料）|社長が書いた現行フロー図の9ステップ]]とほぼ同じ骨格で、対応関係を取りやすい。

### 対応チャネル

楽天市場（API）／Amazon・Yahoo!ショッピング・au PAYマーケット・LINE GIFT・**自社サイト（Shopify）**・**ふるさと納税4サイト**（すべてCSV）／電話・FAX注文は手入力。

> [!caution] ふるさと納税には明示的な留保がついている
> 「ふるさと納税の注文データは**予告なしに頻繁に変わるケースがあり、その場合、即日対応は保証できません**。変更内容によっては費用をいただいての対応となります」。
> 現在🟥断絶中のふるさと納税が「対応可能」になるのは事実だが、**壊れやすさと追加費用のリスクを含む**。

### 配送連携

佐川「e飛伝Ⅲ」／ヤマト「B2クラウド」／**ヤマトweb出荷コントロールサービス（産直用）**。いずれもCSVの相互連携。

## 要件定義16項目（要点）

| No. | 項目 | 要点 |
|---|---|---|
| 1 | 注文データ取り込み・管理画面への反映 | 楽天はAPI、他はCSV。楽天ペイ対応（**サポート会員限定機能**）。APIオプション契約で楽天の送料・代引料以外の項目更新とAmazon出荷完了報告が可能（**別途月額費用**）。電話/FAX手入力は**PC1台での使用**（複数PCで同時使用は別途有償） |
| 2 | 配送方法の自動選定 | ヤマト／佐川を①出荷拠点②商品③クール便希望④配送エリアの優先順で自動設定。取り込み後の手動変更も可 |
| 3 | 出荷場所の自動選定 | 直送先を商品ごとに設定。商品マスタに出荷場所を追加取得。複数出荷場所は代表を登録し後から振り分け（一括置換可） |
| 4 | 出荷日 | 配送リードタイムから到着日を自動算出（逆算も可）。**休日カレンダー**で休日なら前倒し。目安出荷日（予定日）入力可。発送日一括確定、**シーズン商品（果物・母の日）は出荷集中のため日ごとの振り分けが必要**と明記 |
| 5 | 伝票処理 | 各送り状ソフトへのCSV出力と実績CSV取り込み。**温度帯に対応**。出荷日ベースで伝票処理 |
| 6 | ヤマトweb出荷コントロール | 産直用。**契約済みだが未使用**（全直送先で使うかは未定） |
| 7 | **注文内分割対応** | 送付先複数（配送業者・直送先・着日が異なる）／複数商品購入（配送方法・出荷場所・出荷日が異なる）に対応。**※必要かどうか対応時に要相談** |
| 8 | 金額変更 | クール便希望・離島出荷の送料加算を検索して手動変更。**楽天のみAPIでRMSへの送料変更が可能** |
| 9 | 配送追跡 | オプション機能。**※必要かどうか対応時に要相談**。タイムラグあり |
| 10 | **商品別/直送先別の集計表** | **産直先への出荷依頼件数がわかる集計画面（帳票）を新規作成**。現行はExcel管理。セット展開対応は**別途費用のオプション** |
| 11 | ステータス追加 | 注文単位で自由にステータスを作成・検索可（標準機能の保留フラグで対応） |
| 12 | **過去データ移行** | **EasyECSからのCSV移行**。出荷済データは件数制限あり。未出荷分は既存システムで処理完了後の移行を推奨。未処理データ移行は要相談（楽天API必要項目の欠落・送り状番号未取得・ステータス未反映などのリスクあり、**データ不備は保証外**）。立ち会うなら**訪問4日以上＋追加費用** |
| 13 | Amazonの出荷リードタイム取り込み | 注文レポートから取得（現行は管理画面で個別確認） |
| 14 | 出荷日お知らせメール | 予約商品対象。確定なら出荷日、未確定なら「〇日〜〇日」の目安。**送信済みかのステータス管理あり** |
| 15 | 検索ボタン | 確認不要の注文を除外・検索。**「確認する必要のある注文とは？」は要条件確認** |
| 16 | **商品マスタ／統一マスタ／直送先マスタ** | 独自項目＝配送方法・出荷場所・温度帯・出荷形態（産直／自社在庫／直送）・予約商品フラグ。**モールごとに異なる商品番号を統一して取り込める** |

## 動作環境・機器構成

インストール型（オンプレミス）。**FileMaker Pro 2025** ベースで、使用PC台数分のライセンス購入が必要。カスタマイズはFileMakerで柔軟に可能。

| 構成 | 内容 | 備考 |
|---|---|---|
| PC1台 | 店舗アップ♪＋FileMaker Pro 2025＋バックアップ用HDD | — |
| **PC2〜3台（ピアツーピア共有）** | 親機＋子機、全端末にFileMaker Pro 2025 | **提案書に「この構成でのご提案となります」と明記。ただし「FileMakerでは推奨していないやり方です」とも併記** |
| サーバー対応 | 専用サーバー機＋FileMaker Server 2025（5ライセンス込み、6台目以降は追加購入） | サーバー機のみMac可、**クライアントはWindows必須** |

将来のPC増設時は全端末のFileMakerバージョンを揃える必要があり、サーバー構成へ切り替える場合は**現在のFileMakerライセンスが使えなくなる**（5ユーザー以上の新規購入が必要）。

### 外部接続（導入前に社内側の準備が要る）

- 楽天API通信先（`api.rms.rakuten.co.jp` ほか）
- **Googleドライブ**：ファイル受け渡し・カスタマイズ対応・ファイル調査時に使用（専用ドライブ経由）
- 遠隔サポート：オーシャンブリッジ「ISL Light」（自社PCに直接入る必要がある場合のみ）
- SMTPによるメール送信（自社契約プロバイダ経由）
- サーバー運用時はポート5003・80・443。ルーター経由なら5003の開放が必要
- インストール時に最新JAVA／FileMaker ODBCインストーラー／C++ を導入
- 「社内セキュリティ上、環境によっては利用できない場合があります」との注記あり

| **スタッフごとのログイン** | **記載なし** | 🟥要質問 |
| **ステータスの追跡、メール送信者・日時の確認** | No.14でメール送信済みステータス管理はあるが、**「誰が送ったか」の記録は記載なし** | 🟥要質問 |
| **特記事項を検索・クレーム集計** | No.11ステータス追加・No.15検索ボタンで部分的に対応可か | 🟧要確認 |

| 取り寄せ発注商品の自動発注・発注書作成・入荷日登録 | 記載なし（仕入側は範囲外） | 🟥非対応 |
| 熨斗をわかるようにしたい | 明示なし（備考欄運用と推測） | 🟧要確認 |
| 温度帯・複数注文の注文分割 | **No.5温度帯対応・No.7注文内分割で対応**（No.7はオプション扱い） | 🟩対応 |
| 遠隔地への事前伝票発行 | No.6ヤマトweb出荷コントロールで対応 | 🟩対応 |
| 価格の変更等（apiでできるか） | No.8。**楽天のみAPIでRMS送料変更可**、他は手動 | 🟧部分 |
| モールへの伝票登録のAPI同期タイミング | No.1（楽天API／他はCSV、Amazon出荷完了報告はAPIオプション） | 🟩対応 |
| 過去データ・過去メールの保有期間 | No.12に件数制限の記載あり。保有期間そのものは記載なし | 🟧要確認 |

> [!important] 結論として押さえるべき点
> **業務処理（出荷・伝票・マスタ・集計）のカバー率は高いが、社長が赤字の筆頭に挙げた「誰が・いつ・何をしたか」の統制系は要件書に見当たらない。** [[10 開発中システム - EC Channel Console|EC Channel Console]] の弱点と**同じ穴**である可能性があり、次回の最重要質問。

## 社長が「魅力的」と評価した機能（要件No.7 注文内分割）

> さくらんぼ1箱＝6月発送、桃1箱＝9月発送、という1注文を、発送時期ごとの2注文に分けて扱いたい。

要件書では「複数商品購入で**配送方法・出荷場所・出荷日が異なる場合**」として正面から対応対象。ただし注意点が2つある。

1. **オプション扱い**：「※必要かどうか対応時に要相談」。標準は**受注分割**（注文を分割して別注文として扱う）で、要件書も「予約商品と通常商品を一緒に購入した場合は**受注分割で対応した方が管理しやすい**」「注文内分割が必要とする頻度が少なければ受注分割でかまいません」と書いている。**費用と要否をセットで確認すべき。**
2. 社長の懸念「大元のデータを変更するとAPIで修正が入る」について、要件書上でAPIによるモール側書き換えが明記されているのは **No.8（楽天のみRMSへの送料変更）** と **No.1（楽天ペイのステータス・送料・代引料・出荷情報の更新）**。分割そのものがモール側へ書き戻される記載はないため、**分割は店舗アップ♪内部の持ち方**である可能性が高い。ここも確認事項。
