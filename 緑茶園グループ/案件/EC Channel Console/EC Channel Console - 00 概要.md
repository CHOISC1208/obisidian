# EC Channel Console（開発中）

親: [[00 MOC|緑茶園グループ MOC]] ／ 親論点: [[テーマ1 - 受注チャネル統合とツール複数人化]]

> [!info] この案件ノートの位置づけ
> [[テーマ1 - 受注チャネル統合とツール複数人化]] が扱う「断絶チャネルをどう解消するか」という論点に対する、**自社開発側の具体案**。テーマ1には他に「[[店舗アップ♪（外部ベンダー製品）]] を導入」「easyECSごと載せ替え」という選択肢があり、3案の比較表はテーマ1側にある。
>
> **収録ノート**：[[EC Channel Console - 認証情報取得手順]]（先方担当者への配布用）／[[EC Channel Console - 変換器構想とMDC出力]]（2026-09-08〜の拡張構想）

## これは何か

複数のECモール（楽天市場／Amazon／Yahoo!ショッピング／au PAYマーケット／Shopify／Temu／LINEギフト）の受注データを、それぞれの公式APIで取得・表示する社内向けツール。緑茶園グループ向けに開発中で、[[03 業務フローとツール状況]] のSTEP3「受注」で挙げた**チャネル断絶（🟥）の解消**を目的としている。

- リポジトリ：`multi-channel-order-fetcher`（本Vaultとは別リポジトリ）
- 技術スタック：Next.js 16（App Router）／React 19／TypeScript／Tailwind CSS v4／fast-xml-parser（Yahoo・au PAYがXML応答のため）

> [!important] 2026-09-08：このツールの位置づけが「表示」から「変換器」へ広がった
> 先方から easyECS への不満が3点あがり（①一部CSV取込 ②CSVでも取り込めないチャネルがある ③SKUごとの発送リードタイムの可視化）、その回答として **EC Channel Console に2つの出力を足す構想**を整理した。
>
> ```
> [各チャネル]                [変換器 = EC Channel Console]      [出口]
> Shopify / LINEギフト   →  ┌─ MDC形式CSV出力  ──────→  easyECS（メール・送り状・番号返却）
> Temu / ふるさと納税     →  │
> 電話・カタログ（手入力） →  └─ 正規化受注明細  ──────→  受注残ボード（プラットフォーム）
> ```
>
> 同じやり取りで **easyECS のコア価値は「出口」（メール送信・送り状発行・送り状番号のモール返却）であって受注の集計ではない**ことが先方から明言された。つまり①②は入口の問題であり、載せ替えではなく「入口を作って出口に流す」のが打ち手になる。
> TODOは **4:受注残ボード → 2:手動取り込み → 3:MDC出力**（1:API調査は並行）。MDCはベンダーのサポート対象外という重い留保が付く。
> **詳細・リスク分析・次のアクションは → [[EC Channel Console - 変換器構想とMDC出力]]**

> [!success] 2026-09-08：easyECS のDBは **SQL Server**。読み取りはCSVに依存しなくてよくなる
> 同日のやり取りで、**easyECS のデータベースが SQL Server であること**と、**接続情報を先方が既に保有しており共有予定**であることが判明した。テーブル定義書もあわせて依頼済み。
> これにより **[[04 ツールリファレンス]]・[[09 初回すり合わせ論点]] の「インストール型」が正しい**ことが確定し、受注残ボード要件定義書が前提にしていた「ASP型＝データはベンダー側サーバにある」は誤りと判明。**§9（将来の自動連携）は前提ごと書き直しが必要。**
>
> **ただし読み取りと書き込みを対称に扱ってはいけない。** 読み取り（SQL Server 直参照）は壊れてもボードが映らないだけだが、書き込み（DB直INSERT）は受注番号の採番・関連テーブルの整合・メール送信や送り状連携のアプリ側ロジックを丸ごと迂回する。**書き込みはMDC経由を維持する**ため、TODO 3 の必要性は消えない。
> 未確認の前提が3つ（①「SQL Serverと認識」は先方の認識であり未検証 ②Vercel/Supabaseからの到達性＝**au PAYのIP制限と同じ構造の壁**が出る可能性 ③スキーマはベンダー非公開でバージョンアップで変わりうる）。→ [[EC Channel Console - 変換器構想とMDC出力]]

| au PAYマーケット | 🟧手作業（easyECSでCSV取込） | ⚠️ 実装済みだがデプロイ環境では未疎通（IP制限） | Wow!manager API `searchTradeInfoListProc` |

> 棚卸表で「🟥断絶」だった Shopify（自社EC）は、受注取得APIとしてはすでに実装済み。残る断絶は Temu・LINEギフトのみになった。
> ただし [[06 触らない領域]] の通り easyECS＋クロスモール自体は「残す」判断。このツールは**一元管理システムの載せ替えではなく、断絶チャネルを補う位置づけ**として説明するのが正確。[[09 初回すり合わせ論点]] の論点1（一元管理システムの将来性）と直結する。

## 受注取得の方式（クロスモールとの対比）

> [!important] 2026-09-07 追記：既製品のほうが堅い、とは限らないことが分かった
> クロスモール（I'LL社）の初期設定資料（Ver.付き・最終更新2025/03〜2026/08）を入手し、チャネルごとの受注取得方式を突き合わせた。**5チャネル中2つで、EC Channel Console のほうが直接的な経路を使っている。**

| チャネル | クロスモール | EC Channel Console |
|---|---|---|
| 楽天市場 | API | API |
| Amazon | **注文レポートの定期ダウンロード** | Orders v0 を直接呼ぶ |
| Yahoo!ショッピング | API | API |
| au PAYマーケット | API | API |
| [[Shopify]] | **注文確認メールのパース** | Admin GraphQL API を直接呼ぶ |

この差は運用制約として表面化する。クロスモールの資料に明記されている副作用は次の2つ。

- **Shopify**：注文確認メールを取り込む方式のため、クロスモール専用のメールアカウントを用意し、他のメーラーで受信しないようにする必要がある（先に受信されると取り込めない）。クロスモールは取込後にメールサーバから全メールを削除する。フリーメールも非推奨。
- **Amazon**：クロスモールが一定間隔で注文レポートをダウンロードするため、店舗側が「1日1度、自分で注文レポートをダウンロードする」といった**既存の運用が行えなくなる**。

> [!tip] この事実が動かす判断
> [[テーマ1 - 受注チャネル統合とツール複数人化]] の3案比較で暗黙の前提になっていた「既製品のほうが実装として堅い」は、**少なくとも受注取得については成り立たない**。ただし比較の射程は受注取得だけで、在庫送信・出品・画像アップ・配送便変換はクロスモールの領分（EC Channel Console のスコープ外）。比較の軸を「受注取得の堅さ」と「業務カバー範囲」に分けて論じる必要がある。

## au PAYマーケットのIP制限（デプロイ運用の穴）

> [!warning] 2026-09-07 判明：au PAYマーケットだけ、デプロイした状態では通らない
> au PAYマーケットのAPIは Wow!manager に登録した送信元グローバルIPからのリクエストしか受け付けない（5チャネルで唯一）。**Vercel等のサーバーレス環境は送信元IPが固定されないため、登録のしようがなく、本番URLからの取得は認証エラー `0002` になる。** 2026-09-07 に実機で確認済み。
> 「複数人利用の壁」は解消済みだが、**au PAYマーケットに限っては、デプロイ構成そのものが新しい壁になっている。**

対処は「送信元IPを固定する」しかない。

| 対処 | 費用 | 備考 |
|---|---|---|
| Vercel Static IPs | 月$100／プロジェクト | Pro以上のアドオン。もっとも素直だが、この規模には高い |
| 固定IPのVPSにプロキシを立て、au PAYへの通信だけ経由させる | 月数百円〜 | そのVPSのIPを登録する。クロスモールと同じ構造を最小構成で真似る |
| au PAYマーケットだけローカル実行 | 0円 | 複数人利用・自動実行には乗らない。暫定策 |

> [!success] 🟢 2026-09-09 決着：easyECS SQL Server連携用のVPSと兼用で実装済み
> [[EC Channel Console - 変換器構想とMDC出力|easyECS SQL Server直結]] のために立てたVPS（さくらのVPS・東京・Tailscale導入済み）に、au PAY中継プロキシ（Caddy、シークレットヘッダー認証、Let's Encrypt自動HTTPS）を同居させる形で構築・動作確認済み。**追加コストなしで両方の壁が解けた。**
> 実装詳細（`AU_PROXY_URL`/`AU_PROXY_SECRET`の使い方）はリポジトリ側が正本 → `~/git/multi-channel-order-fetcher/docs/credentials.md`「中継プロキシ経由で使う場合」。
> **残るのは、VPSのグローバルIPアドレスをWow!managerの「接続元IPアドレスを登録」に先方経由で登録してもらうことのみ。**

> [!info] 一元管理SaaSはどうしているか
> クロスモールは**14個の固定IP**（`121.83.254.*` の自社データセンター帯＋AWS東京の `13.112.7.206` など）を店舗に登録させている。ロジレスも4個を公開。**この種のAPIに繋ぐために各社が固定IPを確保している**というのが実態で、「クラウドだから動的IP」という話ではない。裏を返せば、月数百円のVPS1台で同じ構造は作れる。

## LINEギフトは実装できるか（2026-09-07 調査）

> [!success] 結論：**技術的には可能。ブロックしているのは仕様書の入手だけ**
> [[クロスモール（I'LL社）]] はLINEギフトを**APIで**連携している。認証はショップCMSの「アプリ > 新規登録」で発行する OAuth2 の認証情報で、**審査は無く即時発行**。楽天やYahoo!のような利用申請・リードタイムも、au PAYのようなIP制限も無い。5チャネルの中でもっとも取得が簡単な部類。

| 項目 | 内容 |
|---|---|
| 認証方式 | OAuth2 認可コードフロー（client_id / client_secret / refresh_token） |
| 発行元 | ショップCMS「アプリ > 新規登録」（アプリ名・Webアプリケーション・Redirect URI・API利用規約に同意） |
| 申請・審査 | **不要**。即時発行 |
| 有効期限 | アクセストークン60日。refresh_token から自動再取得 |
| 前提条件 | 登録するスタッフの権限が「受注: 閲覧可 以上」かつ「商品: 閲覧・変更可」 |
| IP制限 | **無し** |

> [!warning] ただし着手できない — 仕様書が一般公開されていない
> 「LINEギフト・LINEショッピング出店者向けAPI」の仕様書は公開されておらず、**エンドポイントのホスト名すら分からない**。一元管理各社（クロスモール／GoQSystem／ロジレス／コマースロボ）はいずれもAPI連携しているが、公開資料は「発行した認証情報を弊社システムに入力してください」までで、認可URL・トークンエンドポイント・受注APIのパス・レスポンス構造のいずれも出していない。
> 推測で書くと **au PAYマーケットと同じ「実データで照合するまで正しさが分からない」状態**になるため、実装は保留した。→ [[08 要確認事項]]

**実装時に効くチャネル固有の制約**（[[クロスモール（I'LL社）]] の資料より）

- **注文者情報（氏名・メールアドレス）が取得できない。** 取れるのはお届け先情報だけ。ギフトという商品性質上の仕様で、注文者へのメール送信もショップCMS側で行う必要がある。**受注一覧に「注文者名」を出す前提の画面設計はそのままでは成立しない。**
- ポイント・売上金による値引きが金額に反映されない（差し引かれていない額が返る）。
- 受注確定前の「仮注文」がある（お届け先が住所を確定するまで）。取り込み対象を「発送待ち」以降に絞るか、仮注文も扱うかは要件次第。

リポジトリ側の現状：認証情報の項目（`LINEGIFT_CLIENT_ID` / `LINEGIFT_CLIENT_SECRET` / `LINEGIFT_REFRESH_TOKEN`）は確定済みで、マスタ設定から保存できる。`lib/channels/linegift.ts` の冒頭コメントに上記の前提を書き残してある。
