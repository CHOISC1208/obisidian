# EC Channel Console 拡張構想｜変換器化とMDC出力

親: [[EC Channel Console - 00 概要]] ／ 親論点: [[テーマ1 - 受注チャネル統合とツール複数人化]]

> [!info] このノートの位置づけ
> [[EC Channel Console - 00 概要|EC Channel Console]] を「**受注データを見るツール**」から「**受注データを変換して流すツール**」へ拡張する構想。2026-09-08 に先方（[[EC Channel Console - 00 概要|EC Channel Console]] の依頼元）から easyECS への不満が3点あがり、その回答として整理したもの。
> **本ノートは構想段階**。実装判断は下の「TODO」と「MDC採用のリスク」を踏まえて行う。

## 経緯：先方から挙がった easyECS への不満（2026-09-08）

| # | 不満 | 先方の補足 |
|---|---|---|
| ① | インプットが一部CSV（APIをうまく使えていないモールがある） | 楽天=OK／Amazon=データ上CSVでOK／**au・Yahoo=CSV致し方なし** |
| ② | **CSVでも対応できないものがある** | ショピファイ・LINEギフト・Temu・受注ソフトが取り込めない。ふるさと納税は枚数？で管理 |
| ③ | 発送のリードタイムを、商品SKUごとに可視化 | 「プログラムを作ってくれたので要件定義書に落とした」＝**受注残ボード**で対応済み扱い |

> [!important] ①②は「入口」の問題であって、easyECS の代替が求められているわけではない
> 同じやり取りの中で、easyECS のコア価値が明言された。
> > ・メールをお客様の注文ごとに送る
> > ・送り状を発行する
> > ・請求データのキーとなる、送り状番号を各ショッピングモールに出力している
> > 上記、それぞれ大事な所なので、コアのシステムになっています。
>
> つまり **easyECS の価値は「出口」（メール・送り状・送り状番号の返却）にあり、「受注の集計」ではない**。ここは代替不可。だから打ち手は載せ替えではなく、**入口を作って出口に流し込むこと**になる。

## 構想：EC Channel Console を「変換器」にする

```
[各チャネル]                [変換器 = EC Channel Console]      [出口]
Shopify / LINEギフト   →  ┌─ MDC形式CSV出力  ──────→  easyECS（メール・送り状・番号返却）
Temu / ふるさと納税     →  │
電話・カタログ（手入力） →  └─ 正規化受注明細  ──────→  受注残ボード（プラットフォーム）
```

現在の EC Channel Console は「各チャネルのAPIを叩いて**表示する**」ところで止まっている。ここに **2つの出力**を足すと、①②③がまとめて解ける。

- **MDC形式CSV出力** → easyECS に流し込み、メール・送り状・番号返却を既存のまま使う（②の解消）
- **正規化受注明細** → 受注残ボードへ流し、SKU別の出荷予定を可視化する（③の解消）

> [!tip] 既存の要件定義とかみ合う
> 受注残ボードの要件定義書 §4.1 は、もともと「取り込みをアダプタ層に分離する」設計になっている。この構想は**その入力アダプタを増やし、出力アダプタを1本足すだけ**で、既存の設計思想を崩さない。

## 🟢 2026-09-08 追記：easyECS のDBは SQL Server。読み取りはCSVに依存しなくてよくなる

同日 18:19〜18:25 のやり取りで、**easyECS のデータベースが SQL Server であること**、および**接続情報を先方が既に保有しており共有予定**であることが判明した。

> [!quote] やり取り（2026-09-08 18:19〜18:25）
> **こちら**：easyECSのデータってCSV出力するしかないのでしょうか？ データベースがどこかにあって直接繋いだりとかもできますでしょうか？
> **先方**：データベースは**SQLサーバー**と認識しております。
> **こちら**：SQLSERVER の接続情報さえあれば今作られたものもCSV出力ではなく、**連動した形で**作れると思います
> **先方**：おおーー！それは嬉しいです！ **接続情報、前に頂いてるので、改めて共有致します**
> **こちら**：お願いします！ **テーブル定義書的なものもあればなおよし**です！

> [!important] これで「ASP型かインストール型か」が決着した
> [[04 ツールリファレンス]]・[[09 初回すり合わせ論点]] の**「インストール型」が正しい**。受注残ボード要件定義書が前提にしていた「ASP型のためデータはベンダー側サーバにある」は**誤り**であり、**§9（将来の自動連携）は書き直しが必要**。FTP/APIオプションの現実度比較は前提ごと不要になり、**SQL Server 直参照が本命**になる。

### 構想図の更新（読み取り経路が増える）

```
[各チャネル]                [変換器 = EC Channel Console]      [出口]
Shopify / LINEギフト   →  ┌─ MDC形式CSV出力  ──────→  easyECS（メール・送り状・番号返却）
Temu / ふるさと納税     →  │                                      │
電話・カタログ（手入力） →  └─ 正規化受注明細  ──────→  受注残ボード
                                    ↑                            （プラットフォーム）
          easyECS SQL Server ───────┘  ★読み取りは直結（CSV出力が不要になる）
```

> [!danger] 🔴 読み取りと書き込みを絶対に対称に扱わないこと
> **読み取り（SQL Server 直参照）は積極的にやってよい。書き込み（DBへの直INSERT）は絶対にやらない。**
>
> | | 読み取り | 書き込み |
> |---|---|---|
> | 手段 | **SQL Server 直参照** | **MDC形式CSV**（変更なし） |
> | 壊れたときの被害 | ボードが表示されないだけ。**業務は止まらない** | 受注データの破損。**出荷・請求が止まる** |
> | 迂回してしまうもの | なし | 受注番号の採番／関連テーブルの整合／メール送信・送り状連携のアプリ側ロジック |
>
> DBに直INSERTすると easyECS のアプリケーション層を丸ごと迂回することになり、**MDC以上にサポートから遠い行為**になる。TODO 3（MDC出力）の必要性は、DB直結が実現しても**消えない**。

### 直結で何が変わるか

| 箇所 | CSV前提（現行の要件定義） | SQL Server 直結 |
|---|---|---|
| 取り込み | 手動でCSVをアップロード | **定期ポーリングで自動**。§7.5 の取り込み画面の重要度が下がる |
| 列マッピング（§5.2） | ヘッダ名から自動判定＋手動マッピングUI | **テーブル定義が分かれば不要**。§7.5 の列マッピングUIも不要になる可能性 |
| 冪等性（§5.7） | ファイルハッシュで判定 | **主キーで判定できる**。ファイルハッシュは不要 |
| `1900/01/01` 問題（§5.4） | CSV上の文字列から推測 | **DB上でNULLか1900かを直接確認できる**。推測が消える |
| 更新頻度（§13-Q7） | 現行1日7回の手動出力 | **任意の頻度**。運用設計そのものが変わる |
| リードタイムの日数指標 | 保存済み `order_datetime` からビュー追加 | **出荷済みデータも引けるなら実績リードタイムが素直に出る** |

> [!warning] ただし前提が3つ未確認
> 1. **「SQL Serverと認識している」は先方の認識であって、確認された事実ではない。** 接続情報を受領してから確定させる
> 2. **ネットワーク到達性。** インストール型＝客先サーバなので、Vercel/Supabase から到達できるかは別問題。**[[EC Channel Console - 00 概要|au PAYマーケットのIP制限]] と同じ構造の壁**が出る可能性が高く、VPN／固定IPのVPS中継／社内実行のいずれかが要る
> 3. **スキーマはベンダー非公開かつバージョンアップで変わりうる。** MDCと同じ「サポート外」の構造リスクだが、**読み取りなら壊れても業務が止まらない**点が決定的に違う

### 実装上の作法（読み取り時）

- **読み取り専用ユーザで接続する**（更新権限を持たせない。事故を構造的に防ぐ）
- 本番DBへの直クエリは**ロック・負荷のリスク**があるため、`READ COMMITTED SNAPSHOT` かレプリカ/バックアップ参照を検討する。基幹の受注処理を止めたら本末転倒
- 接続情報は **EC Channel Console の既存の仕組みに乗せられる**（Supabase の `multi_channel_order_fetcher` テーブル、`service_role` 経由のサーバー専用処理、値は読み戻さない）。新しい仕組みは要らない

> [!tip] これは [[テーマ1 - 受注チャネル統合とツール複数人化|テーマ1]] の3案比較を動かす
> 2026-08-30 に社長が述べた狙いは「**いつ・何が・どれだけ必要か**を注文ベースで生産管理側（[[テーマ3 - KRKの標準化と接続|KRK]]）と共有すること」で、これが [[店舗アップ♪（外部ベンダー製品）]] への載せ替え検討の動機になっていた。
> **DB直結が通れば、載せ替えなしでこの狙いが達成できる可能性がある。** 「easyECSを別システムへ変更したい」の前提そのものが変わりうるため、[[06 触らない領域]] の再評価が要る。

### 「情報が足りない分は人に入れてもらう」を仕組みにする

チャネルによっては受注データにSKUや出荷予定日が揃わない。その場をしのぐ手入力にすると必ず腐るので、2つに分ける。

**① SKU対応表（マスタ・1回作れば再利用）**

| チャネル | チャネル側商品コード | 自社SKU |
|---|---|---|
| ふるさと納税 | FN-A0012 | GC-SENCHA-100 |
| Shopify | shopify-8821 | GC-SENCHA-100 |

初回取込時に未登録コードを検出 →「未対応SKU」として一覧提示 → 人が紐付ける → 次回以降は自動。受注残ボード要件定義 §7.5 の「列マッピングをユーザー単位で保存」と同じ思想。

**② 手入力フォーム（電話・カタログ用）**

SKU・数量・出荷予定日だけの最小フォーム。CSVアダプタと**同じ正規化スキーマに書き込む**ので、下流は一切変わらない。

### 正規化スキーマの必須項目は6つだけ

| 項目 | 必須 | 欠けたら |
|---|---|---|
| `order_no` | ○ | 取込拒否 |
| `product_name` | ○ | 取込拒否 |
| `sku` | ○ | SKU対応表で解決 |
| `qty` | ○ | 取込拒否 |
| `planned_date` | △ | 「予定日なし」枠へ |
| `is_open` | △ | 消し込み方式による（下記） |

住所・氏名・金額は**そもそも要らない**。受注残ボード要件定義 §8「個人情報を持たない」とも一致する。自作なら**最初から取り込まない**選択ができる。

> [!warning] 🔴 消し込みを誰がやるか — 自作取込の設計上の急所
> easyECS由来のデータは次回CSVに `配送進捗名 = 出荷済` が入るので**勝手に受注残から消える**。自作取込チャネルにはそれを返す相手がいない。**放置すると取り込んだ受注が永久に受注残に残り続ける。**
>
> | 方式 | 内容 | 適する場面 |
> |---|---|---|
> | **A. 差分スナップショット** | 毎回チャネルの未出荷分を全件取り込み、スナップショットごと置き換える | チャネルが未出荷一覧を出せる場合。**最も堅牢** |
> | **B. 出荷実績の取り込み** | 受注とは別に出荷済みリストを取り込んで消し込む | チャネルが出荷ステータスを持つ場合 |
> | **C. 画面から手動で閉じる** | ボード上でチェックして出荷済みにする | 電話・カタログなど少量チャネル |
>
> 既存の easyECS 経路は実質A。**Aを標準にすると構造が揃う。**

> [!warning] 二重計上の防止
> 楽天ふるさと納税のように **easyECS にも入っているチャネル**を別途取り込むと受注残が倍になる。`order_backlog_lines` に `channel` を持たせ、**1明細のソースは必ず1つ**というルールをデータモデルに入れる必要がある。

## MDC形式の解読（TODO 3 の前提）

出典：SAVAWAYサポートセンターより提供（2026-09-08）。`MDC受注CSVファイル仕様.pdf` ／ `MDC_Sample.csv`

### MDCとは何か

easyECS の**汎用受注取込フォーマット**。84列固定のCSVで、仕様書に「楽天形式受注CSVの『受注番号』『レコードナンバー』に対応」と明記されており、**楽天の受注CSVを下敷きにした派生フォーマット**。モール連携が用意されていないチャネルを流し込むための、ベンダー公式の唯一の入口。

### ファイル物性（パーサを書くときの前提）

| 項目 | 内容 |
|---|---|
| 文字コード | **Shift_JIS (CP932)** ※サンプル実測 |
| ヘッダ | あり（仕様書に★で明記） |
| クォート | **ダブルクォーテーション必須**（★明記） |
| 列数 | 仕様84列。**サンプルは行末カンマ付きで85フィールド**（末尾に空列） |
| 明細粒度 | **1行 = 1明細**。同一受注番号の複数行＝複数明細 |
| 取込順 | サイト受注番号順。**同じ受注番号は「下から」処理** |
| 改行 | **フィールド内に改行を含む**（No.43 注文者からの連絡事項に実在） |

> [!danger] 行単位の自前パーサでは必ず壊れる
> フィールド内改行があるため RFC4180準拠パーサが必須。加えて **仕様書とサンプルでヘッダ文字列が一致しない列がある**（No.12：仕様書 `手数料等金額` / サンプル `手数料等の金額`）。
> → **ヘッダ行はサンプルCSVの1行目をそのままコピーして使う。仕様書のヘッダ名を信じない。** マッピングは列順（位置）で行う。

### 受注残ボードとの突合で分かったこと

| # | 発見 | 影響 |
|---|---|---|
| 🔴 A | **MDCに「出荷日」列が存在しない**。あるのは No.49 `配達希望月日` → ECSの「配送日」のみ | MDC由来の受注は投入時点で必ず配送日フォールバック。出荷日はECS側の運用で後から埋まる |
| 🔴 B | `配達希望月日` の形式が「**希望なし** / 1月2日 / 3月4日」＝**年なしのM月D日** | 受注残ボード §5.4 の null 判定語彙（`指定なし`/`なし`/`未定`/`不明`/`-`/`ー`）に「**希望なし**」が無い。**1900/01/01 と同種の全件破壊バグ。語彙追加と回帰テストが必須** |
| 🟡 C | ステータス列が無い。`キャンセルフラグ` はあるがECSは「**今のところは見てない**」 | キャンセル済み注文をMDCに含めると生きた受注として入る。**投入前にキャンセル行を除外するのは変換器側の責務** |
| 🟡 D | SKU規則：`商品番号`(62) → 商品コード。販売スタイル使用時は `商品個別番号`(63) を **`_` で連結** | 既存の楽天/Amazon由来SKUと揃うかは、変換器が商品番号に何を入れるかで決まる |
| 🟡 E | サンプルに**同一受注番号＋`注文個別ID`違いの複数配送先**が実在。だがECSは `注文個別ID` を**使わない**（×）。しかも取込順が「同じ受注番号は下から」 | **複数配送先を1受注番号に持たせると配送先が上書きされる可能性が高い。受注番号自体を分けて投入するのが安全**。ギフト系（LINEギフト・ふるさと納税）が該当 |
| 🟢 F | `レコードナンバー`(3) は存在するがECSは**使わない**（×） | 受注残ボード §13-Q5「明細連番はあるか」への回答＝**期待できない**。冪等キーはファイルハッシュ主で確定 |

## 🔴 MDC採用のリスク（TODO 3 の最大の論点）

> [!quote] SAVAWAYサポートセンターの回答（2026-09-08）
> こちらについては実データ以外での取込については弊社サポートの対象外となります。
> その為、資料の提供は可能ですが実際にデータを取込の際やテストなどにエラーが出た場合でも弊社でのサポートは出来かねます。
>
> また、MDCについては機能としては残されている物の近年の取込改修等が行われておりません。
> 弊社にて共有したサンプルCSVの取込が出来る事は確認しましたが、実際の動作の保証が出来ない状態です、
> 例としては細かい金額の不一致等が発生する可能性があります。

言っていることは3つで、**重さが全く違う**。

| 主張 | 実質 | 深刻度 |
|---|---|---|
| サポート対象外 | **壊れても直してもらえない** | 🔴 本命 |
| 近年改修されていない | 仕様が2014年以前で停止 | 🟡 既知・回避可能 |
| 細かい金額の不一致 | **原因は特定済み** | 🟢 対処可能 |

### 「金額の不一致」の正体は特定できている

仕様書に証拠が残っている。

- No.70 `非課税フラグ`：「0：非課税 / **5：5%税計算する**」、ECSメモ「**すべて5%課税している**」
- No.9 `消費税タイプフラグ`：ECSは**見ていない**。代わりに初期設定ウィザードの「ストアの設定⑥」（内税/外税）で決まる

**消費税5%時代のまま**。「細かい不一致」ではなく「**税率が5%で計算される**」という再現性のある挙動であり、曖昧なリスクではない。

**回避策（要検証・2段構え）**

1. `非課税フラグ = 0`（非課税）を入れてECSに税計算をさせず、単価は税込価格を入れる
2. **MDC専用ストアをeasyECS上に新規に切り、「内税」設定にする**。既存の楽天/Amazonストアの設定を汚さない

### 金額はどこに効くのか

| easyECSの出口 | 金額不一致の影響 |
|---|---|
| 送り状の発行 | **ほぼ無害**（代引を除く） |
| 送り状番号のモール返却 | **無害**（番号だけ） |
| **注文ごとのメール送信** | 🔴 **顧客に誤った金額が届く＝事故** |

**代引を使わず、MDC経由チャネルでメール送信を使わなければ、金額不一致は実務上ほぼ無害化される。**

電話・カタログとふるさと納税は**送り状番号の返却先が無い**チャネルで、必要なのは送り状発行だけ。**リスクが最も低いところから入れるのが素直な順序**になる。

### 段階導入

```
電話・カタログ（月数件・返却先なし・金額の重要度低）
   ↓ 動いたら
ふるさと納税
   ↓ 動いたら
Shopify / LINEギフト / Temu
```

### その他の安全策

- **サンプルCSVを回帰テストの基準線にする** — SAVAWAYが「共有したサンプルCSVの取込ができることは確認した」と明言＝**動作確認済みの正常系**。自前生成CSVとの構造diffで、壊れる前に検出できる
- **投入前後の自動突合** — 投入CSVの `請求額` と、ECS取込後の受注データの支払合計を突合。差異が出たら止める

> [!danger] 一番効く心配は金額ではない
> **「改修が止まった機能に、送り状発行という業務クリティカルな導線を依存させること」**。金額は検証で潰せるが、これは潰せない。
>
> したがって設計原則を1つ置く：
> **コアは正規化スキーマに置き、MDC出力は「出力アダプタの1つ」に過ぎない状態を保つ。**
>
> 理由は2つ。
> 1. MDCが死んでも正規化データは無傷 → 手入力運用（TODO 2）や別の出口へ逃がせる
> 2. **[[テーマ1 - 受注チャネル統合とツール複数人化|テーマ1]] では easyECS 載せ替えが本命として進んでいる可能性がある**（[[店舗アップ♪（外部ベンダー製品）]] 要件No.12＝「EasyECSからの過去データ移行」、しかも2026-01-22時点）。載せ替えが決まればMDC出力は**丸ごと捨てる資産**になる → [[06 触らない領域]]
