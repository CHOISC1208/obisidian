# 画面設計（UI・UX）：仕入アプリ

親: [[Airtable再構築 - 00 概要|案件概要]] ／ 要件: [[Airtable再構築 - 要件定義ドラフト]] ／ データ: [[Airtable再構築 - Supabase実装（inventoryスキーマ）]]

> [!info] 本書の位置づけ
> 画面構成について**何をどう決めたか、なぜそう決めたか**を記録する。画面の実装仕様はリポジトリ `~/git/04_ryokuuchaen/ryokuchaen-inventory` の README を正本とし、ここには書かない。
> 判断の根拠となる数値は、2026-09-13 に `inventory` スキーマの本番データを読み取り専用で集計したもの。

## 進め方の前提（2026-09-13 合意）

- Airtableでの本番運用は続けたまま、POCアプリを作ってPDCAを回す。OKが出たら移行時期を決め、Airtableから最終抽出して一括で切り替える
- POC中にアプリで入力したデータは使い捨て。**抽出スクリプトは実行のたびに全件を消して入れ直す**（2026-09-13 決定）ので、抽出のたびに消える。練習は抽出の合間に1サイクル（入荷入力〜月締め）回す
  - 差分更新のままだと、アプリで区切った原価履歴の期間が抽出でAirtableの値に戻り、重複制約に反して抽出が失敗する。アプリと抽出がぶつからないよう、POC中のDBは常にAirtableと一致させる
- POC中にアプリで採番する連番（取引・支払明細書）は **100万番台から** 始め、Airtable側で振られる番号とぶつからないようにする
- 利用端末は事務所のPCが主。タブレットで使う可能性もある。スマホは想定しない

## データから分かった使われ方

| 事実 | 画面への影響 |
|---|---|
| 1日の入力は中央値10行、繁忙日の上位10%で37行以上、最大78行。6月と8〜9月に集中 | 繁忙期に数十行を素早く打てることを最優先にする |
| 取引の81%は過去に仕入れたことのある商品 | 規格9項目で検索させず、「その取引先がよく仕入れる商品」から選ばせる |
| 1取引先が取引したことのある商品は中央値4.5件、上位10%で16件以上、最大55件 | 候補の一覧は1画面に収まる |
| 2026年の生産者の取引531行のうち521行は、原価履歴の単価のまま | 単価は自動入力で足りる。違う単価にしたときだけ知らせる |
| 1日に入荷がある取引先は中央値2件 | 伝票は取引先ごとが基本 |
| 支払明細書は月5件前後、1件あたり中央値10行 | 月締めは取引先を上から順に片付ける作業リストの形で足りる |
| 取引先34件（KRK除く）のうち登録番号があるのは2件、支払日が未設定なのは6件 | 月締めで発行前に警告を出す |
| 取引明細の76%はKRK。支払明細書は0件で、明細の記録のされ方が生産者と違う | 生産者向けの月締めに混ぜない（→ [[Airtable再構築 - ヒアリング回答ログ]] Q6 回答待ち） |

## 全体構成（2026-09-13 決定）

- **左サイドバー**。見出しを「毎日／月次／マスタ／POC期間のみ」で分け、アイコンだけの表示に折りたためるようにする
  - 上部タブ案は、画面が10個前後あり、KRKの集計画面も加わりうるため横幅が足りなくなるので不採用
  - ホームにアイコンを並べる案（kintone風）は、画面を移るたびにホームへ戻る必要があり、毎日の入力には遠回りなので不採用
- **ホームを経由する**。KPIダッシュボードにはせず「今日やること」の入口にする。入荷入力ボタン、月締め待ち、要確認（単価0円・有効な原価なし・支払期日未設定など）、続きの入力を載せる
  - 放置すると月締めで困るものを毎日目に入れるため
  - 売上・仕入量の推移は、見たい指標が決まるまで載せない（→ [[08 要確認事項]]「ダッシュボードで見たい指標の優先順位」）
- **取引一覧は入荷入力とは別の独立メニュー**にする
- 規格マスタ8種はメニューに並べず、1画面のタブで切り替える
- ヘッダーに **「POC環境」の表示を常に出す**。Airtableと並行する期間に、どちらが本番かを取り違えないため

```
ホーム
毎日　　入荷入力／取引一覧
月次　　月締め／支払明細書
マスタ　取引先／商品・原価／規格マスタ
POC期間のみ　データ品質（migration_issues）
```

## 画面ごとの決定事項

### 入荷入力

- 取引先と取引日を選ぶと、その取引先の商品が「前回いつ・何個仕入れたか」付きで並び、数量を打つだけで伝票ができる
- 単価は原価履歴から自動で入れる。原価履歴と違う単価にしたときは知らせ、原価履歴も更新するかを選べる
- 返品は数量にマイナスを打たせず、「返品として入力」で登録する（実データに負の数量が13件）
- **1枚の伝票に複数の取引先の商品を混ぜられるようにする**（2026-09-13 決定。「あるかもしれない」ため）。取引先を選んで作るのが基本で、検索で他の取引先の商品も追加できる
- 「保存して次の伝票」で取引日を残したまま次へ進む

### 取引一覧

- 期間・取引先・支払い進捗で絞り込み、複数行を選んで進捗をまとめて変える。現行も口頭で入金依頼したあとに手で進捗を変えている（→ [[Airtable再構築 - ヒアリング回答ログ]] Q5）
- 支払明細書を発行済みの行はロックし、明細書と金額が食い違わないようにする
- CSV出力を付ける。現行もCSVを書き出してExcelのピボットで集計しているため（→ ヒアリング回答ログ Q1）

### 月締め・支払明細書

- 清算指示待ちの明細がある取引先を件数付きで並べ、取引先ごとに発行する
- **締め日は月末に固定**し、「何月分か」を選ぶ（2026-09-13 決定。月中締めは不自然なので運用上ない）。過去80件のうち11件ある月中の締め日は、移行データとしてそのまま残す
- 支払期日は取引先の支払条件から自動計算し、手で変更もできる
- 税率ごとに合計する。登録番号が未登録の取引先には発行前に警告する
- **発行後に誤りが見つかったら「明細書を取り消す → 明細を直す → 発行し直す」**（2026-09-13 決定）。取り消した明細書の番号は欠番にして使い回さない
- KRKは Q6 の回答が来るまでこの一覧に出さない

### マスタ（取引先・商品・規格）

- **POCでも画面で登録・編集できるようにする**（2026-09-13 決定）。当初は閲覧のみにしていた
- 削除は、どこからも使われていない行だけ。使われているものは「取引終了」「終売」にしてもらう。2026-07にマスタ削除で取引データが巻き添えになった事故の再発防止（→ [[Airtable再構築 - ヒアリング回答ログ]] Q2）
- 取引がある商品は、取引先を変えられない。変えると過去の取引の取引先まで変わってしまうため
- 新しい商品の商品コードは、既存と同じ「0014-連番」で自動採番する
- 入荷入力で商品が見つからないときは、商品登録画面へのリンクを出す。入力中の伝票はブラウザに残るので、登録後に戻って続けられる
- POC中の編集も、抽出スクリプトを実行するとAirtableの内容に戻る
- **商品・原価は、別画面ではなく一覧の右に開くサイドピークで編集する**（2026-09-13 決定）。一覧の絞り込み条件を保ったまま、商品を次々に開いて直せるようにするため。開いている状態はURLに持つので、ブラウザの「戻る」やリンクの共有も効く
- **取引先を選ぶ欄は、入力すると候補が出る形にする**（2026-09-13 決定）。取引先は35件あり、プルダウンで探すより名前やフリガナの一部を打つ方が速いため。ひらがなで打ってもカタカナのフリガナに当たるようにした。入荷入力・取引一覧・商品一覧・商品フォームで共通

## 未決事項

- KRKの取引の扱い（除外の意味・単価0円・備考の地名）→ [[Airtable再構築 - ヒアリング回答ログ]] Q6
- **「月締め登録済み」が何を表すか。** 2026-09-13のPOC実装中に判明。「清算指示待ち」のまま8月分の支払明細書（6件）に紐づいている明細が114行あり、逆に「月締め登録済み」なのに明細書に紐づいていない明細が43行ある
  - Relayの設計では「明細書に紐づけたら月締め登録済み」だった。一方、実運用では口頭で入金依頼したあとに手で変えている（→ ヒアリング回答ログ Q5）
  - そのため今は「明細書は作ったが入金依頼はまだ」の状態が「清算指示待ち」のまま残っていると読める
  - POCは設計どおり**発行と同時に「月締め登録済み」**にしている。入金依頼の段階を別に持つ必要があるかは先方に確認する
- 納品書画像を伝票単位で持つ場合の置き場所。現行DBには伝票（複数明細のまとまり）のテーブルが無く、Airtableでは取引1行ごとに添付していた
- 支払明細書PDFの作り方（DocsAutomator継続か自前か）→ [[Airtable再構築 - 要件定義ドラフト]] M6。POCでは印刷用画面からブラウザでPDF化する
