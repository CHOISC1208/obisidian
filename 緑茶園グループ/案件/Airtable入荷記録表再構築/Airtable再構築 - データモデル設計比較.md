# データモデル設計比較：AS-IS（Airtable現状）／TO-BE（新システム提案）

親: [[Airtable再構築 - 00 概要|案件概要]] ／ 要件本体: [[Airtable再構築 - 要件定義ドラフト]]（M2 データモデル設計の詳細版）

> [!info] 本書の位置づけ
> Airtableベース `appgHXd85EhNBuXlt`（【現行】入荷記録表）の全23テーブル・フィールド構成をAirtable APIで取得した実際のスキーマ・レコード件数に基づく（調査日 2026-09-05）。〔仮〕マークの箇所は現場ヒアリングで確定する。

> [!warning] 顧客リストの件数は要再確認
> [[Airtable再構築 - 要件定義ドラフト]] のスコープ表で「顧客マスタ管理（顧客リスト）の実データは2件のみ」としていたが、本書の調査で**「顧客リスト」テーブルと「取引先」テーブル（35件）を混同していた可能性**が判明した。「顧客リスト」自体の正確な件数は〔要再確認〕（→ [[#質問リスト]] 最終行）。判明するまで、要件定義ドラフト側の「顧客マスタ管理」行の優先度判断（Must→Want〔仮〕）は暫定のまま扱う。

### 商品マスタ（73フィールド）の内訳と問題

| 種類 | 件数目安 | 問題点 |
|---|---|---|
| SKU/タイトル生成のformula | **6個** | 微妙に組み合わせ・順序が異なる式が並存。用途が「表示名」なのか「集計キー」なのか式ごとに違う |
| 取引内容一覧からのrollup | **12個以上** | 同じ参照元フィールドから月別に複製されたrollupが並ぶ（1月〜12月個別＋copy） |
| 他テーブルへのリンク | 11個 | 7マスタ＋取引先＋原価履歴＋旧入荷記録表＋取引内容一覧＋納品書作成 |
| 壊れたフィールド | **1個** | `multipleLookupValues`型が`isValid: false` |
| 用途不明なsingleLineText | 10個以上 | 「11階級」「量目2」等、命名から用途が読み取れない |

**具体的な6つのSKU/タイトル系formula：**

| フィールド名 | 組み合わせ内容 | 使用状況（2026-09-11回答、[[Airtable再構築 - ヒアリング回答ログ]] Q1） |
|---|---|---|
| 商品タイトル | 取引先＋品種＋荷姿＋等級＋階級＋量目＋玉数房数＋入数（リンク参照） | ✅唯一の実使用formula。【4】商品マスタ・【2】取引内容一覧で使用。取引先＋商品規格でユニークな規格として扱われ、原価履歴の紐づけ単位もこれに合わせている |
| 【集計用】商品タイトル | 品種＋荷姿＋等級＋階級＋量目＋入数（一部は選択肢参照に差し替え） | 現在不使用（機能のみ残存）。規格単位の集計を狙った名残。現在はCSV書き出し＋Excelピボットで代替 |
| SKU | 商品コードA＋（100＋商品コードB） ※唯一の構造化コード。他はすべて人間可読な表示名 | 目的・仕様とも回答者未把握。ただし楽天・Amazon等の外部モール商品コードと認識されており、crossmallで管理（管理ルール不明）。1商品規格が複数のSKUに対応する場合あり |
| 販売規格名組合せ | 品種＋等級＋階級＋荷姿＋量目 | 目的・仕様とも回答者未把握 |
| 商品 | 取引先＋品種＋荷姿＋等級＋階級＋量目＋入数＋玉数房数＋¥原価 | 目的・仕様とも回答者未把握 |
| 【集計用】荷姿＊等級＊階級＊入数＊量目 | 品種＋荷姿＋等級＋階級＋量目＋入数＋玉数房数 | 現在不使用（機能のみ残存）。【集計用】商品タイトルと同じ経緯 |

> [!tip] 一意キーの仮説 → 2026-09-11 回答で確定・修正
> ✅回答済み（[[Airtable再構築 - ヒアリング回答ログ]] Q1）：仮説は外れ。**実際に運用されている一意キーは「SKU」ではなく「商品タイトル」（取引先＋商品規格8要素、商品ごとに一部要素を省略する例外あり）**。原価履歴の紐づけ単位もこれに合わせている。実際に使われているformulaは商品タイトルの1つのみで、【集計用】商品タイトル／【集計用】荷姿＊等級＊階級＊入数＊量目は現在不使用（機能だけ残存、集計はCSV書き出し＋Excelピボットで代替済み）。SKU／販売規格名組合せ／商品の3formulaは回答者（水田）も目的・仕様を把握していない。
> ⚠️新事実：**「SKU」フィールド（商品コードA＋B）は内部の一意識別子ではなく、楽天・Amazon等の外部モールの商品販売コードで、crossmallで管理されている**らしい。1つの商品規格が複数のSKU（外部モールコード）に対応する場合がある。→ TO-BEの`products.sku`は「内部一意キー」ではなく「外部モールコードの1つ（複数対応が必要かもしれない）」として設計し直す必要がある（→ [[Airtable再構築 - 要件定義ドラフト]] 参照）。

### 品種テーブル（45フィールド）の内訳と問題

質問リストで挙げていた「品種テーブルの中身」を確認したところ、**予想通り「等級×荷姿の組み合わせ別の集計」が大量に同居**していた。

| 種類 | 件数目安 | 具体例 |
|---|---|---|
| 等級×荷姿別の数量rollup | **11個以上** | 「秀 M ダイヤパック」「秀 L ダイヤパック」「特秀 L チョコ箱」「特秀 L 鏡詰め」「特秀 2L ダイヤパック」「特秀 2L 鏡詰め300」「特秀 2L 鏡詰め500」「特秀 2L 桐箱300」「特秀 2L チョコ箱」「特秀 3L 鏡詰め」「秀品 2L ダイヤパック」——商品マスタの等級・荷姿の組み合わせごとに、品種テーブル側でも個別集計フィールドを手動で足してきた形跡 |
| 年別の取引額・数量集計 | 複数 | 「24年取引額合計」「25年取引額合計（税込）」「25年取引額平均（税込）」「25年数量総合計」「2019年数量」など、年が変わるたびにフィールドを追加してきたパターン |
| フィールド重複（等級） | 4個 | 「9️⃣等級」「9️⃣等級 copy」「9️⃣等級 copy copy」「9️⃣等級 copy 2」——リンクフィールドとテキストフィールドが混在した重複 |
| フィールド重複（荷姿） | 2個 | 「14荷姿」がテキスト版とリンク版の2バージョン |

> [!tip] 商品マスタ・販売規格・月統計・年統計と同じ設計パターン
> 品種テーブルは、[[#商品マスタ（73フィールド）の内訳と問題|商品マスタ]]・[[#販売規格・月統計・年統計（65／39／39フィールド）|販売規格・月統計・年統計]]とまったく同じ「**取引先名や年を冠したrollupを都度追加してきた**」設計パターンの繰り返しである。マスタテーブル（本来はid・nameだけで足りるはず）にまで同じ増殖パターンが及んでいたことになり、TO-BEでの正規化対象は商品マスタ・統計系だけでなく**品種マスタ自体にも及ぶ**。

### 販売規格・月統計・年統計（65／39／39フィールド）

3テーブルとも、フィールドの大半が「取引先名を冠したrollup」（例：「阿部大介 取引数量」「大石果樹園 平均取引額」）。**取引先が増えるたびに手動でフィールドを追加してきた**設計で、正規化されていない。新設計ではこれをSQLの集計クエリ（GROUP BY）1本に置き換えられる。

## 2. TO-BE：提案する正規化スキーマ

Supabase（Postgres）を前提とした設計案。[[Airtable再構築 - 要件定義ドラフト]] のM2「データモデル設計」に対応。

```
【マスタ系】
species (種別)         id, name
varieties (品種)       id, species_id(FK), name
grades (等級)          id, name
classes (階級)         id, name
weights (量目)         id, name
counts_per_pack (入数)  id, name
piece_counts (玉数・房数) id, name
packagings (荷姿)      id, name
partners (取引先)      id, name, postal_code, address1, address2, phone, fax,
                       invoice_registration_number 〔仮・新設〕, is_taxable_business 〔仮・新設〕
  -- 2026-09-11判明：支払明細書テンプレートに登録番号欄が存在しない（→[[Airtable再構築 - ヒアリング回答ログ]] Q4）。
  --   仕入明細書としてインボイス控除に使うには取引先（生産者）の登録番号・課税事業者区分の管理が必要になる可能性

【商品】
products (商品マスタ)
  id (内部PK。取引先＋規格8要素の組み合わせに対する一意キーとして採番。旧「商品タイトル」formulaが担っていた役割)
  species_id, variety_id, partner_id,
  grade_id, class_id, weight_id, count_id, piece_count_id, packaging_id
  status (販売中/終売/保留中)
  tax_category (8%/10%)
  created_at
  -- display_name はDBに保存せず、アプリ側の関数で都度生成する
  --（実使用は「商品タイトル」formula1本のみと判明。2026-09-11回答→[[Airtable再構築 - ヒアリング回答ログ]] Q1。
  --  8要素のうち商品によって一部を省略する例外があるため、値がある要素だけを結合するロジックにする）

marketplace_codes (外部モールSKU) 〔仮・新設〕
  id, product_id(FK), channel (楽天/Amazon/crossmall管理チャネル等), code
  -- AirtableのSKUフィールド（商品コードA＋B）は内部一意キーではなく、
  --   楽天・Amazon等の外部モール商品コードで、crossmallで管理されている疑い（2026-09-11回答）。
  --   1商品規格が複数の外部モールコードに対応する場合があるため1:Nで別テーブルに切り出す想定。
  --   商品コードAの入力ルール・crossmall側の管理ルールは未確認 → 要ヒアリング

price_history (原価履歴)
  id, product_id(FK), effective_from, effective_to,
  purchase_price, sale_price

【取引】
transactions (取引内容一覧)
  id, transaction_date, product_id(FK), partner_id(FK),
  quantity, purchase_price, sale_price, payment_status
  -- 月別rollup(1月～12月個別フィールド)は廃止し、
  --   SELECT date_trunc('month', transaction_date), SUM(quantity)
  --   GROUP BY 1 のクエリ1本に置き換える

monthly_batches (月締め入荷記録)
  id, target_month, transaction_id(FK)

【販売】
customers (顧客リスト)
  id, name, address, phone, fax, email

delivery_notes (納品書)
  id, customer_id(FK), issued_date, delivery_note_number

delivery_note_lines (納品書明細)
  id, delivery_note_id(FK), transaction_id(FK)

invoices (請求書)
  id, customer_id(FK), issued_date, invoice_number,
  tax_8_amount, tax_10_amount

invoice_lines (請求書明細)
  id, invoice_id(FK), delivery_note_id(FK)
```

### AS-IS → TO-BE 対応表

| AS-IS | 件数/問題 | TO-BE | 解消される問題 |
|---|---|---|---|
| 商品マスタ 73フィールド | SKU式6個（実使用1個のみ）、rollup12個以上、壊れたfield1個 | products テーブル + アプリ側関数1個 + marketplace_codesテーブル〔仮・新設〕 | 表示ロジックとデータを分離。壊れたfieldは削除。外部モールSKUを内部PKから分離し1:N対応可能に |
| 品種テーブル 45フィールド | 等級×荷姿別rollup11個以上＋年別集計＋等級/荷姿フィールドの重複4個 | varieties テーブル（id, species_id, nameのみ） | 集計はSQLクエリへ、重複フィールドは削除。マスタが本来のマスタサイズに戻る |
| 販売規格・月統計・年統計 計143フィールド | 取引先名を冠したrollupを手動追加し続ける構造 | SQLクエリ（ビューまたはAPI関数） | 取引先が増えてもテーブル構造の変更が不要になる |
| 【8】旧・入荷記録表 | レガシー、役割重複の疑い | 移行対象外（アーカイブのみ） | 現行テーブルとの二重管理を解消 |
| 「◯◯ copy」系フィールド多数 | 商品マスタだけで5個以上確認 | 削除 | 保守対象を削減 |
