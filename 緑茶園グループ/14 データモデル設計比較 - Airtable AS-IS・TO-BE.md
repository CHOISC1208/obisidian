# データモデル設計比較：AS-IS（Airtable現状）／TO-BE（新システム提案）

親: [[00 MOC|緑茶園グループ MOC]] ／ 要件本体: [[13 要件定義ドラフト - Airtable入荷記録表フルスクラッチ再構築]]（M2 データモデル設計の詳細版）

> [!info] 本書の位置づけ
> Airtableベース `appgHXd85EhNBuXlt`（【現行】入荷記録表）の全23テーブル・フィールド構成をAirtable APIで取得した実際のスキーマ・レコード件数に基づく（調査日 2026-09-05）。〔仮〕マークの箇所は現場ヒアリングで確定する。

> [!warning] 顧客リストの件数は要再確認
> [[13 要件定義ドラフト - Airtable入荷記録表フルスクラッチ再構築]] のスコープ表で「顧客マスタ管理（顧客リスト）の実データは2件のみ」としていたが、本書の調査で**「顧客リスト」テーブルと「取引先」テーブル（35件）を混同していた可能性**が判明した。「顧客リスト」自体の正確な件数は〔要再確認〕（→ [[#質問リスト]] 最終行）。判明するまで、note 13 側の「顧客マスタ管理」行の優先度判断（Must→Want〔仮〕）は暫定のまま扱う。

### 商品マスタ（73フィールド）の内訳と問題

| 種類 | 件数目安 | 問題点 |
|---|---|---|
| SKU/タイトル生成のformula | **6個** | 微妙に組み合わせ・順序が異なる式が並存。用途が「表示名」なのか「集計キー」なのか式ごとに違う |
| 取引内容一覧からのrollup | **12個以上** | 同じ参照元フィールドから月別に複製されたrollupが並ぶ（1月〜12月個別＋copy） |
| 他テーブルへのリンク | 11個 | 7マスタ＋取引先＋原価履歴＋旧入荷記録表＋取引内容一覧＋納品書作成 |
| 壊れたフィールド | **1個** | `multipleLookupValues`型が`isValid: false` |
| 用途不明なsingleLineText | 10個以上 | 「11階級」「量目2」等、命名から用途が読み取れない |

**具体的な6つのSKU/タイトル系formula：**

| フィールド名 | 組み合わせ内容 |
|---|---|
| 商品タイトル | 取引先＋品種＋荷姿＋等級＋階級＋量目＋玉数房数＋入数（リンク参照） |
| 【集計用】商品タイトル | 品種＋荷姿＋等級＋階級＋量目＋入数（一部は選択肢参照に差し替え） |
| SKU | 商品コードA＋（100＋商品コードB） ※唯一の構造化コード。他はすべて人間可読な表示名 |
| 販売規格名組合せ | 品種＋等級＋階級＋荷姿＋量目 |
| 商品 | 取引先＋品種＋荷姿＋等級＋階級＋量目＋入数＋玉数房数＋¥原価 |
| 【集計用】荷姿＊等級＊階級＊入数＊量目 | 品種＋荷姿＋等級＋階級＋量目＋入数＋玉数房数 |

> [!tip] 一意キーの仮説
> **本当の一意キーは「SKU」（商品コードA＋B）である可能性が高い**。残り5つは表示・集計用の別名で、作り直すたびに前のものが残った形跡。→ [[#質問リスト]] 上位2問で裏取りする。

### 販売規格・月統計・年統計（65／39／39フィールド）

3テーブルとも、フィールドの大半が「取引先名を冠したrollup」（例：「阿部大介 取引数量」「大石果樹園 平均取引額」）。**取引先が増えるたびに手動でフィールドを追加してきた**設計で、正規化されていない。新設計ではこれをSQLの集計クエリ（GROUP BY）1本に置き換えられる。

## 2. TO-BE：提案する正規化スキーマ

Supabase（Postgres）を前提とした設計案。[[13 要件定義ドラフト - Airtable入荷記録表フルスクラッチ再構築]] のM2「データモデル設計」に対応。

```
【マスタ系】
species (種別)         id, name
varieties (品種)       id, species_id(FK), name
grades (等級)          id, name
classes (階級)         id, name
weights (量目)         id, name
counts_per_pack (入数)  id, name
piece_counts (玉数・房数) id, name
packagings (荷姿)      id, name
partners (取引先)      id, name, postal_code, address1, address2, phone, fax

【商品】
products (商品マスタ)
  id, sku (一意, NOT NULL)
  species_id, variety_id, partner_id,
  grade_id, class_id, weight_id, count_id, piece_count_id, packaging_id
  status (販売中/終売/保留中)
  tax_category (8%/10%)
  created_at
  -- display_name はDBに保存せず、アプリ側の関数で都度生成する
  --（6つのformulaを1つのTypeScript関数に統合）

price_history (原価履歴)
  id, product_id(FK), effective_from, effective_to,
  purchase_price, sale_price

【取引】
transactions (取引内容一覧)
  id, transaction_date, product_id(FK), partner_id(FK),
  quantity, purchase_price, sale_price, payment_status
  -- 月別rollup(1月～12月個別フィールド)は廃止し、
  --   SELECT date_trunc('month', transaction_date), SUM(quantity)
  --   GROUP BY 1 のクエリ1本に置き換える

monthly_batches (月締め入荷記録)
  id, target_month, transaction_id(FK)

【販売】
customers (顧客リスト)
  id, name, address, phone, fax, email

delivery_notes (納品書)
  id, customer_id(FK), issued_date, delivery_note_number

delivery_note_lines (納品書明細)
  id, delivery_note_id(FK), transaction_id(FK)

invoices (請求書)
  id, customer_id(FK), issued_date, invoice_number,
  tax_8_amount, tax_10_amount

invoice_lines (請求書明細)
  id, invoice_id(FK), delivery_note_id(FK)
```

### AS-IS → TO-BE 対応表

| AS-IS | 件数/問題 | TO-BE | 解消される問題 |
|---|---|---|---|
| 商品マスタ 73フィールド | SKU式6個、rollup12個以上、壊れたfield1個 | products テーブル + アプリ側関数1個 | 表示ロジックとデータを分離。壊れたfieldは削除 |
| 販売規格・月統計・年統計 計143フィールド | 取引先名を冠したrollupを手動追加し続ける構造 | SQLクエリ（ビューまたはAPI関数） | 取引先が増えてもテーブル構造の変更が不要になる |
| 【8】旧・入荷記録表 | レガシー、役割重複の疑い | 移行対象外（アーカイブのみ） | 現行テーブルとの二重管理を解消 |
| 「◯◯ copy」系フィールド多数 | 商品マスタだけで5個以上確認 | 削除 | 保守対象を削減 |

## 3. SKU（商品タイトル）ロジックに関する質問リスト

| 質問 | なぜ必要か | 影響範囲 |
|---|---|---|
| 6つのSKU/タイトル系formula（商品タイトル・【集計用】商品タイトル・SKU・販売規格名組合せ・商品・【集計用】荷姿＊等級＊階級＊入数＊量目）のうち、**実際に画面・帳票・検索で使われているのはどれか**。 | 移植すべきロジックを1つに絞り込むため。全部残すと新システムでも同じ混乱が再発する | products.sku生成関数の設計 |
| 「SKU」フィールド（商品コードA＋商品コードB）は、**現在の運用で本当に一意な商品識別子として機能しているか**。商品コードAは誰が・いつ・どんなルールで入力しているか。 | 一意キーとして採用できるかの判断材料。もし手入力に抜け漏れがあれば、新システムでは自動採番に変える必要がある | products.sku の設計方針 |
| 「商品タイトル」に使われる8要素（取引先・品種・荷姿・等級・階級・量目・玉数房数・入数）の**組み合わせルールに例外はあるか**（例：ある品種では階級を使わない、等）。 | 表示名生成関数が全商品で同じロジックで良いか、例外分岐が必要か | 生成関数のロジック設計 |
| 既存の商品コード・SKU表記は、**[[10 開発中システム - EC Channel Console\|EC Channel Console]]など他システムとの間で参照・突合されているか**。 | 表記を変えると他システムとの整合性が壊れるリスクがあるため | 移行時の互換性要件 |
| 販売規格・月統計・年統計の3テーブルは、**現在も定期的に見ている人がいるか**、それとも参照されなくなっているか。 | 単純なSQLクエリに置き換えて問題ないか、それとも特別な閲覧用画面が必要か | TO-BEの販売規格/統計の実装要否 |
| 【7】品種テーブルが45フィールドと、マスタにしては多い。**品種テーブルの中に何が入っているか**（年別数量など、商品マスタや取引内容一覧と同様の集計が同居していないか）。 | 品種マスタも同様の整理が必要かもしれないため | マスタテーブルの設計範囲 |
| ☑顧客リスト（正しいテーブル）の実際のレコード件数・最終更新日はいつか。 | 前回「取引先」と混同していたため、販売系の実データ量を正しく把握し直す必要がある | 移行データ量の再確認 |
