#### 1. 現行の紙・ホワイトボード表から分かったこと

##### 1.1 表の基本構造（共通ルール）

3枚とも同じ構造です。まずこのルールを押さえたうえで、各表を見ていきます。

- **行＝担当者名、列＝日付（曜日つき）**の割付マトリクス
- セルの中身＝その日その人が担当する**作業内容（工程名）**
- **斜線・矢印（↑／→）＝同じ作業が複数日にまたがって継続している**ことを示す延長記号

##### 1.5 3枚の表から見えてきた、当初イメージとのギャップ

当初「6月7日・石田さん・ケーキ10個」のような**商品×数量の指示**をイメージしていましたが、上記3枚を見る限り実際の運用は異なっていました。

| 当初のイメージ | 実際の運用（表のどこに現れているか） |
|---|---|
| 商品×数量の指示（例：ケーキ10個） | **人×日×工程**の割り当て（表1：石田／サンド、表3：渡辺／計、加藤／カット など） |
| 1人が1つの作業を1日で完結 | 同じ作業が**複数日にまたがる**（表1：山本の刃入れが29〜30日、表3：村松の焼が29〜2日） |
| 1商品＝1人が最初から最後まで担当 | 工程ごとに**担当者がリレー式に交代**（表2：New CP生チョコが石田→山本→山下） |
| 製造タスクのみ | **店舗配送タスクが同じ表に混在**（表1：遠鉄、表3：横浜） |
| 単一商品 | **1生地から複数フレーバーが派生**（表3：プレミアム5フレーバー） |

##### 1.6 セル内の主な略語（工程を表す）

- 仕＝仕込み
- 焼＝焼成
- サンド／カット＝生地・製品の成形工程
- セ＝セット（箱詰め・アソート組み）
- 補＝補充（店舗陳列補充）
- 計＝計量（配合の計量作業）
- キカイ＝機械作業（成形機・包装機など）
- 遠鉄／横浜＝店舗向け出荷対応日

#### 2. アプリ化の設計方針

##### 2.1 基本コンセプト

「商品×数量×期日」の**生産オーダー**を頂点に置きつつ、その内側に現場の実態である**人×日×工程の割り当て**をぶら下げる、二階建ての構造にします。これにより、経営側が見たい「計画と実績」と、現場が使う「日々の割り当て表」を同じデータで両立させます。

##### 2.2 データモデル（エンティティ）

| エンティティ | 役割 | 主な項目 |
|---|---|---|
| **商品マスタ（既存BOM）** | 何を作るかの定義 | 商品名、カテゴリ、レシピ |
| **生産オーダー** | 商品×数量×期日の計画本体 | 対象商品、目標数量、目標完了日、ステータス |
| **オーダー工程** | オーダーを分解した作業ステップ | 工程種別（仕込み／焼成／カット／セット／出荷）、担当者、計画開始日、計画終了日、ステータス、出荷先店舗（任意） |
| **実績ログ** | 工程完了時に記録される実績 | 実施日、実施者、実際数量、実際作業時間 |
| **スタッフ** | 担当者マスタ | 氏名、役割 |
| **店舗** | 出荷先（既存店舗マスタ） | 店舗名 |

**設計のポイント**

- 多日またぎの工程（例：刃入れが2日続く）は「計画開始日〜計画終了日」の期間で表現する
- リレー式の受け渡し（例：生チョコが石田→山本→山下）は、同一オーダー内で工程レコードを複数に分け、それぞれに異なる担当者を割り当てることで自然に表現する
- 店舗配送（遠鉄・横浜など）は「出荷」という工程種別の一種として同じテーブルで扱う
- 派生値（予実差異、稼働時間集計など）はDBに保存せず、既存方針どおりSupabase RPCで都度計算する

##### 2.3 予実の見方

| 観点 | 計画側 | 実績側 |
|---|---|---|
| 数量 | 生産オーダーの目標数量 | 実績ログの実際数量の合計 |
| 納期 | 生産オーダーの目標完了日 | 最終工程の実際完了日 |
| 稼働 | 工程の計画開始〜終了（計画工数） | 実績ログの実際作業時間 |

稼働の予実データは、そのままフェーズ④（貢献利益ダッシュボード）で必要な「商品ごとの本当の人件費」の情報源になります。

##### 2.4 画面イメージ

1. **オーダー起票画面**：商品・目標数量・目標完了日を入力し、商品カテゴリに応じた工程テンプレート（仕込み→焼成→カット→セット→出荷）を自動提案。プレミアムのような派生商品群はアソート／親子関係として一括起票できるようにする
2. **週間割り当てボード**：現状の紙表を踏襲した「担当者×日付」のグリッド表示。セルは工程レコードに紐づき、ステータスに応じて色分け（🟢完了／🟡仕込み中／🔴資材待ち、既存提案書のフェーズ②配色と統一）
3. **現場用タブレット画面**：本日の担当工程一覧を表示し、タップで「開始→完了」に更新。完了タップ時に実際数量・作業時間を入力（最小フリクション）
4. **予実ダッシュボード**：オーダー単位で計画数量／実績数量、計画納期／実績納期、計画工数／実績工数を並べて比較表示

#### 3. 店舗在庫可視化の課題との関係

担当者から共有いただいた「店舗在庫の可視化による製造判断の適正化」は、新しい課題ではなく、既存ロードマップの**フェーズ③「在庫の見える化」**に該当する内容の裏付けです。

現状、生産オーダーの目標数量は「発注データと経験」に基づいて人が判断していますが、フェーズ③で店舗在庫が可視化されれば、**在庫水準から生産数量を提案する**という連携が将来的に可能になります。

今回のフェーズ①②スコープでは、目標数量は手入力とし、「何を根拠にした数字か（発注ベース／経験ベース等）」のメモ欄を持たせておくことで、後からフェーズ③と接続しやすい設計にしておくことを推奨します。

#### 4. 次に詰めるべき論点

- 「詰め放題」など不定形パッケージ商品の工程・数量の扱い
- プレミアム5フレーバーのような派生商品群のオーダー起票UI
- 工程テンプレート（商品カテゴリ別の標準工程フロー）の初期定義
- 店舗配送タスクと既存のインフォマート代替モジュール（受発注）との連携要否
- 現場担当者の役割・権限設計（更新できる人／閲覧のみの人）
