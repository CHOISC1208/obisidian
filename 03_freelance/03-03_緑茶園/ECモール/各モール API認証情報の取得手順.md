# 各モールAPI認証情報の取得手順

親: [[00 MOC|緑茶園グループ MOC]]

> [!info] 位置づけ
> [[platform - 00 概要|統合コンソール（ryokuchaen-platform）]] の受注取得機能へ接続するために、各モールの管理画面から取得してもらう認証情報の一覧。**この資料はそのまま先方の担当者に渡す配布用ドキュメント**（旧版の原本：`認証情報取得手順_EC_Channel_Console.pdf`。2026-09-16 改訂版は未PDF化）。
>
> **このノートが唯一の正本**。旧ツール（EC Channel Console）時代に対になっていた開発者向け `docs/credentials.md` は、リポジトリのアーカイブに伴い存在しない。ツール側の項目名・必須／任意は `ryokuchaen-platform` の `lib/ec/registry.ts` と一致させること。
> **API の仕様や実装上の注意（署名方式・エラーコード・PIIの細則・ポーリング設計など）はこの資料に書かない。** 開発者向けの内容は `ECモール/` の各リファレンスが正本：[[Amazon - SP-API 受注リファレンス]] ／ [[Temu - Open Platform 受注リファレンス]] ／ [[LINEギフト - API 受注リファレンス]]

> [!warning] ご確認ください
> 先方から預かったクロスモールのAPIキーは、楽天市場の受注データ取得には使用できない。クロスモールAPIは「出荷待ちフェーズの受注を出荷システムへ連携する」ための別の仕組みで、楽天RMSの受注APIとは認証情報・データ形式が異なる。楽天のデータを取得するには、下記「楽天市場」の手順で楽天RMS側の `serviceSecret` / `licenseKey` を別途用意してもらう必要がある。

## 先に把握しておくべきこと

チャネルごとに、事前申請の要否・リードタイム・認証情報の有効期限が異なる。**Yahoo!ショッピング（1〜2週間）とTEMU（目安1〜4週間）は申請から承認までに時間がかかる**ため、最初に着手するのがよい。

| チャネル | 事前申請 | リードタイム | 認証情報の有効期限 | 特記事項 |
|---|---|---|---|---|
| 楽天市場 | 必要（WEB API利用申請） | 即日〜 | licenseKeyは3ヶ月 | 期限前にメール通知あり |
| Amazon | 必要（開発者登録） | 審査あり | refresh tokenは長期有効 | 自己認可でトークン発行。**顧客の氏名・住所が必要なら追加ロールの審査が要る**（FBA注文は審査を通しても取れない） |
| Yahoo!ショッピング | 必要（API利用申請） | 1〜2週間 | 12時間／公開鍵認証で28日 | 下記の注意点を必読 |
| au PAYマーケット | 必要（API利用申請＋IP登録） | 即日〜 | APIキーは90日 | **接続元IPの登録が必要**（中継サーバのIPを登録。下記参照） |
| TEMU | 必要（Partner Platform登録＋審査） | 目安1〜4週間（公式の記載なし） | アクセストークンに期限あり（管理画面に表示） | **全托管の店舗は対象外**。本土店／半托管のみ。**受注取得は未実装** |
| Shopify | 不要（自分で作成） | 即時 | 失効なし | トークンは1度しか表示されない |
| LINEギフト | 不要（自分でアプリ登録） | 即時 | アクセストークンは自動更新。**認証情報画面に表示される有効期限を過ぎたら管理画面で再認証** | **受注取得は未実装**。認証情報だけ先に取得できる |

## 特に注意すべき3点

### 1. Yahoo!ショッピングは公開鍵認証をしないと12時間ごとに再認可が必要

Yahoo! JAPAN IDによる再認可までの期間が既定で12時間のため、そのままでは実運用に耐えない。ストアクリエイターProの「設定 > 暗号鍵管理」から公開鍵を申請すると28日に延長できる。運用に載せるなら公開鍵認証の設定はほぼ必須（公開鍵の有効期限は発行から1年、同時に使えるのは最大2つ）。

### 2. au PAYマーケットは接続元IPアドレスの登録が必要

Wow!managerに登録した**送信元グローバルIPアドレスからのリクエストしか通らない**。IP制限があるのは、現在取得に対応しているチャネルでは au PAYマーケットだけ。

統合コンソールはクラウド（Vercel）上で動いており、送信元IPが固定されない。そのため **au PAYマーケットへの通信だけ、固定IPを持つ中継サーバ（さくらのVPS）を経由させている**。Wow!manager に登録するのは、この中継サーバのIPアドレス（値は開発側から連絡する）。

| 動かす場所 | 登録するIP | 状態 |
|---|---|---|
| 統合コンソール（本番） | **中継サーバのIP** | 🟢 2026-09-09 登録済み・実データ取得を確認済み |
| 開発PC（ローカル実行・開発時のみ） | そのPCのグローバルIP（`curl ifconfig.me` で確認） | 回線・テザリング・VPNでIPが変わると通信できなくなり、**その都度登録し直す**運用になる |

> [!warning] IPリストを編集するときの注意
> 現在のAPIキーは**クロスモールと共用**で、IPリストにはクロスモール側のIPも並んでいる。**追記だけを行い、既存のIPを消したり上書きしたりしないこと**（クロスモールの連携が止まる）。APIキーを再発行した場合も両方に影響する。

> [!info] 参考：一元管理SaaSはどうしているか
> クロスモール（I'LL社）の初期設定資料では、店舗側に**14個のIPアドレス**（`121.83.254.*` の自社データセンター帯＋AWS東京の `13.112.7.206` など）を登録させている。ロジレスも同様に4個を公開している。「クラウドサービスだから送信元IPは動的」ではなく、**この種のAPIに繋ぐために各社が固定IPを確保している**というのが実態。

### 3. TEMUは店舗の「販売モデル」でAPIの利用可否そのものが決まる

TEMUには3つの販売モデル（全托管 / 半托管 / 本土店）があり、**全托管（フルマネージド）の店舗は出荷業務をTEMU側が担うため、受注管理APIの対象外**。認証情報を取得しても取り込むべき受注データが存在しない。確認方法は下記「TEMU」の冒頭を参照。**審査に時間がかかるため、申請より先に店舗タイプを確認すること。**

## 楽天市場

**必要な項目**：`RAKUTEN_SERVICE_SECRET` ／ `RAKUTEN_LICENSE_KEY`

**手順**
1. RMSにログイン
2. RMS WEB SERVICEを開く
3. 左メニューの「アプリ一覧」
4. 「WEB APIアクセス許可設定」→ アプリ登録者「店舗様」→「詳細」
5. セキュリティチェックを通過すると「利用情報」セクションに serviceSecret と licenseKey が表示される

**更新**
licenseKeyは発行から3ヶ月で失効する。期限が近づくとRMS登録のメールアドレスへ通知が届く。更新はRMS上で「ライセンスキーの変更」→「新しいライセンスキーを発行」。失効するとツール側は「認証エラー」として表示される。差し替えは設定画面の楽天欄に新しいlicenseKeyだけを入力して保存すればよい（空欄の項目は変更されない）。定期的な差し替え作業が発生することを運用フローに織り込む。

**補足**
受注データの取得には楽天ペイ受注API（RakutenPayOrderAPI）の利用設定が必要。WEB APIの利用申請とは別枠になっている可能性があるため、「アプリ一覧」で `searchOrder` / `getOrder` が利用可能になっているか要確認。

## Amazon

**必要な項目**：`AMAZON_LWA_APP_ID` ／ `AMAZON_LWA_CLIENT_SECRET` ／ `AMAZON_REFRESH_TOKEN` ／ `AMAZON_SELLER_ID`

**手順**
1. セラーセントラルにログイン
2. 「アプリとサービス」→「アプリを開発」（初回は開発者登録が必要。審査があるため時間を見込む）
3. アプリを新規作成する。ロールは **`Inventory and Order Tracking`（在庫と注文の追跡）** を含める（注文の取得にはこれがあれば足りる）
4. **顧客氏名・配送先住所まで取得したい場合のみ**、追加で `Direct to Consumer Delivery (Restricted)` ロールも申請する。データ保護に関する追加審査がある。取得したいかどうかは開発側と相談してから決める（下記「顧客の氏名・住所について」）
5. 作成したアプリの「LWA認証情報を表示」から client_id → `AMAZON_LWA_APP_ID`、client_secret → `AMAZON_LWA_CLIENT_SECRET` を取得
6. 同じアプリ一覧から「認可」→「アプリを認可」→「リフレッシュトークンを生成」。表示された値 → `AMAZON_REFRESH_TOKEN`（自己認可という手順で、自社アカウント向けの近道）
7. 出品者ID（Seller ID）はセラーセントラルの「設定 > アカウント情報 > 出品者トークン」付近で確認 → `AMAZON_SELLER_ID`（ツールの設定画面では必須入力）

日本のマーケットプレイスであれば `AMAZON_MARKETPLACE_ID`／`AMAZON_REGION` は未入力でよい（Amazon.co.jp・リージョン fe が既定で使われる）。

**補足**
- refresh tokenは長期有効で、アプリが自動でアクセストークン（1時間）に交換する。日常的な差し替えは不要
- 「アプリを認可」を複数回押すと都度新しいrefresh tokenが発行されるが、以前のトークンは無効化されない。どれを使っても動く

> [!warning] 顧客の氏名・住所について
> 「認証は通っているのに氏名が「(非公開)」と表示される」のは認証エラーではなく、Amazonの個人情報の取り扱い制限によるもの。
> - 氏名・住所・電話を取るには、上記手順4の **`Direct to Consumer Delivery (Restricted)` ロール**が必要。税務系のロール（Tax Invoicing / Tax Remittance）では取れない
> - **FBA（Amazon出荷）の注文は、どのロールでも氏名・住所・電話は取れない**（郵便番号のみ）。取れるのは自己配送（FBM）の注文だけ
> - 購入者のメールアドレスは実アドレスではなく、Amazonが発行する匿名化アドレス
> - **現在のツールは氏名・住所を取得していない**。ロールが承認されても、ツール側の対応が別途必要
>
> 詳細 → [[Amazon - SP-API 受注リファレンス]]

## Yahoo!ショッピング

**必要な項目**：`YAHOO_CLIENT_ID` ／ `YAHOO_CLIENT_SECRET` ／ `YAHOO_REFRESH_TOKEN` ／ `YAHOO_SELLER_ID`

> もっとも手数が多いチャネル。承認に1〜2週間かかるので、先に着手することをおすすめする。

**手順**
1. Yahoo!デベロッパーネットワークのアプリケーション管理でアプリケーションを登録（アプリケーションID→`YAHOO_CLIENT_ID`、シークレット→`YAHOO_CLIENT_SECRET`）。サーバーサイド用途として登録し、コールバックURLを設定する
2. ショッピングAPI利用申請フォームから、ストア運営API（注文API）の利用を申請（承認まで約1〜2週間）
3. Yahoo! ID連携（v2）の認可コードフローでリフレッシュトークンを取得：①ブラウザで認可エンドポイントにアクセスし、ストア管理権限を持つYahoo! JAPAN IDで認可 ②コールバックURLに付与される認可コードを受け取る ③トークンエンドポイントへ認可コードを送り、返ってきた refresh_token → `YAHOO_REFRESH_TOKEN`（**この初回の認可だけはブラウザ操作が必要で、ツール画面からは実行できない**）
4. ストアアカウント（SellerId）はストアクリエイターProで確認 → `YAHOO_SELLER_ID`

**有効期限（重要）**
公開鍵認証を設定しないと12時間で再認可が必要。ストアクリエイターProの「設定 > 暗号鍵管理」から公開鍵を申請する（申請後すぐ発行）。

**補足**
- テスト環境（`test.circus.shopping.yahooapis.jp`）が用意されている。設定画面の「テスト環境を使う」に1を入れるとそちらを呼ぶ。本番の受注データに触れずに疎通確認したい場合に使える
- APIリクエストはClient IDあたり1日5万件まで

## au PAYマーケット

**必要な項目**：`AU_API_KEY` ／ `AU_MEMBER_ID`（中継サーバ関連の項目は開発側で設定する）

**手順**
1. Wow!managerにログイン
2. 左メニューの「各種お申し込み > API利用申請」
3. APIキー利用規約に同意し、「APIキーの発行はこちら」→「キー発行」。発行された値 → `AU_API_KEY`（発行済みのキーも同じ画面で確認できる）
4. 同じ画面の「2. 接続元IPアドレスを登録」で接続元IPを登録する。**登録する値と注意点は上記「特に注意すべき3点」の2を参照**（本番分は登録済み）
5. 店舗会員番号 → `AU_MEMBER_ID`
   - Wow!manager の **「店舗構築 > 店舗情報 > 登録情報」** で確認できる（確実な経路）
   - au PAYマーケット管理画面の左上にも表示されている

**エラーコードの読み分け**（2026-09-07 実機で確認）

APIが返すXMLの `error/code` で原因を切り分けられる。

| コード | HTTP | 意味 | 疑うところ |
|---|---|---|---|
| `0001` | 400 | リクエスト情報が不正 | `Authorization` ヘッダーが欠けている |
| `0002` | 401 | 認証に失敗 | **APIキーの誤り／期限切れ、または接続元IPの未登録**。この2つは応答が完全に同一で区別できない |
| `CME0022` | — | 会員番号（shopId）の誤り | `AU_MEMBER_ID` |

> [!tip] `0002` では会員番号の正誤は分からない
> 認証は shopId より先に評価されるため、存在しない会員番号を送っても `0002` が返る。会員番号は上記の管理画面で目視確認するしかない。

**更新**
APIキーは発行日から90日で失効する。期限の10日前に、Wow!manager登録の基本メールアドレスへ通知が届く。**全チャネルの中でもっとも更新頻度が高い**ため、運用担当者を決めておくことをおすすめする。**クロスモールと共用のキーなので、再発行したらクロスモール側の設定も差し替える必要がある。**

**補足**
au PAYマーケットのAPI仕様書は一般公開されておらず、利用申請時に配布される（2026-09-09 に先方から入手済み）。

## TEMU

**必要な項目**：`TEMU_APP_KEY` ／ `TEMU_APP_SECRET` ／ `TEMU_ACCESS_TOKEN`

> [!note] 受注取得はまだ実装していない
> ツール側の実装は、店舗タイプの確認とアプリ審査の通過を待って着手する。審査に時間がかかるため、店舗タイプの確認とフェーズ1の申請を先に進めてほしい。

> [!warning] 先に販売モデル（店舗タイプ）を確認
> **全托管の店舗は出荷業務をTEMU側が担い、出品者側に受注業務が発生しないため、受注管理APIの対象外**。認証情報を取得しても取り込むデータが存在しない。
>
> 1. **セラーセンターのURLを見る**
>    - `seller.temu.com` → **本土店**（自社発送。対象）
>    - `agentseller.temu.com` → 越境店。2 へ
> 2. **越境店の場合**：「アカウント管理 > 主体管理」の店舗タイプ欄に「半托管」と表示されていれば**半托管**（対象）。表示されていなければ**全托管**（対象外）
>
> ※画面名・メニュー名は第三者資料に基づく。管理画面の言語設定や更新で表記が異なる可能性がある。

**手順（2段構え：アプリ審査 → 店舗認可）**

TEMUのAPI利用は「アプリ開発者としてTEMUのPartner Platformに登録する」フェーズと「出品者がそのアプリを認可する」フェーズの2段構え。開発者と店舗のオーナーが同じでも、両方の手続きが必要。

**フェーズ1：Partner Platformでアプリ登録（開発者側／1回だけ）**

1. Partner Platformに登録
   - GLOBAL: `https://partner.temu.com/`
   - 米国向け: `https://partner-us.temu.com/`
   - EU向け: `https://partner-eu.temu.com/`
   - **日本の店舗がどれに登録すべきかは未確認**（開発側で確認する）
2. Partner Profileを作成
3. アプリを新規作成（種別は「Self-developed（自社開発）」を選択）
4. **コンプライアンス／セキュリティ質問票に回答し、審査を受ける**（リードタイム目安：1〜4週間。公式の記載なし）
5. 審査通過後、アプリの `app_key` と `app_secret` を取得 → `TEMU_APP_KEY` ／ `TEMU_APP_SECRET`

**フェーズ2：出品者による店舗認可（店舗側）**

1. TEMUセラーセンターにログインし、認可管理の画面を開く
   - 本土店：`https://seller.temu.com/open-platform/client-manage`
   - 越境半托管：`https://agentseller.temu.com/main/system-manage/client-manage`
2. 認可を取得するボタンをクリック（中国語表記の画面では「授权管理」「获取授权」）
3. 認可対象のアプリを選ぶ（自社開発のアプリはリストに現れる）
4. **必要な権限（スコープ）にチェック**：
   - 注文管理（自社開発アプリの場合は `Order Management`。`Semi Order Management` は公開アプリ向けのパッケージ）
   - **配送先住所**（住所の取得は注文とは別の権限。**後から追加すると認可のやり直しとトークンの再発行が必要**なので、最初から付けておく）
   - 物流・出荷（追跡番号をTEMUへ登録する場合）
   - 商品・在庫（在庫連動を行う場合）
5. 認可完了後に発行される `access_token` を取得 → `TEMU_ACCESS_TOKEN`

**更新**
`access_token` には有効期限がある（認可一覧の画面に表示される）。期限が切れる前に、フェーズ2の手順で再認可してトークンを差し替える。運用担当者を決めておくことをおすすめする。

**補足**
- **配送先住所の保存には制約がある**：TEMUのデータセキュリティポリシーにより、住所を長期間保存するとデータレビューで不適合になる可能性がある。ツール側の保存方針は開発側で決める
- TEMUは**出荷後24時間以内の追跡番号登録**を運用基準としている（第三者資料）。遅れると遅延出荷として評価に影響する
- API仕様・エラーコード・取得できる項目の詳細 → [[Temu - Open Platform 受注リファレンス]]

## Shopify

**必要な項目**：`SHOPIFY_SHOP_DOMAIN` ／ `SHOPIFY_ADMIN_ACCESS_TOKEN`

> チャネル群の中でもっとも簡単。申請も審査もなく、自分で作成できる。

**手順**
1. Shopify管理画面 > 設定 > アプリと販売チャネル
2. 「アプリ開発」→「アプリを許可する」（初回のみ）
3. 「アプリを作成」で任意の名前をつける
4. 「設定」タブ →「Admin APIの統合」→「Admin APIスコープを設定する」で `read_orders` にチェック（60日より古い注文まで遡る必要があれば `read_all_orders` も。こちらはShopifyへの申請が必要な場合がある）
5. 「APIの認証情報」タブ →「アプリをインストール」
6. 表示されたAdmin APIアクセストークン（`shpat_...`）→ `SHOPIFY_ADMIN_ACCESS_TOKEN` **※このトークンは一度しか表示されない。その場で控える。取り逃した場合はアンインストール→再インストールで再発行**
7. ショップドメイン（`example.myshopify.com`）→ `SHOPIFY_SHOP_DOMAIN`。管理画面のURLか「設定 > ドメイン」で確認できる

**補足**
- アクセストークンに失効はない。スコープを変更した場合のみ再インストールが必要
- 顧客名は保護対象顧客データの承認状況によっては取得できない（その場合は「(非公開)」と表示）

## LINEギフト

**必要な項目**：`LINEGIFT_CLIENT_ID` ／ `LINEGIFT_CLIENT_SECRET` ／ `LINEGIFT_REFRESH_TOKEN`

> [!note] 受注取得はまだ実装していない
> 出店者向けAPIの仕様書が一般公開されておらず、エンドポイントが分からないため、ツール側の実装は保留中。**仕様書が手に入れば実装できる**ので、認証情報だけ先に取得しておいて構わない。
> 公式FAQでは「API連携は可能だが、システムサポートは行っていない」とされており、LINEギフトに問い合わせても仕様書は出てこない可能性が高い。**ショップ管理画面のアプリ機能まわりのヘルプや、出店時に受け取った案内資料にAPIの説明がないか探して、あれば共有してほしい。**

**前提（スタッフ権限）**

ショップCMS の「ショップ > スタッフ一覧」で、いまログインしているIDの権限が次のようになっている必要がある。なっていなければ権限を変えるか、権限を持つアカウントでログインし直す。

- 受注：「閲覧・変更可」を推奨（「閲覧可」でも登録はできるが、追跡番号をLINEギフトへ登録する機能を使う場合は変更権限が必要と考えられる）
- 商品：「閲覧・変更可」

**手順**
1. ショップCMS（LINEギフトの管理画面）にログイン
2. 「アプリ > 新規登録」
3. アプリ名（任意。例：`緑茶園 統合コンソール`）、アプリケーションタイプ「Webアプリケーション」、Redirect URI を入力し、「LINEギフト・LINEショッピング出店者向けAPI利用規約」に同意して登録。**審査は無く即時発行**。**Redirect URI に入れる値は開発側から連絡する**
4. 「登録アプリ一覧」に移動し、表示された認証情報 → `LINEGIFT_CLIENT_ID` ／ `LINEGIFT_CLIENT_SECRET`（**この画面に表示される「有効期限」も控えておく**）
5. 1度だけ認可（Redirect URI へのリダイレクト）を通して refresh token を得る → `LINEGIFT_REFRESH_TOKEN`。**この手順は開発側と一緒に行う**（現時点ではツール側に認可の受け口が無く、単独では実行できない）

**更新**

アクセストークン（短命）は refresh token から自動で再取得されるため、通常運用で手動更新は発生しない。ただし認証情報画面に**有効期限**が表示されており、これを過ぎると**管理画面にログインした状態でのブラウザ再認証**が必要になる（実装ベンダー各社が「再認証処理」として案内している。期限の対象が client_secret か refresh token かは未確認）。運用担当者を決めておくことをおすすめする。

**このチャネル特有の制約**（運用に関わるもの）

- **注文者（贈り主）の氏名・住所・電話・メールはAPIから取得できない**：ソーシャルギフトの仕様上の制約。取れるのは配送先（受取人）の情報だけ。受注伝票の「注文者」欄を「送付先と同じにする」か「店舗情報を入れる」かを決めておく必要がある
- **注文者へのメール送信はできない**：追跡番号を登録すると、LINEギフトから受取人へ発送のお知らせが届く。**お荷物番号などの発送情報を注文者（贈り主）に伝えることは禁止**されている（通知先は受取人のみ）
- **仮注文がある**：贈り主が購入した時点では受取人の住所がまだ無い。受取人がLINE上で住所を入力するまでは、氏名に「LINEギフト 仮登録」、郵便番号に `000-0000` などの仮の値が入る。**この状態の注文に送り状を発行しないこと**
- ポイント・売上金による値引きは金額に反映されない（実際の請求額は差し引かれているが、APIから返るのは差し引かれていない額）
- 受注ステータスは 購入手続き（決済待ち）→ 支払待ち → メッセージ送信待ち → 住所入力待ち → 発送待ち → 取引完了 と遷移する（取引中止がキャンセル相当）
- **配送希望日時は指定できない**（2025年4月時点でLINEギフト側に日時指定の機能がない）
- API が使えない場合の代替として、管理画面から受注CSVをダウンロードできる（文字コードは Shift_JIS）

実装上の注意（ポーリング頻度・仮注文の検証方法など）→ [[LINEギフト - API 受注リファレンス]]

## 取得できたかの確認方法

認証情報をチャネル認証情報の画面に保存したら、各チャネルのページで「受注データを取得」を押して確認する。

| 画面の表示 | 意味 | 対処 |
|---|---|---|
| 一覧が表示される | 成功 | ― |
| 認証エラー | 認証情報が誤っている／失効している | 値を再確認。楽天・au PAY は期限切れの可能性 |
| レート制限 | 呼びすぎ | 少し待ってから再実行 |
| APIエラー | 権限不足、申請未完了など | 詳細を開いてエラー内容を確認 |
| 「チャネル認証情報から先に登録してください」 | 必須項目が未入力 | チャネル認証情報の画面で不足項目を入力 |
| 「このチャネルは未実装です」 | TEMU・LINEギフトはまだ取得できない | 認証情報の登録だけ済ませておけばよい |
| 氏名が「(非公開)」になる | 認証は成功している。個人情報の取得制限 | Amazon：上記「顧客の氏名・住所について」を参照 |
