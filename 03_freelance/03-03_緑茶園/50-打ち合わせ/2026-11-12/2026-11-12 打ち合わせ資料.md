## 2｜前回お願いしたことの進捗

### 2-1．仕入入力：KRK は請求書を取り込む、それ以外は入荷入力で対応する

前回の方向性：**KRK は請求書（Excel）をアップロード**して、**ほかの取引先は入荷入力**で入れる。この分け方で運用できそうか。

| 確認すること | 先方の回答（当日記入） |
|---|---|
| この分け方で運用に乗りそうか。困りそうな点はあるか | |
| KRK の請求書は、いつ・誰が取り込んでいるか。取り込めずに困ったファイルはあるか（6月分のファイルは前回から宿題） | |
| 「照合」タブ（集荷日ごとの合計数 vs 手で数えた合計数）は使えるか。**数えた合計数は、どこにある数字を使うか** | |
| 照合は入力を残さない作り（このブラウザに控えるだけ）。**照合の結果を残したいか**（誰がいつ OK にしたか） | |
| KRK 以外の入荷入力の使い心地（前回の並び順・表表示・規格マスタの並び替え）。**規格マスタの並び順の初期化**（単位ごと・数の昇順に整える）は押したか | |
| 単価：KRK は請求書の単価を取引データに入れるか。入れるなら**自動か、人の確認後か**（前回の宿題。「突合」をやめたため、仕様を決め直す） | |

> [!info] 前回からの変更点の確認
> 前回は「請求書と入荷データの突合」を試作したが、**入荷データを KRK 分も入れる運用をやめる**なら突合は不要、という整理で「照合」に置き換えた。**この理解でよいか**を最初に確認する。

## 3｜受注の一元化：クロスモールで集め、easyECS のような画面で操作できるか

**先方のご相談（11/11 チャット）**：easyECS は今後多くのモールの取り込みに対応できない。画面の使いやすさは重宝している。クロスモールは様々なモール（Shopify なども）に対応し、受注 API で連携できる。**クロスモールで受注を集約し、easyECS のような管理画面で、クロスモールの受注データを動かす**ことはできるか。

欲しい機能（easyECS で行っていること）

| # | 機能 | こちらの見立て（暫定） |
|---|---|---|
| ① | 注文内容の確認 | 受注データを取れれば**画面は作れる見込み**。取れる項目（クロスモールの受注 API・CSV）の確認が先 |
| ② | 決済の確認 | 決済情報が**クロスモールの受注データに含まれるか**が決め手。NP 後払い・各モール決済の扱いも要確認 |
| ③ | メール送信・送信履歴 | **いちばん難しい**（遠藤様も同じ見立て）。モールごとに送り方が違う。楽天は RMS の外から返信を自動で送りにくい。まずは「**文面と宛先の一覧を出す**」形が現実的 |
| ④ | 送り状データを各モールへ送信 | 配送業者の**送り状番号を各モールの出荷通知 API へ返す**処理。クロスモールが担うのか、こちらがモール API を直接呼ぶのかで作りが変わる。モールごとに API の有無を確認 |

### 3-1．話をそろえたいこと（現状の整理）

- クロスモールは、現在は**在庫連動・商品ページ作成**で稼働。**受注連携の機能は使っていない**（棚卸の読み取り）。契約に受注連携が含まれるか未確認（[[クロスモール（I'LL社）]]）
- クロスモールの受注取得の方式はモールごとに違う：楽天・Yahoo・au PAY・LINEギフトは API、**Shopify は注文確認メールの取り込み**、**Amazon は注文レポートの定期ダウンロード**。「API で連携できる」はモールによって当てはまらない
- 現在の統合コンソールは、**easyECS を前提に**作っている（受注残ボード・売上の履歴・MDC 形式 CSV の出力）。置き換えるなら、この3つの**作り替えが要る**
- 前提が動いている：2026年1月の要件書（店舗アップ♪）で easyECS の置き換えは検討されていた。**easyECS＋クロスモールは残す**という棚卸の判断は、見直し対象（[[06 触らない領域]]）

### 3-2．先方に決めてもらうこと／聞くこと

| 確認すること | 先方の回答（当日記入） |
|---|---|
| **目的**：easyECS を**やめたい**のか、**取り込めないモール（Shopify・Temu・LINEギフトなど）を足したい**のか | |
| 取り込めないモールの**注文件数**（月あたり）と、手作業にかかっている時間 | |
| **決済の確認**は、具体的に何を見ているか（入金の有無・決済方法・NP 後払いの与信など） | |
| **メール**は、何通を何のために送っているか（受注確認・発送連絡・お詫びなど）。**テンプレート**か個別か | |
| **送り状データ**：どの配送業者の何のシステムで作っているか。モールへの返し方は今どうしているか | |
| クロスモールの**契約に受注連携は含まれるか**／追加費用はあるか／API・CSV 出力はあるか（先方からベンダーに確認できるか） | |
| クロスモール側で**受注を取り込む設定を試してよいか**（Shopify のメール取り込みは専用メールアカウントが必要。Amazon は今の注文レポートの運用が変わる） | |
| easyECS は**いつまで契約**しているか。切り替えの期限 | |

### 3-3．進め方の案（当日に叩く）

| 案 | 内容 | 見立て |
|---|---|---|
| A．いまのまま | easyECS のまま。取り込めないモールは **MDC 形式 CSV で easyECS に入れる**（Shopify は実装済み・実運用はこれから） | 追加の開発が小さい。モールが増えるたびに変換が要る |
| B．クロスモールから受注を取って、統合コンソールで操作 | クロスモールの受注データを統合コンソールに取り込み、①②の画面を作る。③は一覧出力から、④はモール API を直接呼ぶ | 先方の希望に近い。**API・CSV の確認が先**。easyECS 前提の機能は作り替え |
| C．B のうち、まず「見る」だけ | ①注文内容と②決済の**確認画面だけ**を作り、メール・送り状は今のまま（easyECS またはモール管理画面） | 一番小さく始められる。**難所（③④）を後ろに回せる** |

> [!tip] 当日の落としどころ（案）
> 結論を急がず、**①クロスモールに受注データを出せるか（API・CSV・費用）を先方がベンダーに確認する**、②こちらは**C案で必要な画面のイメージ**を作って次回見せる、の2点を持ち帰る。
