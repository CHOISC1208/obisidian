## 1｜仕入入力

### 先に伝えること

- 10/28 の「突合」は**やめた**。KRK の入荷データを入れない運用なら突合は不要、という整理で、**「照合」タブ**に置き換えた
  - 照合 ＝ 請求書の**集荷日ごとの合計数**と、**人が数えた合計数**を見比べる（合えば OK、違えば NG）。**何も書き換えない**
  - 入力は残らない（このブラウザに控えるだけ）
- KRK は**請求書（Excel）を取り込む**、KRK 以外は**入荷入力**で入れる。この分け方で進めたい
- 「この理解でよいか」を**最初に**確認する

### 聞くこと（優先順）

| # | 聞くこと | 先方の回答 |
|---|---|---|
| 1 | この分け方で運用に乗りそうか／困りそうな点 | |

| 3 | **単価**：KRK は請求書の単価を取引データに入れるか。入れるなら**自動か、人が確認してからか** | |
| 4 | 照合の結果（誰がいつ OK にしたか）を**残したいか** | |
| 5 | 請求書の取り込み：いつ・誰が。**6月分のファイル**はあるか（前回からの宿題） | |

### 決めたいこと

- [ ] **単価の仕様**（#3）。ここが決まらないと、単価反映の着手ができない
- [ ] 照合の結果を残すか（#4）。残すなら画面と DB の追加になるので**別見積もり**の範囲
- [ ] 規格マスタの初期化を、**誰がいつ押すか**（まだなら当日一緒に押す）

### こちらの見立て（先方に聞かれたとき用）

- 単価は**人が確認してから反映**が安全。請求書は税抜・取引は税込で換算と端数の判断が要る。請求書は文字列で、商品マスタと直接つながっていない（[[水田様 問い合わせ（入荷入力・取引CSV・KRK請求書・商品登録）]] 3・4）
- 請求書の単価を取引データに入れる機能は**機能追加**にあたり、運用費の範囲外として別途見積もり（10/14 の線引き）
- 突合をやめても、10/28 に出た**数量ずれ・入力漏れ**（8/18 の二重入力の疑い、8/5 あかつき）は、**入荷データ側の問題として残る**。KRK 分を入荷に入れない運用なら、そもそも発生しなくなる

## 2｜CS問い合わせ

### 先に伝えること

- 前回の「**蓄積して検索する**」から、**注文番号 → 注文・出荷予定を自動で引く → AI に渡す文面（プロンプト）を作る → AI の回答と最終回答を記録する**形に作り直した
- 複数回のやり取りは**1件にまとめられる**（丸と縦線でつなぎ、丸を押すと折りたためる）
- **廃止したもの**：楽天 RMS の画面をコピーして貼る登録・過去 213 件の取り込み。**「消えた」と見えたら、この説明をする**（事前確認で 213 件の扱いを確かめておく）
- AI に渡す文面は、マスタ「**CSプロンプト**」で直せる。**誰が直すか**を決めたい

### まずやること：1件、一緒に通す

> [!todo] デモ手順（実際の問い合わせ1件で）
> 1. 注文番号を入れる → 注文と出荷予定が出る
> 2. プロンプトを生成する
> 3. AI の回答を貼る → 先方が直して**最終回答**を記録する
> 4. 注文が出ない／情報がずれる例があれば、そこで拾う
>
> 使われていなければ、**その場で触ってもらう時間を取る**のが最優先（聞くより見るほうが早い）。

- [ ] **AI に渡してよいものの線引き**（#3）。ここが決まれば、返信文案の下書きを進められる

### こちらの見立て（先方に聞かれたとき用）

- 遅延している注文と発送予定日を**特定する**ところは作れる。該当のお客様への**一括メールは、楽天が RMS の外から返信を自動で送りにくい**ため、まずは「文面と宛先の一覧を出す」形が現実的
- 納期ずらし（easyECS の書き換え）は、先方の意向どおり対象外
- ベクトル検索（AI の検索）は、今の量ではキーワード検索で足りる。**探しても出てこない**が出てから決める

### 登録されている2件（AI の回答 → 最終回答の差分）

> [!info] デモの題材にできる
> すでに2件が登録済み。**「AI の案をどう直したか」から、先方の対応基準が読める**。当日は先方に「この直し方は、いつもの基準か」を聞き、プロンプト（マスタ「CSプロンプト」）に反映するかを決める。全文は画面で見られるので、ここには差分だけ書く。

| 項目 | 注文 258324-20261006-0628409381（発送の確認・友人宛て） | 注文 258324-20261005-0332409086（発送時期の苦情） |
|---|---|---|
| 内容 | ご友人宛ての分が未着。自宅分は届いた。注文は未出荷で、出荷予定 11/13・お届け 11/14 | 「12時までの注文は当日発送」と書いてあるのに発送されない。実は**予約商品**で、発送は 11/20 予定 |
| AI が書いたこと | 注文・出荷予定を正しく引いて案内。「お届け 11/14 **午前中**」と書いた | 予約商品は当日発送の対象外、11/20 発送予定と説明。冒頭で「分かりづらい案内で申し訳ない」と謝った |
| 人が直したこと | ①「**午前中**」を削除　②「収穫状況で**数日遅れる場合がある**」を追加　③「ご不明な点は何なりと」を追加　④署名を「カスタマーサポート」→「**遠藤**」 | ①冒頭の**お詫びを削除**　②**10/5 の注文確認メールにも発送予定を書いている**と案内　③「ご案内は**メールで送っている**ので今後も確認を」と追加　④発送後はメールで改めて案内、と書き直し |
| 読み取れる基準 | 画面にない情報（時間帯）は書かない／**遅れの可能性は必ず添える**／署名は担当者名 | 店に非がないときは**お詫びを重ねない**／**注文確認メールで案内済み**であることを伝える／連絡手段はメールだと念押し |

**この2件から先方に確認したいこと**

| 確認すること | 先方の回答 |
|---|---|
| 上の「読み取れる基準」は、いつもの対応基準か。ほかに必ず守ることはあるか | |
| 「午前中」は、AI が**どこから書いたか**わかるか（受注データにあったか）。**データにない情報は書かない**とプロンプトに入れてよいか | |
| 「数日遅れる場合がある」の一文は、**生鮮品の問い合わせには毎回入れる**ものか（プロンプトの固定文にしてよいか） |  |
| 「10/5 の注文確認メールで案内済み」は、**注文日と確認メールの有無をデータから引ける**と便利か（今は人が書いている） | |
| 署名：AI は「カスタマーサポート」と書く。**担当者名は人が入れる**運用でよいか | |
| 「本日」「明日」と書くと、**送るのが翌日になったときにずれる**。日付で書く運用にするか | |

> [!tip] 気づいた点（こちらの課題）
> - 2件目の「予約商品なので当日発送の対象外」は、**注文のデータから AI が判断できた**のか、人が補ったのか。注文・出荷予定から**予約商品かどうか**を引けるなら、プロンプトに渡す項目に足す価値がある
> - 1件目は「ご友人宛て」の注文かを**確認中**と書いて返している。**複数の注文が候補に出る場合**の扱いも、当日聞く
