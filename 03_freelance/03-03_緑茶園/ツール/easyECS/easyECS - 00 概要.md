# easyECS（SAVAWAY）— 受注一元管理

親: [[00 MOC|緑茶園グループ MOC]] ／ 関連: [[04 ツールリファレンス]] ／ [[テーマ1 - 受注チャネル統合とツール複数人化]] ／ [[platform - 10 変換器構想とMDC出力]]

> [!info] このノートの位置づけ
> 緑茶園（山形eLab）が受注の一元管理に使っている **SAVAWAY 社の easyECS** について、**実物の DB に接続して確かめたこと**をまとめる入口。
> 2026-09-17 に Tailscale 経由で easyECS の SQL Server に読み取り専用で接続し、構造と直近の受注データの傾向を調べた。**ベンダーのテーブル定義書は未入手**なので、列の意味は実データからの推定を含む（〔推定〕と明記）。
>
> 受注データを**取り込む側**（統合コンソール）の実装はリポジトリが正本。ここは「easyECS がどうなっているか」の一次情報を置く。

## 要点

| 項目 | 内容 |
|---|---|
| 製品の形 | **インストール型**。先方のマスターPC `ECSSV01` 1台に入っていて、他のPCはそれを見に行く（2026-09-09 先方談、9/17 実機で裏付け） |
| DB | **SQL Server 2012 Express**（11.0.5058）、インスタンス `MSSQLSERVER2`、ポート **14333**、DB **`ecsdb_esy`** |
| 規模 | テーブル120（**データがあるのは40、空が80**）、列2,123。受注 `t_sell` 52万件、顧客 `m_customer` 44万件 |
| 受注の持ち方 | **受注 `t_sell` → 配送先 `t_sell_delivery` → 明細 `t_sell_goods`** の3階層。受注CSVの一意キー `(システム受注番号, 配送番号, 商品番号)` は `t_sell_goods` の主キーそのもの |
| 使っている機能 | 楽天（楽天ペイ経由）・Amazon・Yahoo!・au PAY（Wowma!）の受注、NP後払い、受注メール、在庫履歴 |
| 使っていない機能 | 楽天スーパーロジスティクス連携〔推定〕、ヤフオク！連携、仕入、定期購入、キャンペーン、セット商品（テーブルはあるが空） |
| 接続 | さくらVPS → Tailscale → `ECSSV01`。読み取り専用ログイン `read` のみ使用。**暗号化なしの接続しか通らない**（サーバが古い TLS にしか対応していない） |

## 分かったことのうち、判断に効くもの

> [!danger] ストア名で集計してはいけない（受注CSVの「ストア名」の trim は誤りの可能性が高い）
> `m_name.store_cd` を見ると、**別のストアが同じ表示名を持っている**。`02`・`05`・`07` はいずれも「グルメ＆ギフトお取り寄せ　山形ｅLab」で、**`07` だけ末尾に半角スペースが付いている**。直近3,000受注では `07` が 2,028件（楽天）、`05` が 358件（Amazon）で、モール区分の件数と一致する。
> [[platform - 10 変換器構想とMDC出力]] では 2026-09-08 に「ストア名に末尾スペースがあり、trim しないと**同一ストアが2つに分裂する**（1742件と138件）」と判断していたが、**実際は楽天とAmazon という別ストアを、trim で1つに混ぜていた可能性が高い**。〔CSV のストア名と `store_cd` の対応は未照合。確定するまでこの判断は暫定〕
> → 集計は **`store_cd`（またはモール区分 `mall_cd`）で行う**。詳細は [[easyECS - 03 受注テーブル（t_sell系）]]

> [!important] 「受注進捗」の 900番台は、先方が商品カテゴリとして作ったもの
> `m_name.order_status` には「未確認・出荷指示済・発送済・売上請求済…」という本来の進捗と並んで、**`903`=マルシェ／`904`=りんご：茶箱／`907`=もも：訳／`911`=もも：秀／`912`=ぶどう** などが登録されている。9/8 に受注CSVで見つけた「受注進捗名が商品カテゴリに転用されている」は、**easyECS の区分値マスタを先方が追加して運用している**ことが原因だった。

> [!important] 「未設定」の日付は NULL ではなく 1900-01-01
> `t_sell.cancel_date`（キャンセル日）と `t_sell_delivery.fix_ship_date`（出荷確定日）は、未設定のとき **`1900-01-01`** が入る。9/8 に受注CSVで見つけた「1900/01/01」はそのまま DB の値だった。

> [!warning] 設定系のテーブルは読まない
> `m_system`（327行）や `m_name` の `store_smtp*`・`store_api_merchant`・`store_rbank` などには、**メールサーバやモールAPIの認証情報が入っている可能性がある**。調査でも中身は取得していない。受注連携で必要になるのは受注3テーブルと `m_name` の業務区分（進捗・モール・ストア・支払・配送）だけ。

## まだ分かっていないこと

- テーブル定義書（ベンダー資料）。列の意味の〔推定〕を確定できる → [[08 要確認事項]]
- 受注CSV（76列）の各列が、どのテーブルのどの列から来ているかの完全な対応
- `t_sell.order_date` に、登録日時 `add_date` より後の時刻が入っている受注がある理由（直近サンプルで最大が当日 20:05、調査時刻は 17 時台）
- 本番DBへの定期的な読み取りの負荷を、先方が許容するか
- 売上分析で使う「商品群」「表示用の短い名前」をどこで持つか。easyECS の商品マスタには略称・分類・原価が無い（2026-09-17 確認 → [[easyECS - 02 DB構造（ecsdb_esy）#商品マスタ `m_goods` と、売上分析に使えるか（2026-09-17 追記）|02 の商品マスタ]]）。SKU の接頭辞で分けるか、先方に対応表を作ってもらうか
