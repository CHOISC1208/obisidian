# APP No.06 昼食申込

| 項目 | 値 |
|---|---|

| 表示名 | 昼食申込 |
| 定義 | `template/20_requests/06_lunch-order.xml` |
| 参照マスタ | `MenuMaster`（メニューマスタ） |
| 要望部署 | 経営SPG ／ 元重要度: **高** |
| 承認 | 原則なし（客専用も承認不要と確定） |
| 状態 | ✅ リスト・フォーム構築済み ／ ❌ フロー未実装（**金額計算・集計が動かない**） |

## これは何か

手書きの昼食集計表を廃止し、総務人事の集計負担と計算ミスを解消する。
**唯一の「承認なし」APP**で、性質としては申請というより日次の申込・集計。

給与天引きに直結するため、元重要度は「高」。

## メニューマスタの構造が一度作り直しになった

> [!warning] 口頭回答からスキーマを組んで失敗した例
> **2026-08-17 の回答**: 「ご飯の大盛/普通盛り/小盛で価格が変わる。ご飯のみ/オカズのみでも価格が変動する」
> → `MealPattern`（セット/ご飯のみ/オカズのみ）× `RiceSize`（大盛/普通/小盛/該当なし）の**2軸**で仮組み
>
> **2026-08-22 に実データを受領**: 大盛り(¥400) / Aランチ(¥360) / 小盛(¥340) / Aランチ副食(¥300) /
> 折詰弁当(¥1,100) の**5項目**。サイズ等の組み合わせ軸を持たない**独立したメニュー**だった。
> → `MealPattern` / `RiceSize` の2列を廃止し、`Title`（メニュー名）+ `Price`（価格）の単純な一覧に戻した。
>
> **教訓**: 08-17 の回答は「現象の説明」であってデータ構造の説明ではなかった。
> 実データが来るまでスキーマを確定させない方が安かった。

現在のメニューマスタは SPFx の「マスタ管理」画面から総務が直接編集する運用
（価格改定時にエンジニアを呼ばずに済ませるため）。

## 締切の扱い

| 時点 | 回答 |
|---|---|
| 2026-08-17 | 「当日8時**15**分まで」 |
| 2026-08-27 | 「申込締切は当日8:**30**とし、それ以降は入力不可」 |
| 実装 | **8:30**（`requestTypes.ts` の `lunchSubmitGuard`） |

> [!warning] 2つの回答が食い違っている
> どちらが正か確認していない。実装は後の回答（8:30）に合わせている。→ [[05 要確認事項]] V-1

### 締切チェックの限界（意図的に許容している）

SPFx フォーム側だけのチェックで、**既定の SharePoint リストフォーム（`list.aspx`）から直接投稿すれば
素通りする**。

> **「悪意を持って迂回する社員は想定しない」という判断で許容する**と明示的に決めている。
> フロー側でのチェック強化は不要。締切に間に合わなかった分は下記の救済運用で拾う。

## 申込漏れの救済運用

**総務が直接 SharePoint の既定リストフォームから入力する**（専用の代理申請UIは作らない）。

> [!warning] 申請者名がずれる
> `Applicant`（申請者）列はフローが作成者（＝総務自身）をそのまま設定する仕様のため、
> **実際に注文した本人ではなく総務の名前が記録される**。
> 本人名を残したい場合は `Title` か備考欄に手動で書き添える運用になる。
> **この点は先方に説明しておく必要がある。**
