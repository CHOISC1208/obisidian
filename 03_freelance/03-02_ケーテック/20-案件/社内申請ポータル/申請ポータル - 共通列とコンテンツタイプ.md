# 申請ポータル - 共通列とコンテンツタイプ

親: [[申請ポータル - 00 概要]] ／ [[00 MOC|ケーテック株式会社 MOC]]

出典: `template/00_common/01_site-columns.xml` / `02_content-types.xml`（2026-09-05 時点の実装）。

## 設計原理: 「誰が入れるか」を先に決める

このプロジェクトの列設計はすべてこの1点から派生している。

> **申請者に入力させる列を最小化する。**
> 申請者が入力するのは `Title`（件名）・`RequestDate`（申請日）・`Approver`（承認者）と、
> 各リストの固有列だけ。残りはすべてフローが設定し、フォームから隠す。

新しい共通列を足すときも、**「誰が入れるのか」を決めてからフォーム表示を決める**。

## 「申請共通」コンテンツタイプの7列

ID `0x0100A1B2C3D4E5F6470A9B8C7D6E5F4A3B20`、親は アイテム（`0x01`）。
各申請リストはこれをバインドし、固有列だけを追加する。**FieldRef の並び順がフォームの表示順になる。**

| 内部名 | 表示名 | 型 | 誰が入れるか | 新規フォーム | 編集フォーム |
|---|---|---|---|---|---|
| `Applicant` | 申請者 | User | フロー（`Author` をコピー） | 非表示 | 非表示 |
| `RequestDate` | 申請日 | DateTime(DateOnly) | 申請者（既定 `[today]`） | **表示** | 表示 |
| `ApplicantDepartment` | 所属部署 | Choice | フロー（Entra ID の部署属性） | 非表示 | 非表示 |
| `Status` | ステータス | Choice | フロー（既定 `申請中`） | 非表示 | 非表示 |
| `Approver` | 承認者 | User（必須） | **申請者** | **表示** | **非表示** |
| `ApprovedAt` | 承認日時 | DateTime | フロー | 非表示 | 非表示 |
| `ApproverComment` | 承認コメント | Note | フロー | 非表示 | 非表示 |

### `Approver` だけ扱いが特殊

**新規フォームには出すが、編集フォームからは隠す**（`ShowInEditForm="false"`）。
提出後に承認者を差し替えられると承認整合性が崩れるため。
この非対称性が、簡易承認方式の要になっている。→ [[テーマ2 - 承認者をどう決めるか]]

### `Title` はコンテンツタイプに入っていない

一意な識別子は SharePoint 組み込みの `ID` 列（自動採番・排他制御不要）を使う。
`Title` は表示名を「件名」にするため**各リストの `ListInstance` 側で個別定義**している。

> [!info] 申請番号という概念は持たない（2026-08-08 決定）
> 当初は `{課題No2桁}-{ID6桁}`（例 `07-000123`）をフローが自動採番する設計だった。廃止した理由:
> - 「一意なキーは `ID`、件名は自由入力」という役割分担のほうが単純で分かりやすい
> - 年度リセットの連番にすると採番テーブルと排他制御が必要になり、フローが直列化して遅くなる
>
> `RequestNo` 列は存在しない。**`issues/00` `issues/01` `issues/03` `issues/07` の列表には
> 今もこの旧仕様が書かれている** → [[06 リポジトリ内ドキュメントの現状差分]]

## `Status` の語彙（6値）

```
申請中（既定） / 承認済 / 却下 / 要手動対応 / 精算済 / 取消
```

`Status` は共通サイト列のため、**リスト単位で選択肢を分岐できない**。そのため業務固有値も
この共通列に相乗りさせ、未使用リストでは「単に選択されない値」として残す方針にしている。

| 値 | 位置づけ |
|---|---|
| 申請中 / 承認済 / 却下 | 全APP共通 |
| **要手動対応** | `Approver` に選ばれた個人へ到達できない場合のフォールバック（**必須設計だが未実装**） |
| **精算済** | 仮払金申請（No.1）専用の業務ステータス |
| **取消** | 昼食申込（No.6）の取消要望に対し、物理削除禁止の原則から追加（2026-08-27）。**値だけで操作UIは未実装** |

### 削られていった値の履歴

| 値 | いつ消えたか | 理由 |
|---|---|---|
| 一次承認済 | 簡易承認への転換時 | 2段承認の中間状態は中央トランザクション専用。簡易方式では「承認の開始と待機」を連続実行するだけで中間状態を持つ必要がない |
| 取下げ / 取消済 / 失効 | 2026-08-10 | 中央承認エンジンの「取下げ→再申請パターン」「トランザクション失効」の名残。どのAPPのフローからも使われていない |

> [!warning] `docs/conventions.md` の `Status` 表は9値のまま
> 「一次承認済」「取下げ」「取消済」「失効」を含む9値の表が残っている。実装は6値。
> → [[06 リポジトリ内ドキュメントの現状差分]]

## 削除された共通列

| 内部名 | 何だったか | なぜ消えたか |
|---|---|---|
| `WithdrawnAt`（取下げ日時） | 取下げ→再申請パターンの記録 | 簡易承認方式では「修正＝取下げ→再申請」を必須にしない方針に変更 |
| `OriginItemId`（元申請ID） | 同上（変更申請の元レコード参照） | 同上 |

## 実機で判明した「できないこと」

どちらも 2026-08-07 に dev テナントで確認済み。**設計を大きく規定している。**

### 1. Person 列に「既定値＝現在のユーザー」は無い

`<Default>[Me]</Default>` を試したが解決されず、新規フォームは空のままだった。
適用は成功して `DefaultValue` に文字列 `[Me]` が入るだけなので、**適用ログでは気づけない**。

> サイト列の `<Default>` は SharePoint 側で検証されず、そのまま `DefaultValue` に保存される。
> 値が有効かどうかは**フォームを開いて確認するまで分からない**。

### 2. 「作成者と申請者を IF で振り分ける計算列」は作れない

SharePoint の計算列の数式が扱えるのは **1行テキスト・数値・日付・通貨・選択肢・はい/いいえ だけ**。
Person 列も、組み込みの `作成者` / `更新者` / `ID` / `登録日時` も参照できない。

→ 結論: **「入力者を自動で入れる」はフォームでは実現できず、フローが `Author` を `Applicant` に
コピーするしかない。** これが「フローが動かないと `Applicant` が空になる」という現在の状態の原因。

## 内部名の衝突に注意

`Department` のように SharePoint 組み込みの隠しサイト列と内部名が衝突する語がある
（適用時に `重複するフィールド名 "..." が見つかりました` エラー）。

**新規列名を決めるときは一般的すぎる単語（Department / Status / Category 等）をそのまま使わず、
業務文脈をつけた名前にする**のが基本。実例が `ApplicantDepartment`。

## 代理申請について

共通設計としては**「代理申請は無い」前提**（`issues/99` C-10、先方未回答）。
必要と分かったら `ShowInNewForm` / `ShowInEditForm` を外して申請者に入力させ、フロー側を
「空欄のときだけ `Author` をコピーする」に戻せばよく、**列構成は変えなくてよい**。

> [!info] ただし慶弔だけ先行して代理申請を実装した
> 2026-08-27 の依頼を受け、慶弔連絡（No.2）にのみ `InitiatorType` に「代理申請」を追加し、
> 選択時のみ対象者を入力できるようにした。**共通列ではなくAPP固有列で実装**しているため、
> 上記の共通設計は変わっていない。→ [[申請ポータル - APP No.02 慶弔連絡]]
