# ver10 要望事項

親: [[00 MOC|ケーテック株式会社 MOC]] ／ 前版: [[30-プラットフォーム/spo/ver9/ver9 変化点]]

> [!info] このノートの役割（ver8/ver9の「変化点」ノートとは性質が違う）
> ver8・ver9の「変化点」ノートは**すでに対応した内容**を記録する版だったが、このノートは
> **まだ着手していない受付中の要望を溜めておく**バックログ。2026-09-23の海外保険加入依頼の追加要望から、
> 「要望が来るたびに個別対応するのではなく、ある程度まとまってから一括で着手する」方針に切り替えた
> （[[2026-09-22 年休・慶弔・昼食の追加要望]]は受領当日に11件まとめて着手したのとは逆の運用）。
> 着手を開始したら、このノートの内容を実装記録として「ver10 変化点」ノートへ移し替える。
>
> **2026-09-23、No.03・No.07(要望H)・No.06・No.11、および横断2段階承認(要望F・G)に着手し、
> [[30-プラットフォーム/spo/ver10/ver10.0.2 リリースノート]]へ実装記録として切り出した。**
> 慶弔連絡(No.02、設計方針は決定済みだが実装は未着手)だけが引き続きこのノートに残っている。

## 対応方針

- 要望を受領したら、この一覧に直接まとめる（**個別の`50-打ち合わせ/`ノートは作らない**運用に変更。
  当初は作っていたが、2026-09-23中に「このバックログに直接集約した方が分かりやすい」と判断し統合した）
- 着手のタイミングはユーザー判断。この一覧がある程度溜まってから一括対応する

## 受付中の要望

### No.02 慶弔連絡（`02_keicho-report.xml`）— 2026-09-23受領・同日設計方針確定

出典: 先方からのチャット貼り付け（`KeichoReports`リストのみ対象。列の並び替え・件名変更・制度種別ごとの
対象者/追加項目の再設計など多岐にわたる大きめの要望）

**要望内容の要約**

| #   | 要望                                                              |
| --- | --------------------------------------------------------------- |
| A   | 基本の並びを 対象者(従業員台帳から検索) → 起票区分 → 制度種別 → 対象者 → 雇用形態 → (以下変更なし) に変更 |
| B   | 件名を「yyyymmdd_制度種別_対象者(従業員台帳から検索)」に変更(代理申請でも対象が件名から分かるように)       |
| C   | 制度種別から「特別加算金」「社葬等協議事項」を削除                                       |
| D   | 「起票区分」を「申請者」に改称し、選択肢を 本人／代理申請 の2択に変更(「人事起票」を削除)                 |
| E   | 制度種別ごとに「対象者」の選択肢・追加項目を変える(結婚祝金/出産祝金/弔慰金/傷病見舞金それぞれ個別に指定あり)       |

> [!success] 設計方針確定(2026-09-23)
> 実装前に洗い出した10件の論点のうち、先方確認が必要なのは3件のみに絞り込んだ。残りは社内判断で決定済み。

**社内で決定済みの設計方針**

- 傷病見舞金の「対象」(業務上/業務上以外)は既存の`IsWorkRelated`列をそのまま独立列として維持する
  (`TargetPerson`のcontextual choices化はしない)
- 弔慰金の「実祖父母(同居)／実祖父母(別居)」は`TargetPerson`の選択肢自体に統合し、
  `IsCohabiting`(チェックボックス)は廃止する
- 「特別加算金」「社葬等協議事項」の削除に伴い、`InitiatorType`の「人事起票」選択肢と
  `IsUnderDeliberation`(審議中)列は連動して廃止する。今後この2制度が発生した場合は本システム外
  (手作業)で対応する
  - 根拠: [[2026-08-21_keicho-rule-clarification|2026-08-21 慶弔連絡 規程明文化・列設計決定]]の
    決定事項#4・#5がこの2制度専用の仕組みだったため
  - 依頼文の「起票区分を本人／代理申請の2択にする」(D)で人事起票の削除自体は既に指示済みのため、
    先方には確認ではなく**変更内容の通知**として伝える
- 件名生成の対象者は`TargetEmployee`(対象者(代理申請)、Person列)を廃止し、
  `EmployeeMasterRef`(対象者(従業員台帳から検索))に一本化する
  - 現状は代理申請のときだけ`TargetEmployee`という別のPerson列で対象者を選ばせ、件名生成には
    そちらを使っていた(`computeKeichoFields`のisProxy分岐)。しかし`EmployeeMasterRef`は
    2026-09-09時点で既に本人・代理どちらでも対象者を選べる設計であり、依頼文Bも件名の元を
    「対象者(従業員台帳から検索)」と明記しているため、対象者入力欄を1本化できる
  - 代理申請(`InitiatorType`=代理申請)のときは`EmployeeMasterRef`をSPFxフォーム側の入力必須にする
    (SharePoint列自体は本人申請の未登録者もいるため`Required="false"`のまま、フォーム側の
    バリデーションのみ条件付き必須にする)
  - 件名生成(`computeKeichoFields`)は`values.EmployeeMasterRefDisplayName`
    (lookupDisplayFieldの規約により`${field.name}DisplayName`キーに格納される。
    `RequestForm.tsx`のlookup表示ロジック参照)を優先し、未選択時のみ`__ApplicantDisplayName`
    (申請者本人)にフォールバックする(既存のフォールバック計算をそのまま流用)
- 「事実発生日」(`EventDate`)の表示ラベルを制度種別ごとに変える件は、**列を分割せず現行の単一列の
  ままSPFx申請フォーム側だけラベルを出し分ける**方針を維持する
  - 検討した代替案: 制度種別ごとに専用のDateTime列(入籍日/出産日/死亡日/休業開始日)を新設し、
    値が入っている列をIF分岐で採用する案。標準のSharePoint一覧・エクスポートでも正しいラベルで
    見える利点はあるが、同じ日付データを複数列に持つことになり同期崩れのリスクがある。一覧には
    `制度種別`列が隣にあり文脈で分かるため、採用しないこととした
- 件名フォーマットの日付部分「yyyymmd」は単純な誤記として扱い、8桁「yyyymmdd」のまま実装する

**先方(木村様)へ送る最終確認事項(3件)**

1. 【最優先】結婚祝金の対象者区分の構造: 「本人／子女(第一子)／子女(それ以外)」の3択にする案と、
   「対象者=子女を選んだ場合のみ第一子／それ以外をもう1段選ばせる」案のどちらにしたいか
2. 出産祝金「お子様の続柄」の選択肢を確認したい(自由入力か、プルダウンならどんな選択肢か)
3. 弔慰金の対象者ラベル変更(「父母」→「実父母・養父母・配偶者の父母」、「兄弟姉妹」→
   「本人の兄弟姉妹」)は表現を詳しくしただけで、規程上の対象範囲自体は変わっていないという
   理解でよいか

**先方へ通知する事項(確認ではなく報告)**

- 「特別加算金」「社葬等協議事項」の廃止に伴い、システム内部の関連の仕組み(起票区分の
  「人事起票」・審議中フラグ)も合わせて廃止すること。今後この2制度の申請が発生した場合は、
  本システムを使わず手作業で対応してもらうこと

**下調べで判明していること(先方確認とは別に社内で押さえておく事実)**

- 現状の`EmployeeMasterRef`(対象者(従業員台帳から検索))は既に「本人申請・代理申請どちらでも対象者を
  選ぶ」設計になっている(2026-09-09導入)。順序を先頭に持ってくること自体は既存ロジックと矛盾しない
- `KeichoMaster`(慶弔マスタ)は現状すでに「特別加算金・社葬等協議事項の行を持たない」設計のため、
  この2制度を削除してもマスタ側の変更は不要
- `KeichoMaster`は`TargetPerson`(対象者)と`CohabitingCondition`(同居/別居)を別軸で持っている
  (`config/masters/keicho-master.sample.csv`で確認済み)。上記Q3の統合をする場合は
  `TargetPerson`の選択肢自体に「祖父母(同居)」「祖父母(別居)」を持たせ`CohabitingCondition`列を
  廃止する形になる(マスタの列構成変更を伴う)
