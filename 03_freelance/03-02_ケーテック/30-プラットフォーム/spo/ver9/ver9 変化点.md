# ver9 変化点

親: [[00 MOC|ケーテック株式会社 MOC]] ／ 前版: [[30-プラットフォーム/spo/ver8/ver8 リスト別機能一覧（ベースライン）]]

> ver8からの**変化点となぜそうしたか**を記録する。ソースは2026-09-22の先方フィードバック

> （このバージョンの残タスクは本文末尾「未着手」参照）。リリース判断（いつver9として確定するか）は

## 対応済み

### No.07 年休申請

**① 年休カレンダーの色分け修正**
- 変化: `config/masters/business-calendar.csv`（seed）から9/14の行を削除
- なぜ: 先方が「9/14の色分けは誤り」と認めたため。ver8で送った確認依頼への回答
- 8/20は当初、先方の再確認待ちのまま意図的に残置していたが、**先方から原本PDF
  （`2026年度カレンダー (2).pdf`）を受領し`pdftoppm`で画像化して直接確認**した結果、
  8/20は原本にも一切マークが無い平日と判明。9/14と同じ「こちらの誤入力」パターンだった
- **原本を画像化して1件ずつ突き合わせた結果、9/14・8/20以外にも9件の食い違いを発見。**
  テキスト抽出だけでは色分け（グレー塗り=休日／白枠囲み=その他の休日=会社休日／△=推奨(部署裁量)）が
  失われるため、画像化が必須だった。`business-calendar.csv`を原本準拠に全面修正:
  - 4/29(昭和の日)・8/11(山の日): 祝日→推奨(部署裁量)に変更（△マークだった）
  - 5/1・8/4・8/5: 登録漏れを追加（5/1=会社休日、8/4・8/5=推奨(部署裁量)）
  - 5/4(みどりの日)・5/5(こどもの日)・1/1(元日): **祝日→会社休日に変更**
    （白枠囲みだったが除外対象外の「祝日」のまま登録されていた）
- **5/4・5/5・1/1は実際に取得日数計算へ影響するバグだった**（除外されるべき日が除外されていなかった）。
  4/29・8/11は種別が違うだけで計算結果への影響は無い（祝日・推奨(部署裁量)ともに除外対象外のため）

**② 取得日数計算のバグ修正**
- 変化: `BusinessCalendar`から日数計算の除外対象を取得する際、`HolidayType="会社休日"`の行だけを
  除外するよう修正（従来は`HolidayType`を見ず全行を無差別に除外していた）
- なぜ: 「祝日は休日ではない。指定休日は土日＋カレンダー上四角枠(GW/お盆/年末年始)の会社休日のみ、
  推奨(部署裁量)は出勤日」という会社休日の定義が①への回答で判明したため。8/7〜8/17で7日と
  表示された(正しくは4日)という不具合報告も、この定義に合わせて修正することで解消する設計にした
  （「7日」という数字自体はテナント側のデータ未投入によるフォールバックの可能性が高いと推測している。
  実機未検証）
- 影響ファイル: `RequestForm.tsx` / `types.ts` / `requestTypes.ts`

**③ 特別休暇の事由カスケード（休暇区分→事由→内容）の新規設計**
- 変化: `Reason`(事由)列を、休暇区分＝特別休暇のときだけ選択肢セットが切り替わる方式に拡張
  （フォームエンジンに`choicesFor`を新設）。新規列`SpecialLeaveDetail`(内容)を追加し、
  `Reason=慶弔休暇`のときだけ表示。就業規則第46条(正社員)/第16条(契約社員)の①〜⑦
  （例:「①本人が結婚するとき(5日)」）
- なぜ: 特別休暇には就業規則で定める取得事由の指定があり、年休等の一般的な事由とは別立てで
  選ばせたいという要望。慶弔連絡(APP No.02、慶弔見舞金規程ベース)とは法的根拠も対象(日数 vs 金額)も
  異なる別物であることに注意（名前が紛らわしいため）
- 影響ファイル: `07_leave-request.xml` / `types.ts` / `RequestForm.tsx` / `requestTypes.ts`

**④ 遅刻/早退の入力制御・時刻選択式化**
- 変化: `computeLeaveFields`が遅刻/早退のとき`EndDate`を開始日に固定、`LeaveDays`を空欄のまま
  どちらも編集不可にするよう変更。`StartTime`/`EndTime`をtext入力からchoice(30分刻み・6:00〜22:00の
  プルダウン、`TIME_CHOICES`)に変更
- なぜ: 「終了日・取得日数を入力不可にしてほしい」「時刻を手入力ではなく選択式にしたい」という要望。
  時間帯の範囲(6:00〜22:00)は先方から具体的指定が無かったための仮置き
- 影響ファイル: `requestTypes.ts`（列自体・`07_leave-request.xml`は変更なし。Text型のまま選択式に）

**⑤ 承認者Person Pickerのバグ調査**
- 変化: `ClientPeoplePickerSearchUser`呼び出しの`MaximumEntitySuggestions`を15→30に緩和
- なぜ: 「メールアドレス入力なら常に表示される」のは検索自体が優れているからではなく、
  `NormalPeoplePicker`の`onValidateInput`がメール形式文字列をフリーテキストとして検証だけ通し、
  送信時に`sp.web.ensureUser`で解決する別経路(検索をバイパス)だと判明。氏名検索は完全に
  検索APIの結果次第で、結果件数の上限に該当者が埋もれている可能性が高いと推測した
- **未解決のまま残っている点**: これは緩和策であり根本原因（該当者側のEntra ID属性の状態等）は
  テナント側の実機調査が必要
- 影響ファイル: `PersonPicker.tsx`

**代理申請機能の追加**
- 変化: `InitiatorType`(起票区分: 本人申請/代理申請)・`TargetEmployee`(対象者)列を追加。
  慶弔連絡と同じ考え方（提出後の差し替え防止のため`TargetEmployee`は`ShowInEditForm="false"`）。
  代理申請時は件名にも対象者の氏名を使う
- なぜ: 慶弔連絡で既に実装済みの機能を年休申請にも横展開してほしいという要望
- 影響ファイル: `07_leave-request.xml` / `types.ts`（変更なし、既存の仕組みを流用） / `requestTypes.ts`

### No.02 慶弔連絡

**派遣社員の扱い確定**
- 変化: なし（コード変更不要と確認しただけ）
- なぜ: 「派遣社員には慶弔金の支払いがないため、申請自体を想定しなくてよい」と回答があり、
  `EmployeeMaster`の雇用形態マッピング（マッピングできなければ自己申告のまま、というフォールバック）
  が既に対応済みだったため、追加対応不要と確認した。ver8で送った確認依頼への回答

**1申請=1枚の印刷用出力フォーマット**
- 変化: なし（開発しない方針を確定）
- なぜ: 現金管理の証憑として承認印欄付きの単票が欲しいという新規要望に対し、No.7の毎月20日締め
  出力と同じ考え方で、**開発せずExcel(Power Query)で先方側が対応する**方針に確定した

### No.06 昼食申込

**① 区分の4種再設計**
- 変化: `OrderType`を「社内/客専用」の2区分から「社員/中国出張者/お客様(ISO)/お客様(その他)」の
  4区分に再設計（既定=社員）。新規列`GroupOrderDetail`(明細、自由記述のNote)を追加し、
  中国出張者・お客様(その他)のときだけ表示
- なぜ: 実際の利用形態(社員個人の注文/客の種類別)に合わせて区分を細分化してほしいという要望。
  複数人分をまとめて申し込むケースの内訳は、SharePointに行持ちの仕組みを新設せず自由記述で
  簡易対応した（複雑さを持ち込まない方針を優先）
- 影響ファイル: `06_lunch-order.xml` / `requestTypes.ts`

**② メニューマスタの2軸構造（MealPattern/RiceSize）を復活**
- 変化: `13_menu-master.xml`・`masterTypes.ts`に`MealPattern`(セット/ご飯のみ/オカズのみ)×
  `RiceSize`(大盛/普通/小盛/該当なし)を復活（2026-08-22に一度廃止した構造と同一のGUIDで再設定）
- なぜ: 「メニューの選択について『大盛・普通盛り・小盛』のプルダウンを表示する」という要望を受け、
  「前に戻す」との判断
- **未解決のまま残っている点**: 実データ5項目（大盛り/Aランチ/小盛/Aランチ副食/折詰弁当）をこの
  2軸にどう当てはめるかはこちらの仮置き。2026-08-22に「サイズ軸を持たない独立5メニュー」と
  説明を受けて一度廃止した構造への逆戻りになるため、先方確認が必要
- 影響ファイル: `13_menu-master.xml` / `masterTypes.ts` / `config/masters/menu-master.sample.csv`

**③ 費用負担部署**
- 変化: `CostDepartment`の選択肢を全社部署一覧(経営SPG/購買G/営業/設計/製造/その他)から
  「経営SPG(51)/技術事業(11)」の2択に変更。区分(OrderType)に応じてSPFx側で選択を固定・制限
  （社員・お客様(ISO)→経営SPG(51)固定、中国出張者→技術事業(11)固定、お客様(その他)→選択可）
- なぜ: 実際の運用が2部署のみで、区分ごとに実質固定であるという要望
- 影響ファイル: `06_lunch-order.xml` / `requestTypes.ts`
