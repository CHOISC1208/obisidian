## 1. 方針の要約

- 1リスト=1フロー。共通の骨格(§2)を全APPで同一にし、差分(§3)だけをAPPごとに持つ。
- 使うコネクタは標準のみ: SharePoint / Approvals / Office 365 Users / Teams。プレミアム不使用。
- フロー内に個人名・メール・サイトURL・リストGUID・チャネルIDを直書きしない(環境変数 or 列の値)。
- 承認の宛先は申請者が選んだ `Approver` 列(2段承認APPは `LeaderApprover` → `Approver` の順)。

### 命名

| 項目 | 規則 | 例 |
|---|---|---|
| フロー名 | `No{課題No2桁}_{ListUrl末尾}_Approval` | `No07_LeaveRequests_Approval` |
| 生成中の暫定名 | 先頭に `[TEST]` | `[TEST] No07_LeaveRequests_Approval` |
| ソリューション | `ApprovalFlows`(旧中央エンジン版 `ApprovalFlows_1_0_0_2.zip` は参照のみ・採用しない) | |

### 環境変数(ソリューション)

| 名前 | 内容 |
|---|---|
| `spp_PortalSiteUrl` | 申請ポータルのサイトURL(既存) |
| `spp_{List}ListId` | 各申請リストのGUID(例 `spp_LeaveRequestsListId`、既存の命名に合わせる) |
| `spp_KeichoMasterListId` / `spp_MenuMasterListId` | 慶弔マスタ・メニューマスタ |
| `spp_ReadOnlyRoleDefinitionId` | 閲覧ロール定義ID(既存) |
| `spp_AdminTeamId` / `spp_AdminChannelId` | 管理者アラート先(**新規**) |
| `spp_GeneralAffairsGroupId` | 総務人事の SharePoint グループID(慶弔の閲覧付与・通知用。**新規**) |

不要になった旧環境変数(`ApprovalTransactions` / `AuditLog` / `RequestTypeSettings` / `FullControlRoleDefinitionId`)は新ソリューションに持ち込まない。

## 2. 共通骨格(全APP共通の8ステップ)

```
トリガー: SharePoint「項目が作成されたとき」(サイト=spp_PortalSiteUrl、リスト=spp_{List}ListId)

Scope_Main
 ① 申請者の特定        Applicant ← 作成者(Author)。ApplicantDepartment ← Entra の department
                       (Office 365 Users「ユーザープロフィールの取得(V2)」)。選択肢に無い値は「その他」。
 ② 受付                 Status ← 申請中
 ③ 権限ロック          当面なし(2026-10-07決定。SPFxで編集不可・副作用回避。必要になればAPP単位で再検討)
 ④ 承認                 「承認の開始と待機」(承認/却下・最初の応答)
                         タイトル : [{リスト表示名}] {Title}
                         詳細     : ApprovalMessage(空なら §2-a の簡易文面)
                         宛先     : Approver(2段APPは §2-b)
                         項目リンク: 申請アイテムのURL
 ⑤ 結果の書き戻し       Status ← 承認済 / 却下、ApprovedAt ← utcNow()、ApproverComment ← 応答コメント
 ⑥ 申請者へ通知         承認/却下の結果+コメントを Teams(Flow bot のチャット)で通知
 ⑦ APP固有の後処理      §3(通知・Status追加遷移など。APPごとに最小限)

Scope_Catch(Scope_Main が 失敗 / タイムアウト のとき実行)
 ⑧ フォールバック       Status ← 要手動対応 ＋ 管理者チャネルへ投稿(フロー名・項目ID・項目リンク・エラー概要)
                       ※ 却下にはしない(CLAUDE.md)
```

### 2-a. 承認カード本文

`ApprovalMessage` が空でないときはそのまま差し込む(フロー側で列を連結しない)。空のとき(リスト標準フォーム等から登録)は
「{申請者}さんからの{リスト表示名}です。件名: {Title}」の簡易文面にする。

### 2-b. 2段承認(1次=リーダー任意 → 2次=マネージャー必須)

対象: 01 / 02 / 03 / 07 / 19 / 20。

```
if LeaderApprover が空でない かつ LeaderApprover ≠ Approver
    承認1(宛先=LeaderApprover)
    if 却下 → Status=却下、コメント記録、⑥へ(2次は呼ばない)
承認2(宛先=Approver)
ApproverComment ← 「【1次】{コメント}／【2次】{コメント}」(1次を飛ばした場合は2次のみ)
ApprovedAt ← 最終承認(または却下)の時刻
```

- 1次と2次が同一人物の場合は承認を1回にまとめる(二重承認の無意味な呼び出しを避ける)。
- 提出後に承認者が変わらないよう、`Approver` / `LeaderApprover` は編集フォームから隠してある(`ShowInEditForm=false`)。

### 2-c. エラーハンドリングの方針

| 事象 | 扱い |
|---|---|
| 宛先が解決できない・承認の開始に失敗 | Scope_Catch → `要手動対応` + 管理者アラート |
| 承認の応答が一定期間ない | **催促**(2026-10-07確定): 24時間ごと・平日のみ・最大3回、承認者へ Teams で催促。打ち切りはしない。30日で承認が失敗した場合のみ Scope_Catch(`要手動対応`+管理者通知)に落ちる |
| 書き戻し(項目の更新)失敗 | 同上。リトライポリシー(固定間隔・3回)を更新アクションに設定 |

### 2-d. 再トリガー防止

トリガーは「作成時」のみで、フロー自身の項目更新では再実行されない。トリガー条件で `Status` が空であることを確認し、
SPFx 経由でない直接登録でも二重起動しないようにする。

## 3. リスト別の設計

凡例: **2段**=§2-b を適用 / **固有列**=フローが読む・書くリスト固有列。

### No.07 年休申請 `Lists/LeaveRequests`(雛形)

| 項目 | 内容 |
|---|---|
| 承認 | 2段(Leader任意→Approver必須) |
| 起票区分 | `InitiatorType=代理申請` のとき対象者は `TargetEmployee`。`Applicant` は作成者のまま(代理入力した人)とし、通知は作成者と対象者の両方へ |
| 固有処理 | なし。件名・`LeaveDays`・時刻はSPFxが設定済みのためフローは再計算しない |
| 承認済後 | 通知のみ。20日締めの総務向けCSV/Excel出力はフロー対象外(Excel×Power Query) |
| 留意 | 年休カレンダーの公開/非公開(要確認 §5-A)は承認フローの外 |

### No.01 仮払金申請 `Lists/AdvancePayments`

| 項目 | 内容 |
|---|---|
| 承認 | 2段 |
| 固有列 | `Amount`、`PaymentDueDate`、`SettlementDueDate` |
| 承認済後 | 承認結果の通知に 金額・支払希望日・精算予定日 を含める |
| `精算済` への遷移 | **本フローの対象外**(精算の仕組み・担当が未定。§5-B)。値は共通Statusに存在する |

### No.02 慶弔連絡 `Lists/KeichoReports`

| 項目 | 内容 |
|---|---|
| 承認 | 2段。**承認だけのフロー**(共通骨格のみ。固有の算出処理は持たない) |
| 権限 | 項目権限の絞り込みは**当面なし**(2026-10-07)。「同僚に見せない」要件は別途検討 |
| 金額 | **フローでは算出しない**。`PlannedAmount`(支給予定額)は承認の対象外とし、扱いは §5-C |
| 経理通知 | 先方回答(2026-08-17)は「本人が入力してボタンを押した時」。承認前の通知になるため §5-D で確認 |

### No.03 海外保険加入依頼 `Lists/OverseasInsurance`

| 項目 | 内容 |
|---|---|
| 承認 | 2段(旧:所属長→社長は 2026-09-23 に Leader→Manager へ統一済み) |
| 承認済後 | 総務(保険サイト入力担当)へ「渡航者・渡航先・出発日〜帰宅日・同行者」を通知(メール)。保険サイトへの入力自体は人手 |
| 事後申請 | `IsRetroactive=true` でも承認は通常通り行う。承認カードと通知に「事後申請」と明記 |
| 留意 | 渡航者情報は従業員マスタ由来(SPFxが自動入力)。フローは参照のみ |

### No.06 昼食申込 `Lists/LunchOrders`(**承認なし・最小フロー**)

| 項目 | 内容 |
|---|---|
| 承認 | **なし**(先方回答 2026-08-17 / 2026-09-22。全 `OrderType` で承認不要。確認は後から見られればよい) |
| フローの中身 | 共通骨格の①起票処理(`Applicant`/`ApplicantDepartment`)と②`Status ← 承認済`(受付確定)だけ。③権限ロック・④承認・⑤結果書き戻し・⑥通知は省略 |
| フローで**やらない**こと | 金額算出(`Amount`)、期間まとめ申込の日別展開、締切チェック、月次集計。いずれも **Power Query で実施**(2026-10-07確定) |
| 取消 | `Status=取消` の運用は別途(未実装・§5-E) |
| 留意 | 共通 `Approver` 列は必須だが承認不要のため、SPFxが自動補完しているかを要確認(§5-G) |

### No.19 休日出勤/振休/代休申請 `Lists/HolidayWorkRequests`

| 項目 | 内容 |
|---|---|
| 承認 | 2段 |
| 固有処理 | 防御的検証: `WorkEndTime - WorkStartTime ≤ 8h` かつ `CompensatoryType` が入っている(SPFxをすり抜けた直接登録) → `要手動対応`+アラート |
| 予定/実績 | 実績は予定と紐づけない独立申請のため、フローでは区別せず同一処理。通知文面に区分を出す |
| 承認済後 | 通知のみ(勤怠への反映は人手) |

### No.20 夜勤申請 `Lists/NightShiftRequests`

| 項目 | 内容 |
|---|---|
| 承認 | 2段 |
| 固有処理 | なし(終業が翌日に跨ぐ場合の扱いは先方未回答のため、フローで時刻計算をしない) |
| 承認済後 | 通知のみ。月次集計の要否は先方未回答(§5-H) |

## 4. 作成・検証の進め方

1. **No.07 を雛形として1本だけ**先に作る(`[TEST]` 付き、`Approver` は自分、本番リストに触れない)。
2. 承認〜書き戻し〜通知〜フォールバック(宛先不在で強制失敗させる)を実行して確認し、人が Power Automate ポータルで
   宛先が `Approver` 列になっているか・Scope_Catch が入っているかを確認する(CLAUDE.md の確認項目)。
3. 骨格が固まったら `copy_flow` 相当で 01 / 02 / 03 / 19 / 20 に展開し、固有処理だけ差し替える。06 は承認なし型として別構成。
4. 各フローを `flows/solution/` のソリューションzipとして取り込み(リポジトリを正にする)、`flows/README.md` を本方式に改訂する。

> 現在 FlowAgent の接続先は**先方テナント**(k-ktec)になっている。生成は CLAUDE.md の隔離条件
> (テスト用サイト/リスト・`[TEST]`・新規作成のみ)を満たしてから始める。

### 仮置きした判断の一覧

- 2次が1次と同一人物のときは承認1回に集約する。
- 承認タイムアウトを30日とする(督促はしない)。
- 権限ロックは当面実施しない(2026-10-07)。
- 昼食は全区分で承認なし、フローは起票処理と `Status=承認済` のみの最小構成とする。
- 慶弔は承認のみ。金額算出・マスタ参照はフローに入れない。
- ApplicantDepartment は Entra の `department` から取得し、選択肢外は「その他」とする(列自体の存続は未確定のまま)。
