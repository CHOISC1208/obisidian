# 企画と設計のポイント（調査）

親: [[05_game/00 MOC|05_game]]

1本目のゲームを作る前に押さえる、企画と進め方の判断基準。技術の話は [[Unity×Git初期設定（調査）]] に分けた。

**読み方：** 各項目を `出典`（他者の主張）と `解釈`（このVaultの運用ルール）に分けて書く。前者を根拠、後者を判断として扱う。出典は検索スニペットの要約で、本文まで読んでいないものがある。裏取り状況は項目の末尾に書く。

## 1. 企画書は軽く、1枚で始める

> 出典：Stone Librande の GDC 2010 "One-Page Designs" は**伝達**の話。長い企画書は読まれず、wiki は要素間の関係が壊れる。だから注釈つきの図1枚で伝える。1テーマにつき1枚を何枚も作る方式で、「ゲーム全体を1枚に」という主張ではない。続編 "Simulating a City, One Page at a Time" は大規模・長期案件での長所と短所を扱う。（レビュー指摘。講演原文は未確認）

> 出典：個人開発向けテンプレ記事は、ピッチ・コアループ・機能・やらないことの数項目に絞ることを勧める。試作前に1ページを超えたら計画しすぎ、という書き方もある。（マーケ寄りの記事。業界標準ではない）

> 解釈：**1本目は、ゲーム全体を1枚に収めるルールにする。** 収まらなければ削る。これはスコープ過大の検知として使う自分のルールで、Librande の主張ではない。

> 解釈：企画書は道具だが、1本目は**更新コストに時間を吸われる**ほうが起きやすい。「コアループ1行＋1枚企画＋Won'tリスト」で始め、企画書は捨てる前提にする。更新するのは、試遊で決めたことがあったときだけ。

## 2. コアループを最初に決める

> 出典：動詞3〜4個で書く。行動 → フィードバック → 報酬 → もう一回、を30秒程度で1周するものとして説明される。企画書の中心に置く記事が多い。

> 解釈：ここが面白くなければ他を足しても面白くならない、という前提で、企画の最初に書く。検証は紙プロトタイプ（ルールだけで遊ぶ）→ グレーボックス、の順。

## 3. 完成しない原因と対策

> 出典：個人開発の失敗は機能の肥大化が主因。MVPの定義、Must / Should / Could / Won't の分類、機能ごとのタイムボックス、早期プレイテスト、が繰り返し推奨される。見積もりを2倍にするという主張もある（1記事）。

> 解釈：
> - **Won't（今回はやらない）を最初に埋める。** Mustを減らすより、先に切るほうが効く。
> - 見積もりは「2倍」で足りない。初心者は3〜4倍になりがち（レビュー指摘。出典は未確認）。2倍にするより、範囲を削る。
> - タイムボックスを何度も超えるなら、見積もりではなくスコープを疑う。

## 4. 1本目で効く追加項目

| 項目 | 中身 |
|---|---|
| 誰が遊ぶか | 1文でいい。「〇〇が好きな人」 |
| リファレンス1本 | 類似ゲームを1本選び、そのコアループを自分の言葉で書く。企画の前提 |
| 完成の定義 | 「起動して、1回遊べて、終わりがあり、公開されている」 |
| 公開先 | 最初に決める（itch.io など）。締切として機能する |
| 紙プロトタイプ | グレーボックスより前に、ルールだけで面白いか確かめる |

→ [[ゲーム名 - 一枚企画]] テンプレに反映済み。

## 次に調べる順番

1. **プレイテストの聞き方。** 質問すると社交辞令が返る。黙って見て、「どこで迷ったか」「何をしたかったか」を本人の言葉で拾う。
2. **類似ゲーム分析（1本）。** コアループを自分の言葉で書き出せたら合格。
3. **完成の定義と公開。** itch.io の公開フローを一度通す。1本目のゴール。
4. **AI生成素材の規約。** サービスごとの商用利用に加え、Steam の AI 利用開示も確認。
5. **プラットフォーム審査・費用。** 最後でよい。変わりやすいので公式ページだけを信頼する。
