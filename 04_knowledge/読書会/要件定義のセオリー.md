# 要件定義のセオリー

赤俊哉『だまし絵を描かないための 要件定義のセオリー』（リックテレコム, 2018-05）。**全編を通読**し、序章〜終章の章別ノートを [[要件定義のセオリー_MOC]] 配下に持つ。
読書会の場としては未開催で、**現時点では個人の読了ノート**（2026-09-09 にvaultへ配置）。

## 本の要点

- **要件 ＝ 要求を制約で絞り込んだもの。** 要求の全部が要件になるわけではなく、落とした要求は「どの制約で不可か」を残して先送り管理する
- 上流工程は**システム屋と業務屋の相互翻訳**。自然言語だけでは各人が違うものを見る「だまし絵」になるので、**図式モデルを共通言語**にする
- 要求・要件は**ビジネス → 業務 → システム**の3階層でトレース可能に整理する
- 成果物は最小限（プロセスモデル／データモデル＋用語集／CRUDマトリクス）。**データ要件の不備が後工程で最大の手戻り**になる
- 「トップダウンで骨組み、ボトムアップで肉付け」「最小の労力で最大の成果」

## 自社への当てはめ

- **MOSS の「要求 → 定式化」は本書の「要求 → ToBeモデル → 要件」と同じ構造。** とくに assumption ledger（事実／仮定／対象外の分離）は「要求すべてが要件になるわけではない」を実装側で担保している仕組みと読める（[[MOSS MOC]] / [[MOSS AIチャットモードの対話設計]]）
- **5W2H の `How much`（実施量）は数理最適化案件では必須項目。** 件数・規模が計算時間とデータ量に直結するため、本書が業務プロセス要件の一項目として扱うものを、MOSS の要求ヒアリングでは落としてはいけない項目として扱うべき
- **`devflow-standard` の `spec.md` は本書でいう「設計工程のインプットとして使える要件」に相当。** 本書が要件に課す二重の要請（ユーザーが読める表現かつ設計に使える具体性）をテンプレート側で担保できるか検討の余地がある（`devflow-standard` のノートは未作成）
- **「システム要求が最初から明らかなケース」の4分類**（RFP由来／保守フェーズの現場の声／誰の目にも明らかなUI改善／法改正等の外部要因）は、部門への訪問ヒアリングで「この要求はどこから来たか」を問うチェックリストとして使える（[[DIテーマ MOC]] の初期ヒアリング）
- **業務改革系テーマでは「トップダウンの覚悟」の指摘が効く。** 本書は部門長がリーダーを兼ねる体制の限界を挙げており、[[鹿島フロート受け払い計画の自動化]] のように**意思決定者と運用担当が別の担当に分かれている**構成はこの点では健全。全社最適の判断が要るときに誰が決めるかを先に決めておく話として使える
- **成果物最小化の思想は vault 運用方針と一致する。** 「メンテできない成果物は作らない」は [[ナレッジベース提案（Obsidian × GitLab × Claude Code）]] の方針としても明文化しておきたい
- **「要件定義がうまくいかない5原因」の④形骸化は、テンプレート化・plugin化を進める側の最大のリスク。** 各コマンド・各テンプレに「なぜこの成果物を作るのか」を書いておく根拠になる（[[Claude Code × Vault 使い方の実例]]）

## 使えそうなテーマ

1. **MOSS の要求ヒアリングに 5W2H を組み込む**（とくに `How much` を必須項目にする）— 試すなら `04_knowledge/検証ログ/` にログを起こす
2. **`devflow-standard` の `spec.md` テンプレに「ユーザーが読める／設計に使える」の二重チェックを入れる**
3. **訪問ヒアリング用の「この要求はどこから来たか」4分類チェックリストを作る** — [[DIテーマ MOC]] 配下のテーマ立ち上げ時に使う
