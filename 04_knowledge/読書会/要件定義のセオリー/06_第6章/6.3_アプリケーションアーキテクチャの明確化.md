# 6.3 アプリケーションアーキテクチャの明確化

← [[6.2_システムアーキテクチャの明確化]] | ↑ [[要件定義のセオリー_MOC]] | → 第7章 [[7.1_要件定義の妥当性確認]]

## アプリケーションアーキテクチャの位置付け

- 非機能要件を満たすシステムアーキテクチャを基盤とし、**機能要件を満たす条件** を検討。使用プログラミング言語、データフォーマット、命名規則、通信手段、コーディング規約、UI 標準、プロセスモデル標準、データモデル標準、モデリングツールの使用標準を検討
- 標準に関しては、他システムで採用しているものを **踏襲するのか、新たに作成するのか** をきちんと整理して決める
- 設計標準をアーキテクチャとして捉えるべきかは考えが分かれるが、アーキテクチャの方向性が定まってきたら併せて検討。「基盤」が定まったら、その標準的な「使い方」までを可能な限り検討
- クラウドサービスを採用した場合、システムアーキテクチャの方向性によりアプリケーションアーキテクチャが決まってしまう場合がある → 制約を受け入れた上で検討

## 設計標準の検討

- UI 画面・画面遷移パターンの標準化を、エンタープライズ系・コンシューマー向け・その混合のシステムごとに進め、**UI 画面レイアウト標準と画面遷移標準** を規定
- 業務プロセスの 5W2H 定義を基にした機能要件でマルチデバイス使用を前提とするなら、**デバイスごとの UI 標準** を考える。固定 PC・ノート PC とスマホ・タブレットでは機器・通信環境・利用環境の特性が異なるため標準は異なる
- ここで UI 標準を決めておくことで結果的に後々工数の削減につながる。UI の一貫性を保ち、ユーザーが混乱しない快適な操作性を担保
- 標準を決めるにあたっては画面パターンごとに **いかに UI を「シンプル」に実現するか** を考える。「シンプルさ」を考慮して定めた UI 標準が画面遷移を考慮した際に違和感がないかを確認

## プロセスモデル標準とデータモデル標準

業務フロー表記、業務プロセスの 5W2H 定義、仕様記述、データモデル表記／定義に関しても標準を決めておく。モデル作成時に標準がないとモデルの品質に明らかにばらつきが生じ、モデルの品質低下が **要件定義自体の品質低下** につながる。

## 明確にすべきアプリケーションアーキテクチャ

最低限、以下について方向性を決める：
- 処理形態（オンライン・バッチ等）
- アプリケーション方針（オンラインバッチ連動方法、どこまでサーバー側で処理するか、機能配置等）
- サーバー側プログラミング言語・フレームワークの使用
- DB 操作方法
- 通信プロトコル
- クライアント側プログラミング言語
- ユーザーアクションの検知方法
- データ保持方法・チェック方法
- 画面遷移方法
- 排他制御方式（楽観ロック、悲観ロック）
- 取消方法
- ログ

現時点におけるアプリケーションアーキテクチャの方向性を明確化し、一旦方向性を確定し **「アーキテクチャ定義書」** にまとめる。上記各項を定義する際、守るべき順番はない。それぞれが明確になればよいので「手順」は示さない。

### Column：簡易に作ることを恐れるな！（要旨）
エンタープライズ系に限った話かもしれないが、機能により **簡易言語の使用** を検討する。単純な機能に複雑（プライオリティの高い）機能と同じ工数をかける必要はない。同時実行性が少なく使用頻度が低いが開発せざるを得ない機能なら簡易に作ることを検討してよい。プログラミング言語の統一性は考慮すべきだが、開発の選択肢は昔と比較にならないほど増え、用途に応じて使い分けられる時代。業務プロセスの 5W2H を定義した後、実際にどう実装するか、工数・品質面のメリットを検討。組織の様々な業務プロセスを IT がうまく支援できればビジネスの幅が大きく広がる。投資効果測定等で今回開発対象外となった業務プロセスも、個別システム開発・個別パッケージ適用（クラウド含む）で対応可能とする余地は残す。**外部インタフェースだけでも用意して対応可能な形を整えておく** ことが重要。
