# 1.2 要件定義の工程

← [[1.1_要件定義が果たすべき目的]] | → [[1.3_2種のシステムと2種の案件]]

システム開発全体の中での、工程としての要件定義の位置づけ。

## ウォーターフォール型開発における要件

- WF は「業務分析 → 要件定義 → 基本設計 → 詳細設計 → 実装」を一方向で進める。一方向が原則でも、工程を考える上では **反復を想定し、要求 → 要件 → 設計 → 実装のトレーサビリティを可能にする** ことを考慮すべき
- そのために要件定義では、開発対象システムの **「大枠の方向性と規模が具体的に明確になっているレベル」** が必要
- 「手戻りを認めてはWFではない」という意見もあるが、変更発生時に要件の変更を遡って反映できることは工程全体の整合性担保に不可欠。WF と反復型のハイブリッドが現実解として定着しつつある
- 手戻りを認めない理由はコスト。ただし「手戻りしたくない」と頑迷に思い込み、90点の要件定義を100点にするために工数をかけて利益を失うくらいなら、**トレーサビリティを確保する仕組みを作って設計を進めた方が得策**。これは「手戻りコストを抑制する」WFの理念と矛盾しない

## 「手戻り」と反復 〜 なぜ反復を可能とするか？

- WF でも必要なら **ある程度の反復開発を認める** 立場。理由は「要件の確定」だけでなくプロジェクトの **時間軸** を考慮する必要があるから
- 「要件定義が終わらないうちは次工程に進んではいけない」は正論だが、いつまでも時間をかけてよいわけではない。要件妥当性の合意に工数が超過してよいはずがない → **要件として確定すべき範囲を狭めて次工程に進む** しかない。時間がかかりすぎると要求が陳腐化し、完成時には使えない恐れ
- アジャイルは時間軸の問題は解消しているが、大きな要求変更時にはイテレーション以前に遡る必要が生じる
- いずれの場合も重要なのは **実装段階でも要求 → 要件 → 設計 → 実装のトレースがきちんと取れていること**。トレースできないシステムはライフサイクルが短くなる
- 例外：システムライフサイクルより「リリース時点のビジネス価値最大化」が優先されるならトレーサビリティは不要かもしれない（コンシューマー向けに時々見られる）。それでも当初の開発目的は保守フェーズまで明確であることが望ましく、目的・方向から外れた修正を防ぐためにもトレース可能な環境構築は必要

## 手戻りについて

- WF で「手戻り」は避けるべき事項とされ、それを嫌ってアジャイル信仰が広まった歴史がある。アジャイル派の「仕様確定を手戻りなしで行うのは不可」には著者も同意
- 本書が WF 寄りに見えるのは、**基本形を押さえた上で「崩す」**、基本を踏まえたカスタマイズ可能なやり方が万能だと確信しているから
- どんな開発手法でも **ある程度の手戻りは起こりうると覚悟し、各工程で反復を可能にする** 必要がある

## アジャイル型開発における要件

2つの考え方：
- **A. 要件までは確定した上で反復を行う**：エンタープライズ系・外部連携を伴うシステムと親和性が高い。エンタープライズ系でのアジャイル適用の現実解。「要件定義の後半」から「実装」までをイテレーションの中で行う
- **B. 要件定義も繰り返しの中で行う**：単独で動くシステム、仕様変更が他システムに影響せず現場で仕様確定できるシステムと親和性が高い。前準備の後（これも要件定義と呼んでよい）、繰り返しの中で本来要件定義工程で行うべき作業を行う

要件修正の反映：
- A の場合、操作レベル（ユーザビリティ改善）や項目追加なら即時修正可（WF も同じ）。**ビジネス要件レベルの変更なら要件をもう一度明確にする** 必要
- B の場合、何でも対応可能に見えるが **全体性を見失う危険**。大きな変更はある程度の枠組みをきちんと定めた上で繰り返すのが現実的
- WF でもアジャイルでも、ビジネス要件レベルの修正が生じたら要件定義をきちんと再考した方が近道
- 逆に、要件定義は **後から遡って修正できるレベルで留めておかないと仕様変更は無理**。詳細議論に入り込みすぎると修正が難しくなる

## 2種の開発手法における要件定義

| | 要件定義で定義するレベル |
|---|---|
| WF型（反復型含む） | 機能レベル、あるいはプロセスの機能（概要）レベルまで。プロジェクトにより業務プロセス定義、機能の仕様確定まで |
| アジャイル型 | 作業は基本的に同じだが、「アジャイルは新しい価値を生み出すプロセスで要件は固まらない」前提。それでも **最低限の要件（方向性と制約）の明確化** は必要。機能分割可能な状態まで持っていく。まず方向性、その上で真の要求はアジャイルで設計と共に行う |

開発手法により要件定義の「粒度」は異なるが基本的に相違はない。**システム開発の目的・方向性を明確にし、機能を想定可能とする状態** にすること。

## リポジトリ

- リポジトリ ＝ 開発プロジェクトの関連情報を集約するデータベース。活用できる環境なら積極的に使う。影響度分析が容易になり生産性が大きく上がる
- 使わない場合でも **成果物同士の関連は把握可能にしておく**。WF では「どこを直した時にどこも直さなければならないか」の影響度を明確にしておくと手戻りを極端に恐れる必要がなくなる。アジャイルでも各繰り返しの修正が全体にどう影響するかが明確になり、整合性確保と品質向上に繋がる

## 工程の考え方（アジャイルの場合）

1. ある程度の前準備は行うが、いきなり繰り返しに入るパターン
2. **要件定義の前半部分（概要）をきちんと行った上で、詳細の要件定義 → 設計 → 実装を繰り返す** パターン ← **本書はこちらを推奨**

## 要件定義と基本設計の工程

- 一般に「要件定義」と「基本設計」は別工程。分ける理由は工程終了時点での見積りが必要なため
- しかし分けると確実にコストが上がる。主因は **コミュニケーションコスト**：工程ごとに違う人間が担当し、設計工程での要件確認、用語・ルール確認、項目仕様等で高レベルのコミュニケーションが必要になり、作業重複が生じる
- 実際には **一気通貫で要件定義と基本設計を続けて行った方が効率は抜群に良い**。問題はその時点で求められる見積りレベル次第。プロジェクト全体のためにどちらが最善か、検討の余地あり
