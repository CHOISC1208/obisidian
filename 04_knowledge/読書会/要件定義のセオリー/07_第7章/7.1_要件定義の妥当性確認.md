# 7.1 要件定義の妥当性確認

← [[6.3_アプリケーションアーキテクチャの明確化]] | → [[7.2_要件定義の合意形成]]

要件定義で明確化した機能要件・非機能要件・2つのアーキテクチャの妥当性を確認する。ユーザーから引き出した要求を要件としてまとめ、実装予定の機能の妥当性を判断する。**実装しない機能を明確にすること** も目的の一つ。

## システム要件の妥当性確認

- 要件の合意を得るために、要件定義で作成した成果物が「システム化の目的」「コスト・納期」を踏まえつつ **顧客（ユーザー）の意図を正しく反映しているか** を確認
- 併せて認識を共有すべきもの：「要求として抽出されたが実装対象外（システム要件対象外）となった機能」「要件の変更管理方法」「要件定義の制約条件と前提条件」「未決事項」（変更管理方法・制約条件と前提条件は本書では言及なし。プロジェクト状況に応じて方針決定）

## 要求の妥当性

- 本来は「要求分析」で行う作業だが、要件定義でも確認の意味を込めて整理
- ビジネス要求 → 業務要求へブレイクダウンされた要求の妥当性、ビジネス要求・業務要求 → システム要求へブレイクダウンされた要求の妥当性を確認（要求階層の各矢印の妥当性）。併せて **①元 ToBe モデルと要求との整合性** を確認

## 要求から要件への妥当性

- ビジネス／業務／システム要求からビジネス／業務／システム要件として整理された各要件の妥当性を確認。**要求として現出したが要件化されなかった事項（＝先送り事項）を明確にする** 目的も兼ねる
- 例：ビジネス要求から業務要件にブレイクダウンせずビジネス要件に移行した要件 ＝「新ビジネス立ち上げ」「組織・人事」「マーケティング戦略」等、部門レベルでは解決できないトップダウンの意図を反映したもの

## 要件の妥当性

- ビジネス要件 → 業務要件へブレイクダウンされた要件の妥当性、業務要件 → システム要件へブレイクダウンされた要件の妥当性を確認
- **ブレイクダウンされなかった要件を明確にする**：
  - ビジネス要件 →「新組織設立」「IT 以外のビジネスプラン」「人事」
  - 業務要件 →「IT 以外のマーケティングプラン」「新業務フローの確立」等
  - システム要件 → 今回の開発プロジェクトで開発対象のシステム機能
- 確認作業を改めて **経営資源（人・モノ・金・時間）** と突き合わせた上で妥当性を判断。併せて **③新 ToBe モデルと要件との整合性** を確認

## 成果物の確認

要件定義の作業を通じて作成された成果物：
1. 要求・要件トレース図
2. システム全体図
3. 概念／論理データモデル（ER 図・用語集・データ項目辞書）
4. ビジネスルール集（要件定義レベル）
5. ToBe 業務フロー及びプロセス定義（プロセスモデル）
6. UI 定義（プロトタイプ）／画面遷移図
7. 上記①〜⑥を含む機能要件定義書
8. 非機能要件定義書
9. アーキテクチャ要件定義書

妥当性確認のイメージ：**要求・要件トレース → 機能要件／非機能要件 → アーキテクチャ**。確認された「システム要件」に基づき機能／非機能要件が適切に定義されているか、さらに機能／非機能要件を満たすアーキテクチャの方向性が合っているかを確認。⑤⑥は併せて「業務要件」を満たすプロセスになっているかを確認。

## 「未決事項」の取り扱い

- 時間的制約でどうしても「未決」のまま要件定義を終えざるを得ない場合がある。方向性が定まらないまま終えるのは問題だが、いくらでも時間をかけてよいはずもない。リソース（人・モノ・金・時間）及び技術的制約を無視して成立するプロジェクトはない
- 時間切れの場合、次工程（設計工程）以降、つまり要件定義の後で「何をどうするのか」を決める。何らかの解決策を講じる
- 「未決」事項はシステム要件として整理された今回の開発対象機能の一部。未決のまま置かれたことで開発が滞った場合に **業務要件・ビジネス要件へどのような影響が及ぶか** をしっかり把握しておく
- 次工程以降で解決したら、その結果を「要件定義」の成果物に **フィードバック** できなければならない。そのための次工程以降の「バッファ」をどう確保するか、要件定義段階できちんと検討
