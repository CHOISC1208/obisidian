# 2.1 抜けのない要件定義を目指す

← [[要件定義のセオリー_MOC]] | → [[2.2_UXを整理しよう]]

## 最新の要件定義で留意すべき5つのポイント

今日の IT アーキテクチャは多様化している。要件定義で頭の片隅に置くべきキーワード：
1. クラウド
2. UX
3. アジャイル
4. BABOK
5. **データマネジメント**（著者が特に重視）

（昨今なら IoT・AI も加えるべきかもしれない）

## データマネジメントの重要性

- DMBOK（Data Management Body of Knowledge, DAMA インターナショナル編纂）の定義：データと情報資産の価値を獲得し、統制し、保護し、提供し、向上させるためのポリシー・実践・プロジェクトについて計画を立てて実行すること
- 品質の高いデータなしに成果をあげる企業は存在しない。組織のデータ依存度が高まる中で、データ資産のビジネス的価値の認知度は一層高まる
- データマネジメントは開発プロジェクト単位でなく **企業組織単位** で行うべきだが、個々のプロジェクトでも意識しておかないと運用に悪影響
- **情報 ＝ データに意味付けしたもの**。情報システムの価値はそこで生み出されるデータの価値で決まる → データマネジメントの実施が情報システムの価値を高める。要件定義段階から、最適なデータを生成・参照できる環境構築を意識する
- 特に重要なのは **データガバナンス**：データの標準化を徹底して統制を図ること。データ品質向上・セキュリティ・データインフラ整備などデータマネジメント全体の管理体制を構築し、計画・監視・執行する役割
- データモデルは「データガバナンスを効かせ続けられるシステム」を支えるものでなければならない。新規開発では強く意識し、修正案件でも可能な限り意識する

## 情報システムの使命

> 適切な時に、適切な人が（場所で）、適切な（品質の）情報を input することにより、必要な時に、必要な人（場所）へ、必要な（品質の）情報を output する

この使命を実現するには、システム開発において **アーキテクチャを定義し、その基盤の上で「データ」と「業務プロセス・機能」、そしてその交差点をきちんと管理する** 必要がある。

- アーキテクチャの重要性は今後も高まる。データとプロセスの重要性は永久に不変
- **盤石なデータ基盤の上にプロセスを定義** → データを更新するプロセスの品質が必然的に高まり、支援するアプリケーションもシンプルで保守性が高い。データとプロセスが両輪のように互いを支え、双方の品質を高め保つ
- **データ基盤がめちゃくちゃなままプロセスを定義** → プロセスは複雑なばかりで品質を担保できず、アプリケーションも複雑怪奇に。データもプロセスも品質を保証できない
- 開発現場は「プロセス」と「機能」の議論に終始しがちだが、**「データ」の本質を早期に捉え、要件定義段階からきちんと検討する** のがセオリー。データの方向性を早期に明確にし、更新するプロセスの方向性を早期に明確にすることで、品質の高いシステムができる。データ要件は要件定義の中で重要性を増していく

## 要件定義から整合性を検証する

- 要求同士・要件同士の整合性：各要求 → 要求、要求 → 要件、各要件 → 要件の各工程で整合性がとれているかがポイント
- 最終的には **ビジネス要求・業務要求・システム要求とシステム要件の整合性** がとれていることが条件
- 要件定義でこれらを可能にする方向性を明確にすることで、大きな手戻りを防げる

## Column：ソフトウエアの特性（要旨）

- ソフトウエアは建物と異なり **極めて柔軟性が高い**。この特性を活かして計画・実行すれば、変わり続けるマーケットに最良の対応ができる
- 柔軟性を機能に反映できなければ「50%以上のソフトウエアが使われていない／意図したビジネス目標に応えていない」という調査結果のような悲しい結果になる
- 要件定義段階で「ビジネス目標に応えるソフトウエア」が明白にならない場合も多い。その場合は **「ビジネス目標と一致した」「筋の通った」シンプルな機能を定義** しておく
- UI・機能もソフトウエアの一形態であり、この特性を常に頭に入れておく
