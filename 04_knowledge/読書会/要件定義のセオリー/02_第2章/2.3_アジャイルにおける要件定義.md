# 2.3 アジャイルにおける「要件定義」

← [[2.2_UXを整理しよう]] | ↑ [[要件定義のセオリー_MOC]]

## アジャイル型開発における要件定義（著者の私見）

- 結論：**WF でもアジャイルでも、要件定義で行うべき作業は基本的に変わらない**。作業内容を決めるのは開発手法ではなくプロジェクトの考え方や状況
- 「アジャイルでは設計しない」は間違い。ドキュメント作成を目的としないだけで設計は行う。要件定義も同様。ただし個々の詳細仕様まで要件として明確化するのはアジャイルの精神に反する。それでも **方向性・目的・概要は早期に明確にする**。どんな手法でも不変。アジャイルでは要件定義〜テストを同じメンバーが担当することが多いので、引き継ぎドキュメントが不要なだけ
- 特にエンタープライズ系との融合を前提とする場合、方向性・目的・概要までを要件定義フェーズで捉え、要件の詳細化・設計・製造をアジャイルで実施するのがよい。**機能分割可能なレベルに落とし込む作業は前もって行う**
- 最初から何でもアジャイルでやろうとするとプロジェクトが収束しなくなる恐れ。スクラムでもスプリント単位の機能分割に誤りがあると破綻する。匠の技を持つ技術者を多数確保できれば別だが現実には難しい。エンタープライズ系への影響や他システム連携を全く考慮しないで済む場合を除き、要件定義でやるべきことを押さえておくことが成功に繋がる
- **枠組みを決めるところまでは、開発手法によらず要件定義をきちんと行う** ことを推奨。方向性・目的・概要を明確にする成果物：概念データモデル、ToBe 業務フロー、業務プロセスの 5W2H に基づいて機能洗い出し用に作成したユーザーシナリオ
- ユーザーと合意するための要件定義書（モデル）は作成必須。レベルはアプリケーションの複雑度に依存（数分の画面操作で要件通り確認できるアプリもあれば、金融の勘定系のように複雑なビジネスルールが要件となるアプリもある）

## 計画は要件定義にて

- アジャイルは「反復（イテレーション）」という短い開発期間の単位でビジネス要求の変化に対応しリスクを最小化。1回のイテレーションは通常週単位、規定された作業時間の単位を **タイムボックス** と呼び、リリースまでの期間を最初に定め絶対に変更しない。XP では「イテレーション」、スクラムでは「スプリント」
- その中で設計・開発・テスト・リリースまで行う。各イテレーションの開発範囲と順番がポイント → **要件定義はこの前に終えて「大枠」を掴んでおく** 必要
- スクラム：スプリント ＝「完成」した利用可能でリリース判断可能なプロダクトインクリメントを作るための1か月以下のタイムボックス。作業はスプリントプランニングで計画。この計画は、要件定義で概要を明確化し **機能をスプリント単位に分割可能にした上で** 行う方がよい

## 要件定義で行った方が良い作業

- 「大きな枠組」＝ 基盤となるアーキテクチャの上で「データ」「プロセス」「機能」を明確化すること。細かい機能議論は後回しで構わない。大枠を捉えて機能を想定し、一旦確定した後に機能分割を行う
- そこから先、以下の作業を要件定義の範囲で行うことを考えてもよい（ここが WF との相違点）：

### インセプションデッキの作成
- プロジェクトを始める前に明らかにしておくべきことを知るための活動。「このプロジェクトは何なのか」を共有するため、テンプレート10個の項目を埋める
- 特に **「技術的な解決策の概要」** ではアプリケーションアーキテクチャを決定する必要がある

### プロダクトバックログの作成
- 要件を落とし込んだ一覧表。実現したいことをすべて書き出す
- リリース時期、どこまで行けそうか、何が終わったか、今どこまで進んでいるかを管理。未着手の作業を整理して優先順位を決める
- **スプリントバックログ** も作成（スプリント ＝ スクラムの開発・レビュー・調整の単位）。初期段階でバックログの体裁を整えるのが要件定義の作業
- システムの方向性・目的・概要を明確にした上で、**アーキテクチャの方向性、機能概要から分割方針まで** を要件定義で行う

## アジャイルで行うべきこと

- 「開発した機能の6割は使われない」「WF で開発したシステムは完成時に既に要求と乖離」とよく言われる
- **YAGNI**（You aren't gonna need it：必要になるまで追加しない）の精神。今必要なものだけを実装する。不必要なものを作ることこそ無駄
- 本当に必要なものは大きな枠組みの中にある。木の幹はしっかり根付かせ、その上で俊敏性を発揮できる状況に持っていく。本当に必要なものが分かるのは、**大きな括りの中できちんとした方向性をプロジェクトで共有したとき**

## アジャイルだろうと「要件定義」は必要

- アジャイルでも要件定義の重要性は変わらない、必要というスタンス
- 「要件は固まらない」「真の要求はアジャイルで設計とともに」とはいえ、**最低限の要件（方向性・制約）の明確化** は必要
- Web が絡む日進月歩のエリアでは要件の変化は受け入れざるを得ない。動いているシステムを見ながらなら具体的なイメージで要件を提示できる可能性が大きく、ある程度仕様が固まった時点で開発開始は可能。そのために **繰り返しの前に要件定義で大枠を掴み、設計から実装でブレを生じさせない** ことが大切
- 新規開発でアジャイルを適用した場合、修正（仕様変更）もアジャイルで行うことになる → **システムライフサイクル全般でアジャイルである必要**。開発手法の話に終わらず、長期にわたる **組織論** に踏み込む必要が生じる
