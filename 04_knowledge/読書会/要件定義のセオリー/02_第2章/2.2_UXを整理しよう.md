# 2.2 UX を整理しよう！

← [[2.1_抜けのない要件定義を目指す]] | → [[2.3_アジャイルにおける要件定義]]

## UX の観点

- UX（ユーザーエクスペリエンス）は UI より広い概念で、ユーザーの体験や満足といった全体を意識すること
- システム開発の立場からは、**「情報システムを含むサービス（製品）が、どのようにふるまい、動作し、人と触れ合うか」を明確にする** こと
- サービスの価値 ＝ ビジネスの価値。特にコンシューマー向けシステムでは UX の価値 ＝ システムの価値と見なされる機会が増えた（「楽しさ」「心地よさ」がシステム価値を左右する）
- エンタープライズ系はエンドユーザーの想定がつきやすいためコンシューマー向けほどではないが、業務担当者の置かれた状況を考慮した **ユーザーシナリオ** の分析は重要性を増している。両者の融合により UX は無視できなくなった
- システム形態に関わらず、上流工程で UX を意識する必要が高まっている。要件定義で開発対象システムを UX の観点から見直すことで方向性が明確になる
- 極論：**UX からユーザーシナリオ（プロセス）を抽出し、データとの整合性がとれる仕組み** こそ、ユーザーにとって納得性が高い（合意しやすい）システム。それを実現する開発者とユーザーが並走できる体制・工程が求められる

## UX の観点から要件定義でやっておくべきこと

- UX は「モノ」ではなく「コト」のデザイン。UI・ユーザビリティを含む広い概念
- UX を意識する ＝ いきなり UI の話をすることではない。**UX を想定 → ユーザーシナリオを導出 → UI を想定**。決して逆ではない
- UX はシステム利用中だけでなく **利用前・利用後** も含む（利用時間全体UX）。むしろシステムは体験のほんの一部
  - EC なら購入前・購入後の UX を考慮して UI に落とし込む → 後述の「ペルソナ」をきちんと作成して検討
  - エンタープライズ系でも業務従事者がシステム使用前後にどんな行為を行うかを考慮
- UX を基に業務フローを考える場合、例えば「注文」なら注文前・注文後まで考え、必要な業務プロセスをあぶり出すのがセオリー
- 要件定義ではいきなり UI 検討に入らず先に UX を考え抜く。業務フローもシステム使用前後を包括する。これは **UX を実現するプロセスモデル（業務フロー）→ プロセス定義（5W2H）→ 5W2H を満たす機能と UI** を得ることと同義

## ペルソナ

- サービスを利用する典型的ユーザーの人物像を具体的に描き表したもの
- コンシューマー向け開発では厳密に作成し UX を想定した方がよい。できるだけ事実に基づいた情報を基に、想定ユーザーの顔が想像できるレベルまで、共有できるレベルまでキャラクターを掘り下げる
- エンタープライズ系で想定ユーザーが限定され「顔」が分かっているなら作成不要。ただし実際に操作するユーザーのイメージはきちんと把握しておく
- いずれの場合もお客様・ユーザーの「顔」を明確にして、**データ・プロセス・機能・UI の各要件に反映** する
- その「顔」が操作する UI が UX にどう影響するかを考慮すると、ユーザビリティを含む非機能要件、UI におけるデータ操作、プロセス定義が明確になる。要件定義 ＝ 方向性と範囲の明確化であり、UX を意識するとより明確になる

## カスタマージャーニーマップ

- カスタマージャーニー ＝ ユーザーの体験全体
- コンシューマー向けでは、体験全体を可視化するため **ユーザーシナリオとしてカスタマージャーニーマップ** を作成すると理解が深まる
- 後述の画面遷移と併せて、要件定義段階で **ラフな** カスタマージャーニーマップを作り、UX をシステムに落とし込んで要件確定に役立てる
- ペルソナがどう動くか想定し時系列に並べて作成。「こんな風に動いてほしい」というユーザーの思いが分かれば OK

## 要件定義における UX の重要性

**UX → ユーザーシナリオの大枠 → 業務フロー（業務プロセスの固まり）→ 個々の業務プロセスを抽出 → 業務プロセスに必要な UI・機能を洗い出す**

UX を明確にすることで、必要な UI・機能が明確になる。

## UX を基にした UI の実現

- 要件定義後、設計・実装時にペルソナを想定し快適に操作できる UI を作成。**7割完成時点で実装** を目標とし、リリース後にユーザーの実際の評価を基に完成品（10割）を仕上げる。最初から完璧を求めない
- 本書では UX 体験に基づいて必要な非機能／機能を洗い出すために、**UI の検討を要件定義段階で行う**
