# 4.4 業務プロセス要件の明確化

← [[4.3_業務フローの明確化]] | → [[4.5_UI・機能要件の明確化]]

## 改めて「業務プロセスとは？」

- 業務プロセス ＝ **経営の目的を達成するための活動**（ビジネスプロセスと同義）。一連の仕事・行為の単位。何らかの **入力** を元に何らかの **出力（成果）** を行う（成果は全く別のものの場合も、同じものの状態遷移の場合もある）。各プロセスには **オーナー** がいる
- 「検討する」のように成果を測定できない行為は本来プロセスではない（ダラダラ何も決まらない会議は成果を伴わないのでプロセスではない）
- 見直しをせずに業務プロセスを IT 化した場合、効果は「自動化」による効率化のみ。これからは **「デジタル化」** が求められる。業務プロセスの見直しをきちんと行い、デジタル化に対応可能な価値あるプロセスにする
- 目指すレベルによっては標準化を行い、システム要件以外の要件（導入前教育、人事的処置等）が必要になることもある

## アイコン

わかりやすい業務フローのため、開発者もユーザーも直感的に把握できるアイコンを推奨（「〜を入力する」＝PC に向かう人、「〜を運ぶ」＝モノを運ぶ人、「資料作成」「電話応対」など）。フリー素材でよい。

## ビジネスルール

- 業務フロー図を描いていくと様々なビジネスルールが浮かび上がる（逆にビジネスルールに基づいた業務プロセスを表すように描かなくてはならない）。ここで浮かび上がるビジネスルール ＝ **「ビジネスの動的なルール」**
- 判明した時点で明白な事実を書き出す。最初は題名とメモ書きだけでもよい。何らかの「決めごと」により描かれたフローであることを明確にしておく
- ビジネスルールの集まりはプロセスモデルの精度を高め、ビジネス／業務／システム要件を網羅するものになる
- 抽出したルールは **「ビジネスルール集」** にまとめる。業務フロー図上にも該当ルールで固まった旨を題名だけでも記述（全て書くとごちゃごちゃするので適度に）

## 改めて業務フローを階層化

- 業務フロー図は **階層化して作成・管理**。経営方針＝ビジネス要件から業務要件に落とし込む際、最上層でビジネスモデルとの整合性とともに **経営トップの「思い」** を表現
- 階層はビジネス要件と業務要件に基づいてブレイクダウン。最上層のフローは **プロセス関連図** に近くなる
- トップダウンの「思い」が最下層のプロセス定義に引き継がれるよう心掛ける。上層フローはシステム要件以外のビジネス要件・業務要件をより強く満たすフロー → システム稼働日までにビジネス要件・業務要件を満たす形（組織・人員・インフラ等リソースの再配置）にならなければシステムは稼働しない
- プロセスモデルには、システムが稼働するためのビジネス要件・業務要件も **制約として記述**。ビジネスルールになることもある。これによりシステム開発以外の「覚悟」を企業組織に突き付ける

## 業務プロセスとしての業務フロー

- 要件と業務フロー階層：「ビジネス要件」→「業務要件」→「システム要件」（トップダウン ⇄ ボトムアップ）。上層は「業務プロセス＝業務フローとして定義」、**最下層の業務プロセスは行為として定義**
- トップダウンとボトムアップの両方から業務プロセスをあぶり出して業務の流れを確立。**トップダウンモデリングを基本** としつつボトムアップモデリングで業務プロセスを明確化。ToBe を基に AsIs を踏まえ新 ToBe フローを作成することでプロセスモデルの価値が増大。きちんとした ToBe 業務フローは企業組織の貴重な財産となり、以後立派な AsIs 業務フローとして活用できる
- **現場の問題点・課題を解決するためだけに業務を整理した業務フローを最初から作ってはいけない**。トップダウンで枠組み、ボトムアップで肉付けが大前提。トップダウンで見直すと現場が問題と認識しているプロセス自体が不要になることもある。現場の力は大きく大切だが引っ張られすぎてはいけない。小手先の解決は労力ばかりで結果が出ない

## パッケージ使用時の業務フロー

パッケージ導入時は、パッケージの UI・マニュアルを基に業務フローを作成。AsIs とのフィット＆ギャップではなく **ToBe を作り上げていく姿勢**。パッケージの仕様に「業務プロセスを寄せていく」努力が必要（ToBe 業務フロー → 寄せていく → パッケージのシステムフロー）。

## 業務フローの位置づけ

ToBe 業務フローはビジネス要件を基にした業務要件を満たし、システム要件を反映。ビジネス要件の度合いが強い「プロセスの固まり（大）」→ 業務要件の度合いが強い「プロセスの固まり・プロセス」→ システム要件を満たす「プロセス・機能」の定義、仕様まで落とし込む。

## 現場の人間を惹き込む：ストーリーテリング

- プロセスモデルとしての業務フローは **現場の人間の視点** で業務を表現し共有する。**物語の世界に現場の人間を惹き込む（ストーリー性が必要）**
- 業務フローの作成者（開発者）は **「ストーリーテラー」** である必要。ユーザー（現場）との間でコミュニティの物語を共有する
- 具体的手法：業務の流れを表す線を開発者が **赤ペンでなぞって**、フローの一つ一つの線をユーザーとともに確認・確定。現場ユーザーを主人公とする業務の物語を作り上げる。理想は **登場人物達が自主的に動き出す** ところまで
- ある程度巻き込んだら、ストーリーラインからそれないよう注意するだけで物語は動き出す。注意点2つ：
  1. **ストーリーの結末をきちんと決めておく**（脱線事故を防ぐ）。最後にハッピーエンディングを用意する気持ち。業務の順番どおりに描く必要はなく、エンディングを先に決めて遡る形でストーリーを確立してもよい
  2. **シーン（エピソード〜プロセス）ごとの主人公と、フロー全体の主人公（プロセスの固まり・フロー単位のオーナー）、登場人物（プロセスオーナーまたはユーザー）を明確に**
- 図の内容に引き込むコツ：①これからチェックする業務の前提を伝える（詳細な状況設定で新業務フローのイメージを具体的に持ってもらい、仕様漏れが見つかりやすくなる。物語の背景を伝えた上で物語に入る）②業務の流れを示す矢印を **鉛筆やペンで辿りながら** 話す（順を追って説明することで利用部門の担当者が具体的にイメージし仕様漏れを指摘しやすくなる）
- このテクニックはデータ要件の明確化でデータ項目漏れをチェックする場面でも活きる。フローに惹き込んだ上で別途準備した画面イメージを提示し「この場面でシステムに入力できないと困る機能・データ項目はないか」を確認 → 「XXX 画面では XXX のデータ項目が必要だ」という指摘が得られ、業務プロセスとともにデータ要件・UI・機能要件を明確にできる

## UX と業務プロセス

- UX から、ユーザーシナリオの大枠（使用前後の体験含む概要業務フロー）、業務フロー、業務プロセス、使用する UI が明確になる。ユーザーシナリオから業務プロセスの前後を含めた大きな範囲の業務フローを導き出し、**ペルソナを動かしてみる** ことで業務プロセスと支援する機能・UI が浮かび上がる
- 該当業務フロー以前・以後の体験：（前）気づき →（—業務プロセス—）→（後）感動。前後の間を取り持つ業務プロセスはどうあるべきかを想像し策定
- コンシューマー向けでは、開発対象外のプロモーション（プッシュメール・SNS キャンペーン等）を要する場合、それも業務フロー（プロセスの連なり）の一つ（業務プロセス）として表現。気づき（プロモーション）から IT システムを使用する業務プロセス・UI を想定しユーザーシナリオ抽出につなげる
- 使用前後を含む UX を実現するために必要な業務フローを明確にし、その中で有効な業務プロセスの定義（5W2H）を行い、5W2H を満たす機能と UI の定義につなげる

## 5W2H の定義

業務フロー上に現れる業務プロセスの定義 ＝ 以下の 5W2H を定義すること：

| 項目 | 内容 |
|---|---|
| **When** | いつ → 実施タイミング（事前／開始条件含む） |
| **Where** | どこで → 場所、組織 |
| **Who** | 誰が → 担当者、ユーザー |
| **What** | 何を → 対象データ |
| **Why** | 何のために → 目的、狙い。当該プロセス完了時点で達成される目的と **事後条件**（プロセス完了時に達成できていること。例：受注データが記録されたことにより「顧客と合意した契約内容が記録されたこと」） |
| **How** | どのようにして → 実施要領（制約条件含む）。ユースケース記述まで書くのが望ましいが、シナリオ（手順）までは最低でも把握可能なレベルで記述 |
| **How many** | どれくらい → データ量、時間（How Much／How Long と表す場合もあるが本書では How＝実施要領、How many＝量・時間） |

- 観点を変えると業務プロセスは3つの条件を持つ（5W2H の中で定義）：**開始条件**（タイミング・トリガー）／**制約条件**（例：お客様が登録するならば、伝票にミスがなければ）／**前提条件**（例：プロセス開始時に必要なインプットが終わっている）
- 業務プロセスは **成果を評価する単位** にもなる（手作業か否か問わずプロセス品質の評価）。KPI の測定はプロセスの固まり（連鎖）により可能
- 5W2H をうまく定義できない・明確でない業務プロセスは、**本当に必要なものかどうかを疑う**

## 業務プロセスの統合と分割

- 各プロセスの 5W2H が一旦終了したら Excel 等の一覧表で出力。同じような 5W2H を持つプロセスが複数あったり、強引にまとめたが別々にした方がよいプロセスが見つかる
- 熟考すべき時。システム標準化の観点からはできるだけ統合・標準化が望ましいが、業務の観点から適切かを充分議論した上で決定。**ビジネス要件・システム要件の観点からは統合を推進、業務要件の観点からは熟考を要する**（現場の強みに繋がり、企業組織の存在価値を左右しかねない）。業務要件から遡りビジネス要件を再考する必要に迫られることもある
- 明らかに同一業務を複数の場所・組織で行っている場合は複数の定義を認めることにより同一プロセスとみなせる。「どこまでを1つの業務プロセスとみなすか」は開発者・ユーザー含め皆で議論し決定。5W2H 定義方法の **お手本** を作り皆で真似る
- 統合・分割を行ったら、新規登録や正しい 5W2H 定義の後、業務フロー図に反映
- 何らかの理由でプロセスがブレそうな場合は **「5W2H に戻る！」** これしかない。該当プロセスの 5W2H を基に UI がデザインされ機能が定義されているか、逸脱しているかを確認し、違和感が生じたら別プロセスへの分割を検討

## 5W2H を固めるためのプロトタイプ

- 5W2H がなかなか固まらない場合は簡単なプロトタイプを作成し、画面イメージを基に議論して詳細を詰める。ラフデザインを手書きで作成するレベルで構わない。想定しうる 5W2H を満たすプロトタイプを開発者が作成しユーザーに確認 → フィードバックして修正
- **UI を固めることを目的とせず、5W2H の確定に終始**。画面イメージで議論すれば「主人公」「登場人物」達が活動するために必要なプロセスが具体的に浮かび上がる
- プロセス定義と業務フローの整合性の留意点：
  1. プロセス単体では品質が高くても、プロセスの固まりを基にした業務フローレベルで品質が落ちる場合がある（全体最適の視点欠如）。プロセスオーナーが納得する落とし所を見つけプロセス単体を見直す。「いいパスを出しても受けきれない」場合もある
  2. プロセス単体に問題があることが明白なら、オーナーに事実を認識してもらいプロセス自体の改善を即刻行う

## 自ら動いて仕様を固める

- できるだけ早い段階で仕様を決めるよう開発者（チーム）側から積極的に働きかける。「早く決めてください」と口だけ言っても「まだ調査中」「部門間調整が必要」といった返事しか返ってこない（分岐・合流の有無を確認しても曖昧な答えしか得られないことがあった）
- 「この業務フローの分岐の有無が分かる人は誰ですか？」と尋ね、**食い下がる覚悟** で固める。詳細を知る人・決められる人を突き止めて確認できなければ仕様が漏れたまま設計が進む。上司・同僚か別部門か聞き出したら **自ら確認に動く**。待っていても事態は好転しない。**「主体性を持って動く」** がセオリー
- 開発者は「ユーザーが現場の強みを生かすこと」「管理業務の負担を大きく下げるというさらなる価値を生むこと」が企業組織にとって重要であることを常に意識
- 以上を踏まえ ToBe 業務フロー図を作成。「ToBe」はあるべき姿を示すと同時に新システムの **稼働時のイメージ**。業務処理内容の違いをアイコンで表し、前後関係・時系列に沿って並べ、線で結んで数珠繋ぎにすることで一連の業務の流れを表す
- 「最小の労力で最大の効果」。管理すべき情報が少ないほど情報の品質を容易に保てる。「当たり前のことをやれば、きちんと成果を出せる」仕事環境が理想

## 手順：「ToBe 業務フロー図」の作成

1. **全体を鳥瞰可能なレベルの業務フロー図を作成する（トップダウンモデリング）**：RFP・規定・ビジネスルール・新システム全体図・要件定義書・AsIs 現行業務フロー図（あれば）を基に全体の大まかな流れを描く。ToBe プロセスモデルがあれば要求と要件の差異を意識しつつ修正。印刷時に1枚の紙（A3 横）またはプロジェクター1画面に収まる全体図が理想。システム全体図で想定した「サブシステムとなりうる業務領域」を1つのアイコンとみなし、前後関係が明白になるよう矢印でつなぐ。ラフでよく、とにかく全体を捉える
2. **全体図の各アイコンを1枚の業務フロー図に分解（トップダウンモデリング）**：全体図の各アイコン（独立サブシステムとなる業務領域のまとまり）を1枚（1ページ）の業務フロー図へ細分化。個々の業務領域の中身を分析し、より小さな複数の業務プロセスの流れ（手順）として整理。全体図のアイコンの数だけ2階層目のフローができる。コンシューマー向けで業務領域がある程度定まったシステムではトップダウンモデリングの必要性は低い → 最下層の業務フローを作成
3. **業務フロー図をさらに細分化する**：もう1階層下を描く。同じ階層の図同士でアイコンの粒度（意味する範囲・大きさ・抽象度）を揃える。3階層目以降は **お手本フロー** を作成し皆で合わせる。何枚もの図同士で業務領域の幅の厳密な整合性はとれていなくてもよい（漏れは困るが少々の重複は構わない。迷ったら大き目の業務領域で作成）。階層間のフロー同士の関係が明確で、同じ階層の図同士の視点の高さが明らかに食い違っていないレベルを目指す
4. **業務プロセスに命名する**：全階層のアイコンが表す業務プロセスに命名。最下層以外は業務領域をブレイクダウンしたもの → 動詞句ではなく **名詞**（「在庫」「営業」または「在庫プロセス」「営業プロセス」）。最下層は最も細かい単位 → **「〜する」動詞句**（「受注する」「登録する」）。これにより最下層とそれ以外を明白に区別
5. **外部／内部インターフェースの定義を行う**：主要な外部インターフェースと業務間（内部）インターフェースを明確化。他社・社内の他システムとの間、Step 2・3 のフロー図の業務同士の連携を記載し業務の流れの中で整理。システム全体図を参照し整合性を確保
6. **フローの詳細化（トップダウンとボトムアップ）**：業務フローをブレイクダウンして最下層のプロセスを表すまで階層化。上位フローのアイコン一つ一つを下位フローへ展開（上位の目的を果たすために下位が手段として存在するように）。大規模案件でも **5階層くらい** で最下層に辿り着くようにすると見やすい。ビジネスの階層構造に沿って上位から下位へ、目的から手段へ掘り下げるとスムーズ。厳密に上から下だけでなく、最下層のフロー図を描けるなら先に作成しグループ化して一つ上の階層を作成（下位フローを上位のアイコンとして表し、アイコンの集まりを1枚のフローにまとめる）。トップダウンとボトムアップを合わせて正当な階層化を伴う業務フローが完成。要求段階で作成した ToBe プロセスモデルはトップダウンが強くボトムアップの視点が弱いことが多いので見直し時は注意
7. **業務フローの定義**：階層化された ToBe 業務フロー図に概要を定義。①業務の流れの説明、②業務フローの存在意義（業務プロセス定義と同様）。この工程のフロー図は後の開発工程・保守工程でも繰り返し参照される。後工程で業務の流れを変更しなければならなくなった場合、本工程の ToBe プロセスモデルにも理由を付けて反映
8. **スイムレーンを分ける**：適切にレーンを分け、個々の業務プロセス同士を矢印線で結ぶ。A3 横ならレーン見出しを左に配置し左から右へ、A4 縦なら見出しを上に配置し上から下へ
9. **外部データとの連携を詳細に記載する**：連携方法・連携方向・受け渡す情報や物・業務処理との関係をわかっている範囲で記述
10. **最下層の業務プロセスの 5W2H を定義する**
11. **各業務プロセスを統合または分割する**：定義した業務プロセスを一覧に書き出し（出力）、統合・分割を行い、結果を業務フローに反映

### 「トップダウンで骨組、ボトムアップで肉付け」の徹底
業務フロー図に限らずシステム開発全般で常に頭に入れておく言葉。プロセスモデルだけでなくデータモデル作成、仕様を固める際の基本原則。「現場の知恵」は有効だが、ボトムアップが強すぎると部分最適に引っ張られる。**ボトムアップによってトップダウンを潰すことは避ける**

### 実施作業の場合分け

| | 新規 | 修正 |
|---|---|---|
| エンタープライズ系 | ❶ | ❸ |
| コンシューマー向け | ❷ | ❹ |

- ❶ ToBe プロセスモデル → AsIs プロセスモデル → 新 ToBe プロセスモデルの流れをきちんと踏襲。ToBe がなければ要件（特に業務要件）を基に ToBe プロセスモデルとしての業務フローを作成
- ❷ 新ビジネス創出なら AsIs を意識せず **お客様視点** のプロセスモデルを作成
- ❸❹ ビジネス要件レベルなら ❶❷ と同じ流れ。業務要件レベルならプロセスモデルの見直し。**老朽化によるリプレース（置き換え）は要注意**：既存機能の焼き直しの場合フロー本流自体は変更がないため、プロセスモデルでは変更点の確認ができない場合がある
