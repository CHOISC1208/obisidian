# 4.1 要件の範囲の明確化

← [[要件定義のセオリー_MOC]] | → [[4.2_制約と外部接続の明確化]]

## 「要件の範囲」を明確にする！

- 要求はある制約を伴って「要件」として整理される。**どこまでを要件の範囲とすべきか** を明確にすることが要件定義の目的といってもよい
- 本項では要求を基に要件を明らかにし、要求がどう要件として整理されたかのトレースを行い、「要件の範囲」を明確化する
- 要件定義の目的 ＝ ①理想の ToBe と ②AsIs＋制約 を基に ③実現を目指す ToBe（新 ToBe モデル）を作成すること。③は稼働後に AsIs モデルになり、以後の修正はその AsIs を基に行う

## 第4章の進め方（反復とフィードバック）

```
4.1 要求→要件のトレース
 ↓
4.2 システム全体図の作成（＋新ToBeモデル概要）
 ↓
4.3 業務フローの明確化
 ↓
4.4 業務プロセス要件の明確化 ⇄ 4.5 UI・機能要件の明確化 ⇄ 4.6 データ要件の明確化
 ↓                                                    ↑
4.7 CRUDマトリクス分析 ──→ 4.4／4.5／4.6 へフィードバック ─┘
```

- 4.2〜4.5 で抽出された情報を基に 4.6 でデータ要件を明確化し、業務プロセス・UI・機能へフィードバック。さらに CRUD マトリクスを作成し、結果を各要件へフィードバック
- ここまでで新 ToBe のプロセスモデルとデータモデルを確定。モデルと各要件の整合性を再度精査し、要件自体を見直す。**この一連のサイクルを複数回繰り返す** ことで新 ToBe モデルを完成させ要件定義を確立
- 一度だけで何とかしようとしない。反復の中で開発者もユーザーも多くの気づきを得る。理論に裏付けされた経験の繰り返しに勝るものはない

## 「現行どおり」の危うさ

- ユーザーから「現行どおりに作ってくれ」（機能踏襲）と言われることがあるが、そのまま要件とすべきかは熟考を要する。プロジェクトオーナーであるトップの思いと異なることがある
- 「現行どおり」でも設計書がなければ現行仕様を一から調査する必要。仕様漏れ・設計漏れのリスク、現行機能どおりに作った機能が実は業務フロー上の問題点だった等のリスクも内在
- 経営トップはシステム投資に効果や付加価値を求めている。現場からの「現行機能の踏襲」（業務要求）をビジネス要求との整合性を図らずシステム要件にすると、システムの価値が評価されない事態を招く。インフラ老朽化などやむを得ない場合も、ビジネス継続の視点からビジネス要求として整理しトップの理解を得る
- 著者の立場：**機能踏襲が前提でも、何らかのプロセス・機能の見直しは行うべき**。プロセスの見直しはこのタイミングでしかできない。踏襲するとしても検討した上で行う。何も考えずに「現行どおり」は NG。基本機能を踏襲しつつ非機能・ユーザビリティ向上で価値を高める付加価値でも構わない

## 要求から要件へ

- ビジネス／業務／システム要求として浮かび上がった事項は全てが要件になるわけではない。優先順位の高いものを中心に「システム要件」の形に整理
- **「システム要件の形」＝ 開発対象システムの ToBe モデル**。元 ToBe モデルへの制約や AsIs を考慮して作り上げた新 ToBe モデルで、プロセスモデル・データモデル・機能・UI を想定できる要件

### 「要求」から「要件」への対応表
| 要求側 | 要件側 |
|---|---|
| 要求管理No. ／ 要求分類（ビ・業・シ）／ 内容 ／ 要件化可否（可・否） | 要件管理No. ／ 要件分類（ビ・業・シ）／ 内容 ／ 元要件管理No. |

- 無理に要件化せず、システムに求めるべきものの実現可能性を基に要件化。制約で要件化できなかった要求は **どの制約で不可だったかを明確に** する

### 代表的な7つの制約

| 制約 | 内容 |
|---|---|
| **人** | 素晴らしい方法論・ツールがあっても使いこなせる人がいなければ成り立たない。技術力・マネジメントの欠如も妨げ。新ビジネスの適材 |
| **物** | 設備、実装環境、インフラ、ツール。人が使うツールも重要な「物」 |
| **金** | 外注に限らず自社開発でも人員コスト。インフラ投資も非機能要件次第とはいえ最終的には金で決まる。投資効果は定量的に金額で判断されるため、**制約としてのウエイトが一番大きい** |
| **時間** | 納期がなければ多くの制約から解放されるが現実にはない。「時は金なり」 |
| **技術的困難** | ビジネスに大きなインパクトを持つが実現に技術的リスクを伴うもの |
| **技術的制約** | 「既存システムの一部を利用」「ERP 使用が決定」「クラウド使用が決定」等 |
| **現状との乖離** | 元 ToBe と AsIs の乖離が激しい場合、十分な検討が必要。経営判断でビジネス要件化する固い意志があれば別だが、現実的に可能か判断した上で要件化 |

### 要件化の流れの方向
- 新規開発：「ビジネス要件 ⇒ 業務要件 ⇒ システム要件」と基本的に一方向（稀に遡る）
- 修正案件：「業務要求 ⇒ 業務要件 ⇒ システム要件 ⇒ 業務要件 ⇒ ビジネス要件」「システム要求 ⇒ システム要件 ⇒ 業務要件 ⇒ ビジネス要件」のように起点が業務要求・システム要求になることが多い。この場合もビジネス要件との整合性をとる
- 代替案を立案する場合、要求から要件化する「⇒」のタイミングで、元々の要求を満たしているかを考慮して検討
- 新規開発でも **トップダウンが弱い** ために一方向に流してはいけない場合がある → 修正案件と同じ流れ（起点を業務要求・システム要求とし、吸い上げる形でビジネス要件との整合性を確保）
- 要件を固める過程でどんな分析・検討・意思決定が行われたかを振り返り、**トレース可能** にする。要件がプロジェクト全体の方向性と一致しているか常に確認可能な状態を作る。リポジトリがあれば容易、Excel 等なら要求・要件・機能・UI それぞれに **ID を振り出し相互に結びつける**
- 業務の複雑さに向き合う覚悟が必要。何でもシステム要件とせず、ビジネス要件・業務要件を検討した上でシステム要件を整理し、**業務プロセスやデータ構造をシンプルにする** ことを目指す

## 要求が曖昧？

- 要件定義段階で「そもそもの目的は？」「新業務イメージが湧いていない」「何がしたいのか漠然としている」という事態は、システム化企画・業務分析（第3章）が実施されていない状態。本来あるべき ToBe モデルは存在しない（あっても役に立たない）
- 現実は残酷。「本来そうあるべき」を蒸し返しても解決しない。前工程の作業が未消化なら、**要件定義工程で消化し、設計工程以降への悪影響を断ち切る** しかない。前工程の不備もすべて要件定義で吸収する
- 2パターン：
  1. ToBe モデルが存在する → AsIs と制約を踏まえ、ToBe から新 ToBe を作成して要件定義（第3章が実施済みの状態）
  2. 要求が曖昧で ToBe モデルがない → 要求を明確化しつつ ToBe モデルを作成して要件定義（第3章が未実施）
- いずれでも要件定義で最低限まとめ上げるもの：**要件としての合意を可能とするもの／設計工程のインプットとして有用なもの**。システム開発の失敗はほとんどここがうまくできなかったことに起因
- 要件定義からアサインされて前工程の成果物が曖昧・使い物にならないなら、**要件定義工程の期間延長を堂々と主張し WBS に反映** させる

### Column：上流からのやり直し経験（要旨）
要求分析が曖昧だったプロジェクトで、要件定義工程において上流からやり直した。期間は超過し全工程の半分近くを費やしたが、開発全体としては若干の遅れで品質の高いシステムが完成した。教訓：**上流工程を焦っていい加減に終わらせてはならない**。「形だけ」で終わらせるのが最悪。腰を落ち着けてきちんと終えることが成功への近道。

## 手順：「要求→要件」を明確にする

1. **要求階層の確認**：ビジネス／業務／システム要求の分類が正当か、各ブレイクダウンが正当か確認。ToBe モデルがあれば各要求を反映しているか確認。なければ 3.1 の方法で要求の明確化と階層化（ToBe 作成は時間的に難しいので要求明確化に専念）
2. **要求から要件へ**：ビジネス要求のうちビジネス要件へ、業務要求のうち業務要件へ、システム要求のうちシステム要件になりうる事項を確認し、対象になった事項に限り要件として整理。ToBe があれば AsIs を踏まえ新 ToBe 作成の準備。なければ要件化に注力し、要件から新 ToBe を作成する準備
3. **要件の整理**：各要件についてビジネス要件 → 業務要件 → システム要件へブレイクダウンしうる事項を抽出・整理。要求分析でブレイクダウンできなかった要求がスライドした要件が対象。システム要件へのブレイクダウンは注意を払う
4. **システム要件の確定**：システム要求から要件化した、または業務要件からブレイクダウンした項目を「システム要件」として定め、実現の対応方針を要件定義書にまとめる。要求をそのまま要件化せず、「一見実現性が薄い」「ビジネス上のインパクトが弱い」要求には **ビジネス価値を高める代替案** を想定して要件化。**ここが要件定義工程の「胆」**
5. **要件範囲の明確化**：整理されたシステム要件を基に対象となる機能／非機能を一覧化。その時点で分かる範囲で構わない。落とし込み方が未定なら「未決」とし、データモデル・プロセスモデル作成時まで放っておいてよい。新規開発はシステム全体のイメージと想定機能、修正（保守）は対象機能とシステム全体への影響を明らかに。この時点で **ビジネス要件を基にした新 ToBe ビジネスモデルを確定**

### 実施作業の場合分け

| | 新規 | 修正 |
|---|---|---|
| エンタープライズ系 | ❶ | ❸ |
| コンシューマー向け | ❷ | ❹ |

- ❶❷ 系統を問わず要求 → 要件へトレースできる環境作りが必要。コンシューマー向けはシステム要件までの落とし込みを時間をかけずに行い、「未決」になりそうな要件は後回しにして確定
- ❸❹ ビジネス要件・業務要件・システム要件各々の修正レベルに応じて対応
- ❹ でビジネスに大きな影響を与える場合を除き、業務要求・システム要求からシステム要件への移行・ブレイクダウンを迅速に行い、ビジネス要求との整合性を後回しにしても速やかに設計・実装すべき場合がある。与えられた状況で **どこまで正確な整合性を求めるか、迅速性を求めるか** を決める
