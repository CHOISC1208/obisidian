# 4.5 UI・機能要件の明確化

← [[4.4_業務プロセス要件の明確化]] | → [[4.6_データ要件の明確化]]

## UI と機能

業務プロセスの定義（5W2H）を実現するために必要な UI の概要を検討し、**画面 UI ラフデザインと画面遷移図** を作成。併行して UI を実現する機能も定義する。

- **機能は、業務プロセスを支援する（成立させる）ために存在する**
- **UI は、業務プロセスを支援する機能を成立させるために存在する**

## UI の基本形

UI の基本的な画面要素7点：検索／参照表示／選択／入力／実行（ボタンクリック）／結果表示／画面遷移（他画面へ）。この形を基に UI と画面遷移を要件化。

## 情報システムにおける UI の意味

企業情報システムで UI は「ユーザーに **円滑にデータ操作** を行ってもらう」ために存在。IT システムとユーザーの間を取り持つ。業務プロセスの 5W2H を実現するために円滑にデータ操作してもらえてはじめて UI は価値を持つ。

### UI におけるデータ操作 ＝ CRUD
生成（Create）／参照（Read／Refer）／更新（Update）／削除（Delete）の4種類。目的に沿ったこの4種のデータ操作を円滑に行うために必要な UI を考える。

## UI 確定のためのプロトタイプ

- 4.4 のプロセスモデル確定用プロトタイプを流用できればよいが、作成意図が異なる。ここでは **実装され実際に使われる UI** を想定する必要があり、必然的に詳細になる。データ操作をいかに円滑に行ってもらうかにフォーカス
- ある程度ユーザビリティに踏み込まざるを得ないが、それは別途詳細に行い（5.2）、ここでは UI が実現すべきデータ操作を明確にする
- 図：5W2H を満たすデータ操作の実現 → UI ← ユーザビリティ
- UI プロトタイプ作成時、**どのエンティティに対するデータ操作か** を明確にし、後述の CRUD マトリクス作成時に登録。可能ならどの属性（想定で構わない）に対するデータ操作かも明確に

## UI と機能

- 「UI は機能を実現するために存在する」→ **UI と機能は併行して定義すべき**。UI が固まることで機能が固まり、機能が固まることで UI が固まる
- 例外は **バッチ処理**：機能として業務プロセスを支援するが UI を持たない。4.4 で作成した ToBe 業務フローに業務上必要なバッチ処理が業務プロセスとして定義されているか確認。EC サイトのようにバッチが存在しないシステムでも、外部・内部のデータ連携・集計処理は要注意（基幹系連携があるなら特に）

## ユーザーシナリオ

- UX から大枠のユーザーシナリオ（体験前後を含む概要業務フロー）は抽出済み。ここではエンタープライズ系・コンシューマー向けを問わず、定義した業務プロセスから **詳細なユーザーシナリオ** を抽出（ユースケース記述でも可）。「一連の行為」である業務プロセスを基に実際に UI 操作レベルまで落とし込んだ手順を想定
- 特にユーザーシナリオの中で **データ操作に着目** し UI と機能を想定
- コンシューマー向けではお客様のペルソナが主人公のアクターとして登場。アクター ＝ 業務の役割（担当）、ペルソナ ＝ 実際に「顔」を持った登場人物。ペルソナがウキウキするストーリーを想定して UI を検討。ユーザビリティが差別化の大きなポイント
- 業務プロセス（5W2H）→ ユーザーシナリオ（複数のユースケース）を抽出。初期のユーザーシナリオから UI を意識したプロトタイプを作成し、シナリオの磨き上げを繰り返すことで UI が固まる
- 自然言語で記述したユーザーシナリオの例：ペルソナ（鈴木太郎）が比較検討していたプリンタを購入するため、12月23日に書斎のノートPCでサイトにアクセス、価格比較サイトで最安値を確認してカートへ、会員番号の入力ミスでエラー表示、正しく入力して確定処理、レコメンド表示された消耗品も購入——といった具体的な行動の記述
- シナリオで想起できるべき内容：
  - ユーザの UI 操作とそれに対するシステムの応答内容
  - シナリオの基本パターンと代替パターン
  - シナリオが中断して終了するパターン

### ユースケース記述の形式（例：予約情報を登録する）

| 項目 | 内容 |
|---|---|
| ユースケース名 | 「（システムは）XX を XX にする」の形。例：予約情報を登録する |
| 概要 | 内容を要約。例：窓口担当者が予約情報をシステムに入力すること |
| アクター | 使用者。例：窓口担当者 |
| 事前条件 | 事前になされるべき条件（省略可）。例：予約可能座席が用意されている、会員登録がされている |
| 事後条件 | 事後に整う条件（省略可）。例：予約情報が登録済みである |
| 基本フロー | アクターとシステムの対話を順序付きで記載。例：①窓口担当者は会員番号を入力 ②システムは会員情報を表示 ③担当者は予約座席を選択 ④システムは予約座席情報を表示 ⑤担当者は予約確定入力 |
| 例外フロー | アクターとシステムの例外の対話。例：①で会員番号が無効の場合、無効であることを表示してユースケースを終了 |
| 代替フロー | 代替の対話。例：⑤の前に予約座席の追加がある場合は③に戻る |
| シナリオ | 事例。ペルソナが主人公。例：窓口担当の田中太郎がお客様から会員番号12345を聞き出し入力 → システムが会員（鈴木次郎）情報を表示 → … |

事後条件を満たすフローが「基本フロー」「代替フロー」、途中で中断するフローが「例外フロー」。

## 業務プロセスと UI

- UI は機能を実現するために存在し、機能の主な役目はデータ操作。業務プロセスの 5W2H から関わる可能性のあるデータ操作を想定し、それを実現する UI を想定しプロトタイプを作成。ただしこれは **開発者の論理**。「作り手」と「使い手」では求めるものが違う：

| 分類 | 目的 | 効果 |
|---|---|---|
| 作り手 | データ操作 | 定量効果 |
| 使い手 | 心地よさ・使い勝手 | 感動、使いやすさ、安心 |

- まず作り手の論理を優先して各項を重点的に検討し UI を作り上げる。叩き台となるペーパープロトタイプを作成し、開発者とユーザーが一緒にユーザビリティを含む機能要件・非機能要件を踏まえた UI を検討
- **プロセスモデル ⇄ データモデル ⇄ UI・機能（プロトタイプ）** の作成を繰り返すことで各モデル・プロトタイプの精度を高める

### Column：得意技を磨け！（要旨）
何でもこなせるゼネラリストが理想だが、不器用な人はまず一つ「得意技」（データモデル作成・業務フロー作成・UI プロトタイプ作成のどれでも）を磨いて自分なりの方法を見つけ出す方が近道。得意技の領域を習得してからできることを拡げる。全てにおいて優秀なゼネラリストでなくても要件定義は可能。

## プロトタイプの提示タイミング

- **「早すぎるプロトタイプ提示は仕様の肥大化を招く」**。業務フローによる業務の流れ、各業務プロセスの 5W2H がある程度明確化してから。可能ならユーザーシナリオ抽出とともに
- 開発者とユーザーが 5W2H を共有した上でプロトタイプを基に UI を議論。早期提示は機能を肥大化させ 5W2H の定義自体を揺らがせる。肥大化した機能はリリース後、確実といってよいほど使いものにならない
- あくまで **業務フローの世界に惹き込んだ上で** プロトタイプの出番。「この場面（状況）で提示することにより、入力すべき項目やどのような機能であるべきか『自分達の議論』を交わせるようになる」→ 現場の強みを徹底的に生かす／過度な要求の膨らみを防ぐ
- エンタープライズ系：「業務の流れ」「業務プロセスの定義」が明確化した状態で提示すれば、ユーザーは入力項目・必要機能を主体的に議論できる
- コンシューマー向け：お客様の操作の流れを捕獲した上で提示すれば、ペルソナがより効率的にデータ操作を行える UI・機能の議論が可能

## UI と項目

- プロトタイプ検討時に項目を議論することになり、「この項目は必須」「数字で入力」等の画面仕様も明確になる
- **「明確になったものは管理しておく」** 姿勢が大切。全てを完璧に終わらせようと闇雲に時間をかけるのは得策でない。UI を形作る上で必要な項目の洗い出しに務める
- 洗い出された項目は「データ要件の明確化」で作成するデータモデルの **属性** として適切に登録（UI の項目 → データモデルの属性）

## ペーパープロトタイピング

- 紙で作った画面プロトタイプで試行錯誤するやり方。手書きで作成。ユーザーシナリオを基に UI・画面遷移の検討、および非機能要件として耐えられるかを判断するために作成し、結果は UI とともに非機能要件としてもまとめる
- 紙芝居のようなもので構わない。画面上のボタンの位置、押すと次に遷移する画面がわかればよい。機能検討、画面・操作性確認に役立つ
- 目的を絞って、プロセスの定義・必要項目の洗い出し・機能概要の洗い出しのために使用（本項は主にこの目的）
- この時点のプロトタイプは機能・非機能を問わず「要件」を固めることが目的。概要でよい。ただし設計工程で流用できればなおよい

## 手順：「UI・機能の明確化」

1. **ユーザーシナリオの抽出**：各業務プロセスの 5W2H を基にユーザーシナリオを抽出。厳密なユースケースでなくても業務プロセスに基づいたユーザーの行動・振る舞いが明確になればどんな記述法でもよい。ペルソナの行動を手順化した文章でも、現時点で想定可能なレベルのユースケース記述でも
2. **ペーパープロトタイプの作成**：ユーザーシナリオを基に必要と思われる UI・機能を想定し、システム形態に応じて作成した **画面標準** を参照してペーパープロトタイプを作成。データ操作の観点から必要な UI をデザイン。最低限必要な操作と項目が表現されていればよい。紙に手書きで項目・ボタンを大きく書く（ハサミで切り貼りしても可。大きく書くと赤入れ時に修正しやすい）
3. **画面遷移の明確化**：システム形態に応じた **画面遷移標準** を参照して画面遷移を検討し、ペーパープロトタイプを並び替えて明確化
4. **プロトタイプの確認**：ユーザーに実際に操作する気持ちになってもらい UI の観点から確認。開発者は次ページに遷移するタイミングで次の画面に差し替え、紙の上とはいえユーザーが操作をシミュレーションできる環境を作る（ユーザーが紙のボタンを押したら次画面のプロトタイプに差し替える）。指摘事項をまとめプロトタイプと画面遷移に反映。反映時は **UI の存在目的である業務プロセスの 5W2H とブレていないか** を常時確認
5. **機能の洗い出し**：業務プロセスの 5W2H を満たす UI を確定し、必要な機能を洗い出し定義。併行して必要項目も可能な限り洗い出す
6. **プロトタイプ、画面遷移に関する要件の確定**：現時点でのプロトタイプ・画面遷移を確定
