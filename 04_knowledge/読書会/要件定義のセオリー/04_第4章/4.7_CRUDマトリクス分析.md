# 4.7 CRUD マトリクス分析

← [[4.6_データ要件の明確化]] | ↑ [[要件定義のセオリー_MOC]] | → 第5章 [[5.1_非機能要件の明確化]]

## CRUD マトリクスの重要性

- 「データ駆動経営」（データに基づいて仮説検証型経営を行う）が提唱されている。データは経営資源の一つだが重要性は益々増す
- **データの活用度はデータが参照される環境にまるごと依存**。参照したいときに、したい形で参照できるようになっているかが重要（Web 系解析データでも基幹系伝票データでも同じ）
- 参照環境構築の前提は **「データがきちんと生成されていること」**（絶対的な原則）。データを生成する個々の業務プロセスが業務の流れの中で滞りなく遂行されることが基本
- **データの連鎖** に着目：生成したものの参照されないデータ、いつまでも削除されないデータがあれば、①そのデータ自体が不要か、②参照・削除するプロセスが欠けているか、③プロセスの機能が欠けている。これを確認するのが CRUD マトリクス分析の目的。データおよびデータを操作するプロセスと機能が、**データライフサイクルを全うするよう正しく定義されているか** を確認

## CRUD マトリクスとは？

- C（生成）R（参照）U（更新）D（削除）の4種のデータ操作の頭文字。データとプロセス、データと機能のマトリクスがつくる欄に4種のアルファベットを並べて作成
- 要件定義で作成する意味 ＝ 定義したプロセスと機能がデータライフサイクルを全うしているかの確認。CRUD を配置した欄に対する更新要領・ロジックの定義は設計工程以降の作業。ここでは「データ要件の明確化」で定義した論理データモデルの各エンティティのデータライフサイクルまでを確認

| プロセス＼データ | 顧客 | 受注 | 受注明細 |
|---|---|---|---|
| 顧客登録を行う | C R / U D | | |
| 受注登録を行う | R | C R / U D | C R / U D |

## CRUD マトリクス分析の実施

論理データモデルの各エンティティが、ToBe 業務フロー図に現れるどの業務プロセス、および UI・機能要件で定義した機能から、きちんと C・R・U・D の操作がなされているかを確認。

## CRUD マトリクスの作成

- UI・機能要件の明確化で各 UI・機能の操作対象データ（エンティティおよび UI に現れた属性）が明らかになった。そのデータを横軸、各業務プロセスおよび機能を縦軸にとりマトリクス表を作る
- 個々の業務プロセス・機能とデータの交差点（セル）は、そのデータに何らかの操作が行われるタイミングを表す。操作内容は C/R/U/D のどれかで、それを業務プロセスまたは機能が実現する
- **データ×プロセスの CRUD マトリクス** と **データ×機能の CRUD マトリクス** の2種

### データ（エンティティ）側からの登録・確認
エンティティがきちんと C・R・U・D されているかをデータ視点で登録し、各エンティティのデータライフサイクル（CRUD）に漏れがないか確認。

### プロセス・機能側からの確認
更新対象データ（エンティティ）に対してプロセス・機能が行う登録・更新内容を確認。プロセスとして不足している更新・参照操作がないか確認。

### CRUD の配置方法
セル内で C・R・U・D を配置する場所を決めておく。**左上 C、右上 R、左下 U、右下 D** が一般的。

### エンティティと業務プロセスの並び順
- エンティティはサブジェクトエリア単位で分割管理した上で、**イベント系とリソース系に分けて並べる**。イベント系は業務フローを参照してデータ発生の時系列（想定で可）順に左から右へ
- 業務プロセスも業務フローを参照して発生の時系列順。機能の並び順も同様

## 手順：CRUD マトリクス分析

1. **CRUD マトリクスの作成**：業務プロセスとエンティティの間の CRUD マトリクスを作成。論理データモデルの **サブジェクトエリア単位**（エンティティ関連図の作成単位）に作成。横にエンティティ、縦に業務プロセスを並べ、ToBe 業務フローと UI プロトタイプを基に CRUD を記述
2. **業務プロセス側からエンティティを確認**：当該業務プロセスが更新・参照すべきエンティティに、もれなく CRUD が定義されているか確認。続いて当該プロセスが更新・参照できるようにエンティティ間のリレーションシップが定義されているか確認。不備があれば改めてリレーションシップの定義を行い、業務プロセス側から該当エンティティへの抜けているデータ操作を登録。例（業務プロセス「受注登録をする」）：受注＝CRUD／受注明細＝CRUD／顧客＝R／商品＝R
3. **エンティティ側から業務プロセスを確認**：各エンティティに最低でも CRUD のどれか1つ以上が定義されているか確認。不備があればエンティティ側から想定される業務プロセスに CRUD 登録。想定される業務プロセスが ToBe 業務フロー図に記述済みかを確認し、なければ記述（プロセスモデルを変更）。例（エンティティ「受注」）：受注登録をする＝CRUD／受注照会をする＝R／受注伝票を出力する＝R
4. **機能とエンティティの CRUD 分析**：機能についても同様。論理データモデルのエンティティと機能の CRUD マトリクスを作成し、①サブジェクトエリア単位に分析 ②機能からエンティティを確認 ③エンティティから機能を確認。例（機能「受注情報登録」）：受注＝CRUD／受注明細＝CRUD／顧客＝R／商品＝R。例（機能「顧客検索」）：顧客＝R
5. **外部連携やデータ移行に関する CRUD 定義**：外部インターフェースの連携先やデータ移行元をエンティティとして定義した場合、外部連携・データ移行を司る業務プロセスおよび機能との CRUD を登録
6. **CRUD マトリクスの確認**：要件定義における CRUD マトリクス作成の目的はデータライフサイクル、プロセス・機能の漏れの確認。最後にこの作成目的を果たしているかを確認

**データとプロセス・機能の交差点を抑える** ことが CRUD マトリクスの本質。
