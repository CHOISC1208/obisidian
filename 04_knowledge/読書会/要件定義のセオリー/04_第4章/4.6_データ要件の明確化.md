# 4.6 データ要件の明確化

← [[4.5_UI・機能要件の明確化]] | → [[4.7_CRUDマトリクス分析]]

## データ要件の重要性

- プロジェクトではプロセスや機能の話が中心になりがちだが、特に業務システムにおいて UI の目的は **「適切なデータの出し入れ」**。**システムの価値は極めて多くの場合、データが左右する**
- 要件定義で早期にデータ要件を固めれば、ライフサイクル全般で高品質を安定して保てる。データ要件が曖昧だと一定以上の品質担保が極めて困難。データ要件の大枠が固まらない ＝ システムの方向性が定まっていない（とても危険）
- WF／アジャイルによらず普遍。**「枠組み」「方向性」「範囲」** だけは要件定義段階で明確にしておかないとプロジェクトそのものが破綻しかねない

## データ要件の明確化の手順（概要）

ToBe データモデルとしての概念データモデルが存在するか否かで手順が異なる：
- **存在する場合**：マスターとなりうる「リソース系」エンティティの位置づけは明確なはず。ビジネス／業務／システム要件を基にトップダウンモデリング → ToBe データモデルの追加・修正 → 業務要件・システム要件を基にボトムアップモデリングの結果を追加 → 概念データモデルを修正して新 ToBe データモデルとして作成 → 主要属性を定義した論理データモデルを作成
- **未作成の場合**：各要件を基にトップダウン・ボトムアップモデリングを行い、ToBe データモデルとしての概念データモデルおよび論理データモデルを作成

### 用語の整理
- **概念データモデル**：エンティティ（業務上で管理すべき対象物）とその意味、エンティティ同士の関係を表す
- **論理データモデル**：業務要件上必要なデータ（項目）とビジネスルールを表現する
- どちらもあらゆる技術や特定の実装から独立
- 本書の要件定義で作成する論理データモデルは、DMBOK でいう **「エンタープライズ論理データモデル」** に相当。属性付与は主要なもののみで部分的にとどめる。後工程で全属性を付与した「ソリューション論理データモデル」を作成。正規化・抽象化は限定して行う
- **マスター系の位置づけが変更になると後工程への影響がとても大きい**ので要注意

## AsIs データモデル

- ①理想の ToBe データモデル → ②AsIs データモデル＋制約 → ③実現を目指す ToBe データモデル
- AsIs の有無に関わらず、③を作成するには AsIs の内容と制約を考慮する。特に AsIs のリソース系（マスター）エンティティに注目
- 元々ビジネス変化に対応可能なマスターなら良いが、そうでない場合は **決断** が必要：問題があろうとも流用するか、マスター変更まで行って③を作成するか。新規より修正案件に多い。前者は工数少だが現行課題を引きずる、後者は課題解決するが工数増大を覚悟

## なぜ、データ要件を明確化するか？

- データ要件の不明確さは **後工程で一番の手戻り原因**。しかも修復不可能な場合が多い
- データ要件が曖昧なまま設計に入る ＝ 設計・実装時に基盤が崩れる可能性。データモデルの不備を原因とするデータモデル変更 ＝ データベース基盤の崩壊。**マスター系の変更は致命的**。変更前の DB 構造を基盤に開発されたアプリケーションは作り直し
- 用語の意味の曖昧さ・間違い・コード設計の不備も同様。これらは「受け入れテスト」等リリース直前に大問題として噴出し、使い物にならず多大なコストで作り直し
- 逆にデータ要件を早期に明確にすれば、素晴らしいシステムを効率よく開発できる可能性が飛躍的に大きくなる

## システム開発におけるデータモデルの位置づけ

- 本書：要求分析工程で「概念データモデル」を作成し、要件定義工程で主要属性を定義した「論理データモデル」を作成
- データモデル作成の目的 ＝ **「静的なビジネスの全体像を把握すること」**。システム要件を満たすことが絶対条件
- DMBOK の概念データモデルは通常 **ER 図とデータディクショナリ** の形で整理。ER 図はエンティティとリレーションシップを明確にしビジネスの概要把握を可能にする。ディクショナリはその時点で明確な用語の定義集
- 要件定義におけるデータモデルの定義内容はプロジェクトごとに差異。主な3種類：
  1. エンティティとリレーションシップの関係のみ把握可能（DMBOK 概念データモデルをそのまま踏襲）
  2. エンティティ属性を一部登録し UI・機能想定を可能にしたモデル（DMBOK エンタープライズ論理データモデルを踏襲）
  3. エンティティの全属性を登録（DMBOK ソリューション論理データモデルを踏襲）
- **本書は②を基本としつつ③までを可能とした形**を「論理データモデル」と総称。要件定義で必要な見積りを可能にするレベルと時間的制約を考慮すると適当。①で終えても問題ない（プロジェクトの考え方次第）

### ER 図の用語
- **ER 図**：エンティティとリレーションシップによりデータ構造を表す図
- **エンティティ**：データ構造の中で実体として認識可能なもの。ビジネス活動を行う上で把握すべき対象（「参照や関連付けを受けるデータのまとまり」とも）。例：顧客、商品、受注
- **リレーションシップ**：エンティティ同士の関連・結びつき。例：顧客と受注の関係
- **属性**：実体内で管理されるべき「項目」
- 本書は **IE 記法** で表記。記法は慣れを含めわかりやすければ何でもよい

## 要件定義における論理データモデル

- 目的は「静的なビジネスの全体像を把握すること」。今回の開発範囲と制約が明確になっていることを前提に作成
- ToBe データモデルがある場合：AsIs と制約を踏まえ「要件」を基に概念データモデルの追加・修正を行い、新 ToBe 概念データモデルの精度を上げる → 属性付与して論理データモデルを作成。ない場合は要件を基に一から作成
- ToBe でリソース（マスター）の追加・変更を要する場合、AsIs との検証段階で本当にそこまで行うか、必要があるかをビジネス方針・制約（予算・時間）を含め検討し決定。マスターはそのまま既存流用、新規に重複承知で作成し MDM（マスタデータ管理）等で対応、という選択もある。AsIs と ToBe でデータ構造があまり変わらない場合もある
- 修正変更では **マスター変更は比較的少なく、トランザクション変更・追加の方が多い**。新規開発でマスターがきちんと設計されデータマネジメントが機能し、レコードを一意に特定できるなら問題ないが、そうでない場合は変更時に熟考

### 概念／論理データモデルの意味付け
「ビジネスの静的側面を支えるビジネスルールを明確にする」側面もある。例：お客様からは同じに見えても、開発対象システムにおける組織の捉え方（店舗・支社の位置づけが組織内で異なる場合）を業務ルールとして整理。法人顧客や季節限定値引率の設定などもデータモデルから抽出されるビジネスルール。

## 論理データモデルとは？

概念データモデルを参考に、箱（エンティティ）と箱同士の関連を表す線（リレーションシップ）を組み合わせ、箱の中に属性をはめ込んで作成。箱の意味・線の方向・意味等が全てビジネスルールを内包しており、要件定義段階で明確にすべきデータ要件でもある。

## トップダウンとボトムアップモデリング

データモデリング ＝ データをわかりやすく人間の目に見える形に描く作業。プロセス同様、データもトップダウンとボトムアップの両面から正しく美しいデータモデルを作り上げる。

### トップダウンモデリング
- ビジネス要件 → 業務要件 → システム要件とブレイクダウンした要件を基に「本来あるべきデータモデル」を作成。要件・ビジネスルール（システム以外の規定等含む）を基に、主に **リソース系エンティティ** の抽出と定義
- **リソース（資源）系エンティティ** ＝ DB において「マスター」となりうるエンティティ。ビジネス活動に必要不可欠なリソース。例：取引先、顧客、商品。業務ルール・業務規定・要件定義書・新システム全体図等からマスターとなりうる用語を抽出
- 本来は要求段階・業務分析工程で実施済であるべき。マスターとなりうるエンティティの定義がブレるとシステム全体の整合性を保つのが難しくなる
- 「顧客」とは？「商品」とは？——マスター系の定義は企業組織の **生命線**。新規は経営方針から逸れることなく企業組織内で合意し決定。修正は現行マスター流用がほとんどだが、本来あるべき姿から乖離していれば修正で調整可能か検討

### ボトムアップモデリング
- ToBe 業務フローで捕獲した **発生データ** を基に主に **イベント系エンティティ** の抽出と定義を行い、**UI プロトタイプから項目** の洗い出しと定義を行いつつ、正規化を実施して「現実に即したデータモデル」を作成
- **イベント系エンティティ** ＝ DB において「トランザクション」となりうるエンティティ。今後ビジネスを進めるために必要な記録すべきビジネス活動。例：取引、受注、発注。日々の業務など企業組織の活動で発生する出来事
- 例：受注（元）{受注番号, 受注金額, 受注年月日, 商品コード, 適用開始年月日, 受注数量} → 受注{受注番号, 受注金額, 受注年月日} —を明細として持つ→ 受注明細{#受注番号, 受注明細番号, #商品コード, #適用開始年月日, 受注数量}

トップダウンとボトムアップを繰り返すことで論理データモデルが完成。**リソースモデル（マスター系）はビジネスルールにより、イベントモデル（トランザクション系）は業務の流れと UI プロトタイプから抽出！**

- この時点で結果が物足りなくても嘆く必要なし。インプットがそれしかないならそれなりのものしかできないのは当然。とにかく繰り返すことで完成度が高まる
- 修正の注意点：当初は全体最適を指向していても、現場の意見で個々の業務を最適化する修正依頼をそのまま実装した結果、データ設計も部分最適化するケース。似たようなエンティティ・データ項目が作成・実装され、アプリも重複データを操作 → **「スパゲッティ化」の始まり**。常に全体最適を意識し、ビジネスの静的側面全体を鳥瞰して個別最適に陥らないよう気をつける

## 正規化とは？

- データの重複をなくしデータの整合性を保つようにすること
- 概念 → 論理データモデル作成時、UI から抽出した項目を属性として各エンティティに振り分けた後、正規化を実施
- 正規化はデータ登録・更新・削除時の不整合・喪失を防ぎ、保守性を高めシステムライフサイクル向上に貢献 → データモデル作成時から意識
- 第一〜第三正規化まで（厳密には第六正規形まであるが、第三を満たせばほぼ第五を満たすので、まず第三まで意識）
- **原則「One Fact In One Place」**（ひとつの場所にひとつの事実）。この原則を念頭に属性を整理すれば自然と正規化状態になる。正規化 ＝ 用語（属性）の意味でもリレーションシップの意味でも「一意である」こと。現時点では登録済み属性について一意であることを意識するレベルで構わない。正規化は正規形という **状態** を作ることであって、第一から実施する手順のことではない

## データモデルの作図

### エンティティの抽出：5W1H を表す名詞
| | 例 |
|---|---|
| 誰が（who） | 組織、取引先、顧客 |
| 何を（what） | 製品、商品、原材料、サービス |
| いつ（when） | 年月（日）、催事、会計年度 |
| どこで（where） | 国・地区、住所、店舗 |
| なぜ（why） | 業務ルール、法律、慣行、問い合わせ、クレーム |
| どのように（how） | 指示方法、請求、受注 |

- 実体同士の関係をリレーションシップの線で結び、データモデルとして表す。例：顧客種別 —分類する→ 顧客 —を行う→ 受注
- 作図の際、エンティティの **名称・概要・リレーションシップの定義** を行う。概要にはエンティティの意味の定義とビジネス視点でのライフサイクル（発生〜消滅）を記述。単に箱を書いて線で結ぶだけではモデルにならない。**モデルを作る ＝ 作図とともにモデルの定義を行う**。定義が不明確 ＝ 基本的なビジネスルールが曖昧 → そのまま後工程に進めば仕様確定がままならないまま地獄が待っている
- エンティティ・リレーションシップの定義は静的で厳格なビジネスルールになる。要件定義で大枠を押さえる

## 用語の管理

- エンティティ名称・リレーション定義に使用する用語・属性となりうる項目をこの時点で整理。一般用語を **「用語集」** に、データ項目を **「データ項目辞書（データディクショナリ）」** に登録。用語集には「顧客」「受注」等、データ項目辞書には「顧客名称」「顧客コード」等のエンティティ属性項目を中心に
- **「データモデル」＝ ER 図と用語集、データ項目辞書をセット** で管理。どれが欠けてもデータモデルと呼べない
- 用語集では可能なら **「禁止語」** も管理（現行システムで使っているが新システムでは使用不可の用語。企業合併で吸収された側の社内用語など）
- 用語整理は設計工程まで待たず要件定義から始める。気づいたことはその時点で登録。設計段階で気づいた時には抜けが生じて間に合わない。データモデルの大幅変更で手戻りが生じ、プロジェクトが破綻することもある。用語整理はユーザーがデータモデルを理解する手助けになる
- UI・機能要件の明確化で作成したプロトタイプにより、データ操作の対象エンティティと UI に現れる属性が明確になる。現れた項目を該当エンティティに振り分け属性として登録

## 適度の抽象化

- 論理データモデル作成時に正規化とともに抽象化を検討・実施。「パターン」の活用が鍵になることがある
- **データモデルパターン** ＝ 業種や業務の違いに左右されない汎用のデータモデル。代表例：人や組織（取引先等の外部組織含む）を表す **「パーティパターン」**、受注／発注を表す **「取引パターン」**。パターン適用 ＝ 業務を抽象化して表現
- 注意：パターン多用で **「過度の抽象化」** を行うと個々の企業組織のビジネスが見えにくくなる。「やりすぎ」でビジネスの静的側面がわかりにくくなるのは本末転倒。パターンはあくまで **参照** モデルとして活用。パーティ・商品等の整理はパターンを参照しつつ企業組織の文化を踏まえて整理
- 例（パーティパターンによる取引先管理）：パーティ（ID・識別・タイプID）をスーパータイプに、組織／人をサブタイプ、パーティロール・パーティ関係（From／To、有効開始日・終了日）等
- 必要なのは **ユーザーとの確認が可能なレベル** のデータモデル。今回の開発範囲におけるビジネスの静的側面が把握可能でなければならない。抽象化をもう一歩進める場合はデータサンプルの提示など確認しやすい工夫。図解した補助資料やサンプルが必要

## 美しいデータモデル

「わかりやすい」データモデルには「美しさ」を意識。シンプルかつ目的をきちんと叶えることで美しいモデルになる。2点に留意：
1. **サブジェクトエリアの適切な切り分け（分類）**：データモデル全体をいくつかに区切った個々の領域。ビジネス上の観点から区別した方がよい単位で分割（ビジネス・事業・業務単位が一般的）。目的は「データモデルを見やすくすること」なので、分割しなくても見やすければ不要（EC サイトでは分割しなくても収まることが多い）
2. **エンティティの配置ルール**：一定のルールで ER 図内のエンティティを配置すると美しく見える。例：タイプ（リソース系・イベント系）で色分けし、リソース系は上・イベント系は下、イベント系は発生順に左から右へ。左右は発生順またはリソースの種類毎にグループ化。**リレーションシップの線の交差をいかに少なくするか** が見やすさのポイント

## ユーザーにデータモデルを理解してもらうには…

- 2つのエンティティと関連を示すリレーションシップを抜き出し、箱・線を **赤ペンでなぞりながら** ビジネスルールを確認。例（顧客 —を行う→ 受注）：「顧客」は「受注」なしでも存在する／「受注」は「顧客」なしでは成立しない → 受注前に顧客登録が必要。その場合「一見さん」の取扱いは？／顧客登録の際には顧客名・住所・email は必須
- **データモデルを固めるためのプロトタイプ**：イメージが湧かない場合、プロセス要件・UI 要件の明確化で作成したプロトタイプから必要部分を抜き出して提示し、データモデルに内在するビジネスルールを固める（例：受注／受注明細と受注の属性＝UI に必要な項目をビジネスルール確認）
- ビジネスルールと用語集・データ項目辞書を現時点で整理するのは論理データモデルを固めるため。逆に概念／論理データモデルに表されているルールと用語が整理されていなければモデルとして成立していない
- 業務部門に見せても簡単には理解してもらえないことを踏まえ、**画面イメージとエンティティを切り出して提示** するといった見せ方の工夫が必要な場合もある

## 例外ルールの洗い出し

- 現行システムに内在する例外ルールが、AsIs データモデルが存在する場合でも抜けている場合がある。本来データモデルで整理すべきビジネスルールをアプリケーションロジックで実装している場合が殆ど
- 業務プロセス要件でプロセスモデルの観点から例外パターンを絞り込むのと併行して、データモデルでも例外ルールを絞り込む

### エンティティからの例外ルール抽出
5W1H を表す名詞には、エンティティとして管理されるべきものと属性として管理されるべきものが混在。エンティティ同士・属性同士の間にリレーションシップとして現れていない関係がないかに着目。例：
- 「取引先」と「製品」：製品の「製品ジャンル」と「取引先」により特別値引きルールがある
- 「顧客」と「受注」：顧客の「顧客ランク」と受注の「受注日」によりキャンペーン価格適用・特別ボーナス付与。クーポンを持った顧客の適用ルール等
- 「地区」により「出荷」形態が異なる

## BABOK における概念クラス図

- BABOK は要件定義で「概念クラス図」作成を推奨。業務プロセスの開始〜終了までを要約する際に現れる名詞（モノ・コト）や名詞句、動詞を名詞化したキーワードを抽出。情報システムを意識せず業務の視点から概念を抽出。概念に付けた用語を文章にすると曖昧さが判明したり新たな発見がある。用語集は部署によって用語が違うことがあり、部署ごとの異なる言いまわしを「シノニム（異音同義語）」として記載する場合もある。この段階で完成させるのではなく新業務フローや情報モデル作成の中でブラッシュアップ
- 著者は要件定義段階での概念クラス図使用は全システムで有効とは考えていない。クラス図よりもわかりやすい表現にこだわる。上流工程では **技術者ではなくユーザーが主役** で彼らの理解を優先すべきという信念
- さらに要件定義を工程として区切った場合、以降の設計工程をどんな技術者が行うか、技術水準もわからない。日本では下流（設計・実装）を担う技術者が上流より軽視される傾向があり「当たり外れ」がある。外れを引いてもプロジェクトを成功に導かなくてはならない
- 「データ」と「プロセス」はビジネスや業務の異なる側面。この2つの事象をあくまで業務寄りに表現することを目指す。キーを含む属性を定義しないならどちらでも構わないが、今この時点で議論し決定したデータ要件が設計を経て実装されることをイメージしやすくするには、**クラス図よりデータモデルの方が有効**

## コード体系の精査

- AsIs データ分析で一番優先すべきは **現行コード体系の調査**。現行コード体系にはコードごとにロジックを伴ったビジネスルールが内在していることが多い
- 要件定義段階で全コード設計を終える必要はないが、現状分析としてコード体系を把握し、場合によってはデータモデルへの反映・用語集への登録を行う

## AsIs モデルについて

- 「データはプロセスに比べて安定している」。AsIs モデルから ToBe モデルを作成できてしまうこともある。本来は ToBe を基に AsIs を参照しつつ見直し・修正
- ただし AsIs がしっかりできている場合に限る。きちんとした AsIs がない時は手間をかけて作成する必要はない。作成しても概要を表したモデルで構わない。主要なエンティティとリレーションシップのみ洗い出し、「あくまで静的なビジネスルールの確認用」と割り切る
- プロセスモデル同様、データモデルもなければ **LIVE で作成** してしまう。最低限リソース系（マスター）となりうるものはきちんと押さえた上で、現行 AsIs の UI ハードコピー等を収集して作成に臨む

## 外部インターフェースの明確化

- 新システム全体図・要件定義書・概念データモデル・ToBe プロセスモデルに基づき、外部システムとのインターフェースに関する要件を明確化
- 外部インターフェース ＝ 設計対象システムと他の社内外システムとの **「データの受け渡し」**
- 「どのデータを受け渡すか」だけでなく「どのように受け渡すか」も考慮。厳密にはデータ要件だけでなく機能にも影響するが、第一の目的はデータの受け渡しをきちんと把握すること。どのような外部インターフェースがどのくらいの種類存在するかをまず把握

## 手順：「ToBe データモデル」作成

1. **サブジェクトエリアに分割**：概念データモデルがある場合、ER 図を見やすくするため必要に応じてサブジェクトエリアを分割。エリアの一覧表と各エリアに所属する把握可能なエンティティの一覧表を作成。**業務視点** で分割を推奨（データモデルは開発者とユーザーのコミュニケーションツール。ユーザーが理解可能な単位でまとめる）。概念データモデルがなければある程度形をなしたところで切り分け。新規は括りを意識して作成（たいてい複数の管理対象）、修正は追加すべきか既存を修正すべきか熟考。重要度はエンタープライズ系 > コンシューマー向け。開発対象範囲が明確な場合はサブジェクトエリアを意識する必要なし
2. **リソース系エンティティの抽出と定義**：リソース系 ＝ ヒト・モノ・金など企業組織の活動基盤を表すデータ（「台帳データ」とも）。まず **トップダウンモデリング** で要件定義書・ビジネスルール等を基に抽出。定義はビジネス要件からブレイクダウンしたシステム要件を踏まえたもの（「顧客」とは？「商品」とは？を明確に）。概念データモデルがあれば AsIs と制約（要件）を踏まえて元の概念データモデルを修正、なければ要件を基に一から抽出。次に概要を定義（すべてのエンティティには定義すべき存在意義がある。説明・制約・ルール・範囲になりうるものは余さず洗い出す。「顧客」と「商品」の関係、複数「商品」を「受注」で処理可能、「顧客」グループごとの個別販売価格の有無、商品の店舗別販売価格等）。**エンティティの概要定義はデータモデル作成の「必須の作業」**。保守フェーズの修正では、マスター定義が以前から不明確でも、プロジェクト方針でマスターから作り直すのでなければそのまま流用を基本とする（開発範囲外の議論はしない）。新規では今後のマスター管理のあり方を考慮しながら作成
3. **各エンティティ間の関連を分析する**：リソース系エンティティ同士の関連を分析し、リレーションシップの登録と静的なビジネスルールの洗い出し
4. **イベント系エンティティの抽出と定義**：現時点で把握可能なイベント系エンティティを抽出。業務フロー図を参照して業務の流れから **ボトムアップモデリング** で抽出。概要定義も同様に行う。業務の流れからだけでは漏れが生じる場合がある（データ活用の観点からの分析帳票等）→ 改めてトップダウンで追加を検討。イベント系は「業務要件」からブレイクダウンした「システム要件」を満たす必要
5. **リレーションシップの線を引く**：抽出したエンティティ同士に線を引き併せて定義。すべての線には引かれた理由・方向・矢印の意味がある。意味の定義文は「〜する」「〜される」という **動詞句で統一** を基本。矢印方向に沿って「親（起点）は子（終点）を〜する」（行為）もしくは「〜になりうる」（存在）等の書き方で統一。親→子へ「（主語）＋（目的語）＋（述語）」の形で整理。これで概念データモデルの大枠が固まる。元の概念データモデルの有無にかかわらず、この時点で **新 ToBe モデルとしての概念データモデルを確定**
6. **属性の登録**：完成した概念データモデルに修正を加え論理データモデルを作成。UI プロトタイプから項目を洗い出し、リソース系・イベント系エンティティに振り分けて項目を属性として登録。登録後に正規化を実施しデータモデルを「一意従属」の形に整える。属性命名は極力 **用語集・データ項目辞書に整理されたビジネス用語** を使う（解りやすいモデルのためとても重要）。用語集等がまだない段階ではビジネス用語を属性名称（または一部）として使用した上で併行して用語集・データ項目辞書に登録。命名規則（ネーミングルール）に従う。用語登録の際は属性の意味をきちんと定義（例：「顧客名：管理対象となる顧客の名称」）。要件定義段階ではエンティティ名称となりうる用語と UI で使用する項目を整理（「顧客名」「取引先名」「商品名」など UI に現れる各項目までを把握）。定義も明確に（例：「顧客」には見込み客を含むのか等）。エンティティの属性となりうる用語は最大限かつ「できる範囲で」整理
7. **主キーの設定**：登録された属性から主キーを設定。各エンティティに対して必須。エンティティを一意に識別（特定）するため
8. **抽象化**：「データモデルパターン」を使用した抽象化を検討し必要な場合には実施。どこまで抽象化するかは開発プロジェクトとして事前に決めておくことが望ましい
9. **外部インターフェースの記載**：外部インターフェースが存在する場合、新システム全体図と ToBe 業務フロー図を基に、対象ファイルをエンティティとしてモデル図に記述。正規化が崩れる等、少々泥臭い表現になっても仕方ない。存在するものはモデル上に表現。外部接続・データ連携が存在することを論理データモデル上にきちんと書き込んでおくことが大切。受け渡しに必要な項目がわかれば可能な限りエンティティ属性として登録。相手側（外部）システムの項目名称・型・桁は例外として、そのまま当該システムへの変換対象項目として整理（正式な用語ではなく UI の「ラベル」と同様に管理）
10. **サブジェクトエリアの見直し**
11. **用語集の整備**：「用語集」と「データ項目辞書」を整備。登録すべきはビジネス用語・同義語（あれば）・エンティティの属性名称等。属性は命名規則に準じる形で登録。この時点で把握できた用語のみで充分。用語集・データ項目辞書が設計・実装で使用可能ならプロジェクト全体の効率が格段に高まる。**「要件定義段階での用語集、データ項目辞書」は忘れずに成果物に**。用語集・データ項目辞書は ER 図と対をなす。両輪を押さえてはじめてデータモデルと呼べるものができ、理解度も格段に高まる
12. **別名・異音同義語・同音異義語の整理**：登録された属性の用語を整理。3つを常に念頭に：**エイリアス（別名）**：実体と呼び名がくい違っている／**シノニム（異音同義語）**：実体は同じなのに見方によって呼び名が違う／**ホモニム（同音異義語）**：実体は異なるのに同じ名前で呼ばれている。特に登録用語にシノニムがないかを早い段階で意識。論理データモデルは設計を経て DB として実装される際の基盤。用語の意味不明・勘違い・曖昧な箇所を放置すると実装工程で重大事になり、プロジェクトの致命傷にもなる。勘違いを元にした手戻り、「騙し絵」になる恐れ。意味の混同やくい違いは水面下で起こりなかなか表面に現れない。不備が発覚するのはテスト工程がほとんどで、重大な欠陥が最後の最後に発生する危険性が高い。ユーザーからは「こんなものは使えない」と突き返される。アジャイルは WF より気づくのが早いかもしれないが手戻りは同様に生じ大枠の変更に迫られる。早いうちから用語の意味をきちんと定義し用語集・データ項目辞書に登録
13. **データモデルの確認**：2つのエンティティと結びついているリレーションシップの線を切り出し、ビジネスルールと必要な属性を確認。場合によっては UI 確認に使用したプロトタイプの当該箇所を切り出して確認用に使用。特に留意すべきは何度も繰り返すが **「リソース系エンティティ」**。リソース系エンティティの意味合いや定義が後工程で覆る ＝ ビジネス領域における「顧客」「商品」の扱いが変わる ＝ 取り返しのつかない大惨事
14. **さらなるデータモデルの磨き上げ**：エンティティ間で関係のない属性に当たりをつけてビジネスルールを炙り出す／リレーション1本1本を赤ペンでなぞりながらビジネスルールを炙り出す／関連あるエンティティの属性同士からさらなるビジネスルールを炙り出す／システム全体図・プロセス・データの観点から外部接続の漏れの確認
15. **要件定義書の作成**：ここまでの検討・定義内容をデータモデルとして要件定義書にまとめる。作成された概念／論理データモデルは実現すべき ToBe データモデルとなる

「時間がない」という理由で概念／論理データモデルを作成せず DB を設計しようとするプロジェクトがあるが止めた方がよい。データ要件の枠組みを定義する概念／論理データモデルの作成は **必須**。重要性を理解せずセオリーを無視したテーブル定義で DB 設計を行った気になっているようでは、ライフサイクルを全うするデータ構造は整備できない。**データ構造の不備はそのままビジネス価値の低下に直結**。コンシューマー向けでもエンタープライズ系でも変わらない。

### Column：属性名の命名規則（ネーミングルール）の標準化と明確化（要旨）
属性の命名体系は「修飾語」＋「主要語」＋「修飾語」＋「区分語」を前提（修飾語は省略可）。例：修飾語＝月次、主要語＝売上・顧客・商品、修飾語＝合計・借方、区分語＝金額・氏名・住所・コード・区分 → 「月次／売上／合計／金額」。命名規則に沿って主要語・修飾語・区分語を統一・標準化し、異音同義語や同音異義語が発生しないよう注意。

### Column：導出項目の整理（要旨）
UI プロトタイプで洗い出された項目は全てがエンティティの属性になるわけではない。画面上の「合計金額」＝【(売上)合計金額＝各行の単価×数量の合計値×税率】で算出されるなら、洗い出す項目は「合計金額」ではなく「単価」「数量」「税率」。計算で算出される項目 ＝ **導出項目**。導出項目をそのまま属性としてはいけない。属性とする場合は導出項目であることをきちんと把握・定義。洗い出した単価・数量・税率は命名規則に基づいて命名し、該当エンティティに振り分け属性として登録。

### Column：ビジネスルールの整備を開始しよう！（要旨）
概念／論理データモデル作成過程で様々なビジネスルールが明らかになる（顧客と時期・数量によりサービス内容が変更、変更内容は値引きか配送コストを持つのか等）。全てがデータモデルから抽出できるとは限らないが、想定しうるものは書き出し、プロセス定義・機能定義の際に追加して完成に近づける。この時点で判明したルールを **「ビジネスルール集」** としてまとめ要件定義の成果物に。後々の DB 定義や機能ロジック定義になり、設計工程で流用可能なら効率・生産性が格段に向上。見出しとメモ程度でも構わない。エンティティ・リレーションシップの定義以外で明らかになったルールを書き出し、**文書化** することが大事。蓄積は設計のみならずシステムライフサイクル全般で価値を持つ。

### 実施作業の場合分け

| | 新規 | 修正 |
|---|---|---|
| エンタープライズ系 | ❶ | ❸ |
| コンシューマー向け | ❷ | ❹ |

- ❶❷ ToBe データモデルに要件を加味し新 ToBe データモデルを作成。ToBe がなければこの工程で要件から作成
- ❸❹ 修正の対象と対象外を明確にすることを心掛ける。ビジネス要件の変更を伴う大幅修正はリソース系エンティティの見直しを必要とする場合がある。影響度を見極めてデータモデルの修正を行う
