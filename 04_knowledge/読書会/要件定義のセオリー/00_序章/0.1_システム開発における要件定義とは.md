# 0.1 システム開発における「要件定義」とは？

← [[要件定義のセオリー_MOC]] | → [[0.2_本書が目指すもの]]

## 要件定義の定義

> 要求分析の結果を基に、システムで実装すべき **制約を明確にし、「要件」として確定する** こと

要件定義が意味を持つための2条件：
1. **ステークホルダー間で合意できる表現**であること（技術者でない人も理解できる）
2. **設計工程のインプットとして使える**こと（後工程の技術者が分かる表現）

## 本来の要件定義の位置づけ：ToBeモデルとの関係

要求とは「要求事項の羅列」ではなく、**ToBeプロセスモデル（プロセスのあるべき姿）と ToBe概念データモデル（データのあるべき姿）が業務レベルまで考え抜かれた状態** を指す。

- プロセスモデル：業務プロセスを手順として図解したもの（＝組織の仕事の仕方の図解）
- データモデル：組織が管理すべきデータとその構造の図解

### 要求分析 → 要件定義の作業列挙

| # | 作業 | 工程 |
|---|---|---|
| 1 | 時間をかけて要求を明確化し、ToBeビジネスモデルを検討 | 要求分析 |
| 2 | 要求を基に ToBeプロセスモデル・ToBe概念データモデルを作成 | 要求分析 |
| 3 | AsIs（現状）モデルを検証 | 要求分析 |
| 4 | AsIs を参考に、人・モノ・金等の制約を考慮して ToBe の実現可能性を検討 | **要件定義** |
| 5 | 実現可能性が低ければ ToBe を修正し、新 ToBe のプロセス／データモデルを作成 | **要件定義** |
| 6 | AsIs → 新 ToBe へのプランを策定 | **要件定義** |

要件定義の本質は **「理想を現実に近づける作業」**。
①理想の ToBe → ②AsIs 分析で現状と制約を加味 → ③実現を目指す ToBe（＝要件）

### 前提条件の2パターン

本書は以下どちらの状態からでも要件定義ができるように書かれている：
- **A) 要求が ToBeモデルに落とし込まれている**（本来目指すべき形。要求分析がきちんと行われた）
- **B) 要求がやや曖昧で ToBeモデルが存在しない**（要求分析が不十分。実際はほとんどこちら）

## 機能の仕様を確定すること

- 一般論として「要件定義の中で機能の仕様まで確定すべき」とされる
- ただし要件定義で押さえる「仕様」は **ユーザー視点での機能の振る舞いと制約** であり、内部構造には踏み込まない
- 新規開発では見たこともないプロセスの機能仕様を確定する必要があり、「極めて困難」。それでもここを確定しなければプロジェクトは先に進めない
- ユーザーは仕様確定の重要性を理解していないことが多い（曖昧・誤った要件が後工程に与える影響も理解していない）

### 機能仕様の記述例（業務プロセス：受注登録を行う）

5W2H で記述する形式が示されている：

- **Why（実施目的／システム化の狙い）**：受注伝票の記入を省き効率化、受注時点での在庫把握と納期回答、在庫を元にした正確な発注 など
- **When（実施タイミング）**：電話／FAX受注時に即時登録、内示受注も即時、変更・取消時の対応
- **Where（実施場所）**：営業部の各PC、営業部員のタブレット、他部署は参照のみ
- **Who（実施者）**：営業の予約担当社員は入力可、営業部以外は不可
- **What（実施対象データ）**：顧客／社内からの受注情報、直送／自社経由、現金取引／受注単価決定済み
- **How（実施要項／業務の流れ）**：受注受付 → 在庫確認・与信確認 → 在庫不足なら仕入先選定・見積 → 受注書・受注確認書の出力・送付
- **How much（実施量）**：月平均500件、ピーク（GW・年末年始）は月2000件
- **その他留意点**：有効在庫のリアルタイム引き当て、複数通貨対応

※ ユースケース記述を用いてもよい。詳細は第4章。

## 方向性を指し示す

- 要求はビジネス（経営）／業務（現場）／システム（エンドユーザー操作）の各レベルから出てくる。整理するフォーマットは **ビジネス表現＝ユーザーが理解できる表現** でなければならない
- 要件も同じく、ユーザーが理解できなければ合意が得られない
- 要求と要件の違いを一つ挙げるなら、**要件は設計工程のインプットとして有益でなければならない** こと → 要求よりは IT 寄りの用語が必要になるが、それでもユーザーが理解できる表現を優先
- 結論：**誰が見ても「わかりやすい」表現** で、「方向性が適切か」を見極め、「枠組みを明確にして具体化」する

## 要件定義の範囲

どこまでを要件定義とみなすかはプロジェクトによって異なる。本書の立場は「実装（HOW）を意識せず、まず何（WHAT）をきちんと定義すべき」。ただし近年はアーキテクチャが実装工程を左右するため、要件定義時点でアーキテクチャ検討も必要。

本書が扱う範囲は以下の2択：
- **a) 機能／非機能要件の確定まで**：開発対象システムの全機能／非機能要件を確定
- **b) 機能／非機能の目的・方向性の明確化まで**：想定アーキテクチャを基盤に、データ・プロセス・必要な機能・UIを確定

b) は a) の途中まで。**本書は b) を基本** とし、両方に当てはまるように説明。

### まずは「枠組み」を明確にする

枠組み ＝ システム／インフラ／アプリケーション／データに関するアーキテクチャの方向性（例：アプリは現行踏襲か、インフラはオンプレかクラウドか、言語は、データモデルは流用か）。枠組みを想定できれば **開発規模の見積り精度** を判断できる。

要件定義の段階で「どこまで求めるか」は後工程の定義内容を変える → 読者は自プロジェクトの工程観に合わせて本書をカスタマイズして使うべき。

## 情報システムにおける「要求」と「要件」

| | 定義 | 一言で |
|---|---|---|
| **要求** | ユーザーが情報システムで実現したいこと | 本当に **欲しい** もの |
| **要件** | 要求に基づきつつ、**制約を踏まえて**、情報システムに盛り込むべきもの | 本当に **要る** もの |

### 要求の階層（レベル）

ビジネス要求 → 業務要求 → システム要求 の順にブレイクダウンし、それぞれをビジネス要件 → 業務要件 → システム要件として整理する。

例（EC）：
- ビジネス要求：定性＝顧客拡大と満足度向上／定量＝売上向上
- 業務要求：顧客利便性向上によるクレーム減、受付事務負担の軽減、部門売上・会員数・アクセス増
- システム要求：新ECサイト構築、新決済手段、アクセスログ、リコメンド、基幹系連携、顧客マスター再構築

### 最初から「システム要求」が明らかなケース

1. RFP に明示されている → それでもビジネス／業務要求との整合性を精査する
2. 保守フェーズで現場の声に押されて明らかになった → ビジネス要求との乖離を精査
3. 誰の目にもシステム要件とすべきもの（操作性の悪いUI改善など）→ 緊急性ゆえ着手はやむを得ないが、結果的にどうビジネス／業務要件に反映されるかは精査できるように
4. 外部要因（税制・法改正、グローバル対応、BCP、セキュリティ、データ駆動経営）→ 業務要求を通り越してシステム要求になる。優先度を上げて対応せざるを得ない

### 「要求すべてが要件になるわけではない」

- しかるべき制約の中で **実現可能な要求だけ** が要件になる。現状を含む制約を無視した理想は要件たりえない
- そもそも多くのユーザーは「システムで解決すべき要求」と「別の手段で解決すべき要求」を判別できていない（業務改革・新規事業ではとくに顕著）
- 開発者がユーザーの言うことを丸呑みして全てシステム要件に取り込もうとし、工数超過して構築できなかった例は珍しくない
- 対策：**要求を階層化し、ステークホルダーのレベルに応じて整理し、「要件となりうるか」を明確にする**
