# 0.2 本書が目指すもの

← [[0.1_システム開発における要件定義とは]] | → [[0.3_本書の構成]]

本書は ①要求のあるべき姿が明確（ToBeモデルあり）／②要求が曖昧（ToBeモデルなし）のどちらでも対応できる要件定義のあり方を示す。

## 上流工程とは？

- 一般的な定義：企画／分析／要件定義・機能定義。下流＝構築・実装・テスト
- **川の源流のメタファー**：ユーザーが本当にやりたいこと・やらねばならないことが源流。そこから流れ出す「思い」を汲み取り、整理し、枠組みと方向性・範囲を定めるのが上流工程の役割
  - 上流は源流に極めて近いところから始めるべき。遠いと源流の思いを汲み損ね、下流の流れを作れない
- 上流工程を巧く行う鍵は **コミュニケーション**。しかも「コミュニケーションの価値は受け手が決める」——送り手の独りよがりでは成立しない

### 著者による上流工程の定義

> **システムのプロと業務のプロとの間で相互翻訳作業を行い、開発対象のシステム構想を作り上げる工程**
>
> 言い換えれば、システム屋と業務屋のコミュニケーションを円滑にするためにお互いの言語を翻訳・整理し、システム構想を固めていく段階

### 「相互」であることの重要性

- システム屋が一方的に業務屋を理解するだけではダメ。業務屋にも **システムに対する自主的な理解** と、開発されたシステムをツールとして活用しビジネス価値を生む責任が求められる
- 両者がお互いの立場から必要なアーキテクチャを考え抜き、要求と要件の橋渡しを行う
- **禁句（システム屋）**：「ユーザーが要件を提示してくれないから要件定義ができない」。業務屋はシステムで何ができるか分かっていないのが普通。システム屋から積極的に働きかけ、思いを汲み取った上で、実現できることをきちんと提示する
- **禁句（業務屋）**：「こんなシステムだとは思わなかった」。夢を語ってよいのは要求段階まで。出来上がったシステムは自分たちのものであり、活用して成果を上げるのが使命
- 要件定義では「どこまでシステム化するか」の範囲と制約を明確にする

### 三カ条のセオリー

1. **安易に作りに走らない**
2. **目的を念頭において常に立ち帰る**
3. **自ら動く**

## 必要なもの：ツールと「図式」

- 上流工程では立場の異なる人間同士が関わり合う → **共通認識を持てる仕組みと、それを可能にするツール** が必要
- ここでいうツールはモデリングツールに限らず、描画ソフト・メール・掲示板・ワークフロー・MS Office など、仕事のルールや作業を支援するもの全般
- 「自然言語だけで十分」という考え方への反論：
  - 自然言語だけでは、お互いが架空のイメージを思い浮かべて共同していくことになる
  - 誰もが同じイメージを共有しているかは誰にも分からない。根拠なく「共有している」と思い込み始め、実際はズレている → **まさに騙し絵の世界**
  - 曖昧さを許す日本語は、システムの要件を整理する上ではリスク
- 解決策：**言葉だけに頼らず、目に見える図版（モデル）を共有する**。チャート図・フロー図・ダイアグラム・表など、誰が見ても同じ理解を得られる形にする
- 「作る人」と「使う人」を繋ぐのが要件。両者の相互理解を可能にする **コミュニケーションツールとして図表が必要**。表現はシンプルであるべき（立場の違う者同士の共通言語になる）

### 図：異なる立場の間で理解を促進する手段が必要

経営層（システムのオーナー）／ユーザー（システム担当）／エンドユーザー（現場責任者・現場担当者）／開発者（SE・PG）の間に双方向の矢印。それぞれの間で翻訳が必要。

### Column：ツールについて考える（要旨）

登山のピッケルのように、ツールは「使う人の目的と技量に合っていること」が重要。高価・高機能なツールを揃えることが目的化してはならない、という趣旨。

## トップダウンの重要性

- 大原則：**「トップダウンで骨組み、ボトムアップで肉付け」**。要求も要件も **ビジネス → 業務 → システム** の順に考える
- ただしトップの期待値ばかりが大きすぎると現場で使えないシステムになる。期待値を実現するには **現場を変える** しかない場合もあり、その際はビジネスの方針変更や人事的処置を行う **トップの覚悟** が問われる。システムだけでは解決できない問題
- ERP 導入による抜本的業務改革ではとくに顕著。経営陣には IT 導入以外の覚悟（ビジネス・人・組織のリソース改革）が問われる

### 要件のレベル

要求と同様、要件にも **ビジネス要件／業務要件／システム要件** のレベルがある。
- システム要件を満たしていても、ビジネス要件・業務要件を満たさなければ「役に立たない箱」。現場で使われず投資効果が出ない
- システム要件の前にビジネス要件・業務要件を満たす術を講じる → 強烈なトップダウンが必要。トップダウンなしに業務改革は成功しない。「部門長以下に丸投げ」では無理

### 部門長をリーダーにする危険

- 部門システムの開発案件で該当部門長をリーダーに任命するケースが多いが、**止めた方がよい。リーダーはトップが務めるべき**
- 部門長は自部門の利益最大化が役割。「全社最適」の視点を持っていても自部門を優先し、結果 **「部分最適」** に陥る
- 日本企業はトップダウンで決める風土が醸成されていないことが多い → その場合は、現場から吸い上げた「業務要件」を「ビジネス要件」としてまとめ上げ、再度ビジネス要件から業務要件・システム要件へ落とし込む、といった工夫が必要

## 人真似でうまくいくか？

上流工程のやり方は既に多くの書籍で紹介されているが、システム開発の失敗は減っていない。現場で「うまくいかない」5つの原因：

| # | 原因 | 内容 |
|---|---|---|
| 1 | 十分な時間が与えられていない | やるべき作業・成果物は認識しているが、実プロジェクトで時間を割けない |
| 2 | 難しくて非現実的 | 作業・成果物は理解しているが、メンバーの技術スキルが追いつかず不可能 |
| 3 | 前工程で決めるべきことが決まらない | 前工程で決められた事柄・成果物の記載が曖昧で、作業に入れない |
| 4 | やるべきことが形骸化している | 作業・成果物は規定されメンバーも理解しているが、**作業の目的が共有されておらず**フォーマットに沿って形だけ落とし込んでいる |
| 5 | やるべきことの共有が難しい | メンバーの一部は理解しているが、プロジェクト全体で共有されていない |

本書の狙いは、これら①〜⑤を解決すべく **「匠の技なしに要件定義を可能にする」** こと。
- 達人にしか使えない技は危険。実戦の場は凡人が大多数
- 理論より **実戦で有効な手段** を優先。ただし「理論あっての実践」であり、達人にも理論的に納得できるものであるべき

### Column：初太刀の面（要旨）

薩摩の示現流は下級武士が短期間で実戦力を得るため、「初太刀のみ」に集中して鍛錬した。一方、新撰組は数的優位で戦うランチェスター戦略的な手法。著者の狙いも同じで、匠でも達人でもない凡人が **シンプルでオーソドックスな手段** で目の前の敵（＝プロジェクト完遂）を倒せるセオリーを示すこと。難しい表現やモデルを極力使わないのはこのため。要件定義スキルは SE・PG 経験を生かせば習得可能。

## 要件定義における成果物

- 方針：**成果物を最小限に抑える**。「最小の管理で最高の成果を出す」
  - 管理対象が少ないほど理解が深まり管理が容易
  - 理論的に正しくても維持コストが大きすぎれば意味がない。管理対象が多いと **すぐ陳腐化** する（いつでも使える状態にメンテナンスし続けられないため）
- 主要成果物（アーキテクチャの中で）：
  1. **プロセスモデル**：ビジネスの動的側面（業務視点でのプロセス手順）
  2. **データモデル**：ビジネスの静的側面
  3. **CRUDマトリクス**：動的側面 × 静的側面の交差点
  4. （＋）**UI仕様（画面遷移）** と各概要
- これ以上多いと、システムの成長に合わせて維持メンテして **「育てる」** ことが難しくなる
