# 5.1 非機能要件の明確化

← [[4.7_CRUDマトリクス分析]] | → [[5.2_ユーザビリティ要件の明確化]]

## 非機能要件では「社会的責任」を最優先

- システムダウンに伴う業務停止について「社会的な責任」が問われる時代。公共性が高いシステムは天災でも事業継続を求められ、情報管理責任も厳しく問われる（個人情報流出 → 組織の信用失墜）
- 非機能要件となりうる「ビジネス要求」として、特に **セキュリティと BCP の実現を目的とした可用性・信頼性** が最優先。社会的要求はビジネス要求 → システム要求へのブレイクダウンを経てシステム要件として **早期に** まとめる。社会的要求により必要とされる非機能は **機能よりも先に要件化** すべき

## 非機能要件が競争優位を制する！

- IT 前提の情報システムは成熟期にあり、アプリの基本操作パターン（選択 → 入力 → 登録）はどれも変わらない。従業員向けでもコンシューマー向けでも **機能面での差別化はますます難しい** → **非機能面がサービス全体の価値を決め、競争優位の絶対条件** になる事態が生じている
- エンタープライズ系：事業継続性・情報セキュリティといった「守り」がこれまで以上に重要。社内・関連会社・パート従業員の「働きやすさ」を求める声も高まる。従来従業員が行っていた操作をお客様に委ねる例も増え、「攻め」である **ユーザビリティ** がより重要
- コンシューマー向け：非機能要件の重要度がより高くなった。ユーザビリティ・アクセシビリティ・パフォーマンス・セキュリティの強化は絶対条件。競合に勝つため「攻め」を優先しつつ「守り」もおろそかにできない
- 具体的ポイント：**「迅速な処理（操作）」「快適性」「安全性」**。迅速な処理＝性能、快適性＝ユーザビリティ、安全性＝セキュリティに起因。ここでのユーザビリティの快適性は「情報量や見栄えの良さ」による「使い勝手」の意味。セキュリティを確保しつつユーザビリティと性能がトレードオフにならないよう、**シンプルな UI** を心掛けて非機能要件を明確化

## FURPS+（フープスプラス）

著者が非機能要件整理の参考にしている、ソフトウエアの品質属性を表すモデル：

| 頭文字 | 内容 |
|---|---|
| **F**unctionality | 機能性。画面や帳票など、利用者が扱う UI と処理要求を含む |
| **U**sability | 操作性。使いやすさ。画面の使い勝手や見栄え等 |
| **R**eliability | 信頼性。システムの停止要件（停止許容時間）、障害対策（ネットワークやハードウェアの二重化など） |
| **P**erformance | 性能。オンライン処理の応答時間やバッチ処理時間など |
| **S**upportability | 保守の容易性。ハードの拡張性や互換性、プログラム保守のしやすさなど |
| **+**（Other） | 上記に当てはまらないもの。主にプロジェクトの制約。ハードウエア設置場所等の物理的制約、特定要件を満たす操作端末（防爆仕様のハンディターミナルなど）、プログラミング言語の指定、セキュリティ要件等 |

非機能要件は F（機能性）を除いた **「URPS+」** が対象。U（操作性）はコンシューマー向けで重要性が高いので 5.2 で別途説明。

## プロセスモデルから抽出

- 業務フロー図の各アイコン（業務プロセス）から必要な非機能要件を洗い出す
- 「業務フローで非機能要件を洗い出すべきではない／記述すべきでない」という意見もあるが、著者は **業務の流れの中で必要とされる非機能要件としてユーザーが認識している事項を漏れなく抽出するには業務フローが最適** と考える。わかりやすい業務フロー図は開発者とユーザーの共通言語。機能要件だけでなく非機能要件の明確化にも活用
- 具体的には業務フローの流れと **業務プロセスの 5W2H** に注目。特に月次・日次やピーク時の処理件数、新規顧客数、1件当りの処理時間等の **How many** については、ユーザーから参考情報を聞き取り、現行システムの調査に基づき新業務プロセスの処理量を想定して新システム要件として定義。あくまで想定だが非機能要件をまとめる参考になる
- ピーク時の処理想定も 5W2H を基に。特にコンシューマー向けはビジネス要求に遡ってシステム要件として満たすべき非機能要件を想定・定義

### 5W2H と非機能要件の関係

| 5W2H | 例 | 関係する非機能 |
|---|---|---|
| **When**（実施タイミング） | 「24時間随時」——エンタープライズ系ではグローバル展開システムであればありうる／コンシューマー向けでは当たり前 | 信頼性、保守の容易性 |
| **Where**（場所、組織） | 「事務所」「倉庫」「外出先」——エンタープライズ系はデスクワークだけでなく倉庫・外出先での作業もありうる／「場所を問わず」——コンシューマー向けでは当たり前 | 操作性、性能、その他 |
| **Who**（担当者、一般ユーザー） | 「該当部署担当者」「窓口パート社員」「協力関連会社担当者」——エンタープライズ系は社員だけでなくパート、協力会社担当者に開放するケースも／「一般ユーザー」——コンシューマー向けは誰がユーザーになるか分からない。セキュリティに留意 | 操作性、性能、その他 |
| **How**（実施要領） | 「該当システムに入力することにより」——エンタープライズ系は When・Where・Who との組み合わせを考慮。基本的な項目入力だけでなく AI・IoT を通じたデータ操作も想定（その他にも関係）／「該当 UI に入力することにより」——コンシューマー向けは When・Where・Who が広範囲で実施要項も多岐。ペルソナを中心に想定しうる状況に対応。入力デバイスは PC・スマートフォン等日々増加 | 操作性、性能 |
| **How many**（データ量、応答時間） | 「XXX／D」——エンタープライズ系では該当機能の性能の目安。業務プロセス定義ではユーザー視点の数値目標が定義されている。それとともに想定しうる技術視点の数値も想定／「0.XS 以内 XXXXX/d」——コンシューマー向けでは応答時間と処理件数の目安 | 性能、その他／操作性、性能、保守の容易性、その他 |

業務プロセスから非機能要件を洗い出す場合、まずあくまで **「業務視点」「ユーザー視点」** からまとめ、客観的・技術的数値に落とし込んでいく意識が重要。

### Column：応答時間の感覚の違い（要旨）
窓口受付業務システムで「応答時間3秒以内」という話が出たが、お客様と対峙しながら使う窓口では3秒は永遠に近い。机上の数値と現場の体感には開きがある。バッチなら「翌朝オンライン起動までに終了」が合意しやすいが、「障害発生時でも翌朝の業務再開を可能とするか」等の例外対応も合意しておく必要。合意事項は一度決めると覆すのが容易でない。UI を伴わないバッチでもユーザーシナリオを元に業務要件を優先して決める。**システム要件というよりビジネス要件・業務要件に関する合意** が必要。

## 性能をどう数値化するか？

- ユーザーの聞き取りだけを頼りに決定するのは危険。**開発者が「一般的に想定される性能」をきちんと把握した上で** 数値化目標を決める。間違っても先にユーザーに聞き取りをしてはいけない。ユーザーは実際に操作するのが自分だとしても感覚的に捉えているケースが多い。**開発者が指針を出した上でユーザーとの合意に至る** 形が理想
- 例：コンシューマー向け Web でボタンをクリックして数秒間何も動かないようでは話にならない（今日では一般常識）

## プロトタイプからの非機能要件抽出

ユーザビリティ要件を明確化するために、「UI・機能要件の明確化」で作成したプロトタイプと画面遷移図を使用。注意点は **設計レベルの議論に深入りしない** こと。あくまで非機能要件としてまとめる意識を持つ。

## 移行要件を甘く見ない

- 移行要件は URPS+ の分類では「その他」扱い。非機能要件を整理する際、移行要求をどう要件化するかもきちんと検討。AsIs → ToBe を作り上げる過程でも検討。ユーザーの要求としては当たり前であるにもかかわらず埋もれてしまい、後々問題になることがある。移行要件をきちんと明確化する
- 具体的にはまず **データ移行**。データ要件の明確化で作成した概念／論理データモデルのうち、データ移行が必要と思われる **移行先エンティティ** を抽出し、移行元である現行システムのファイルと項目の特定、移行機能の概要を検討
- 移行は一度に実施できるのか、複数回に分けるのか、システム上と業務上の制約を考慮して現時点でわかる範囲でまとめる

## 仕様継承の際の非機能要件とは？

現行仕様を継承する際の非機能要件の扱いは要注意。エンタープライズ系でアーキテクチャに変更が生じる場合でも、特に **レスポンス（性能）が現行より劣化するようではユーザーは受け入れない**。コンシューマー向けでは、より使いやすくならない限り一般ユーザーは離れていくだけ。アーキテクチャの選定を含め熟考が必要。

## 手順：「非機能要件の明確化」

1. **「社会的責任」になりうる非機能要件の明確化**：要件定義の前工程で「ビジネス要求」の中で企業組織の社会的責任を全うするために必要と思われる事項を「システム要求」として整理した。社会的責任を最優先事項として実現性を考慮しつつ要件化
2. **業務プロセスの定義から非機能要件の明確化**：業務フロー図の「業務の流れ」および個々の業務プロセスの定義から、各プロセス単位の非機能要件を抽出
3. **その他非機能要件の明確化**：移行要件等、プロセスから抽出できない非機能要件を明確化。移行要件は **ToBe と AsIs の差異** から洗い出す。基本はデータ移行の要件を中心に。漏れチェックのため類似プロジェクトがあれば参考に。特に **古いデータを本当に移行する必要があるのか** 熟考（例：「5年間取引のない顧客および取引データを移行対象とするか」）
4. **トレードオフ関係にある非機能要件の整理**：明確化された非機能要件のうちトレードオフ関係のものを抽出し、ある程度の両立が可能か、そうでない場合はどちらを優先するかを決定
5. **非機能要件定義書の作成**：以上の非機能要件をプロセス単位と機能単位に一覧にし、最終的には目安で構わないのでシステムで実現すべき目標を **数値化**（例：「応答時間○秒以内」「同時登録可能な件数最大○件」）。数値化は「ユーザー視点」「開発者（技術者）視点」で行う。一覧表にして非機能要件定義書としてまとめる。現時点で想定しうる **実装方式の概要・方針** までを記述
