# 3.1 システム化企画／業務分析

← [[要件定義のセオリー_MOC]] | → [[3.2_要求の明確化]]

## 要件定義の前に

本来「システム化企画」「業務分析」は要件定義の前に終了していることが前提。業務分析／新業務定義で行うべき作業は2つ：
- システム企画に基づく **ToBe モデル（あるべき姿）** の策定・作成
- **AsIs モデル** の作成

- システム化企画：ビジネス視点から今回の開発の **投資効果・目的・方向性** を明確にする（「超上流工程」とも呼ばれる）
- 業務分析：システム化企画を基に ToBe モデルを作成し、現状分析で作られる AsIs モデルを参考に ToBe 新業務の形を想定可能にする
- 要件定義の本来の内容：システム化企画と業務分析で明確になった要求を基に ToBe モデルを作成、そこから **AsIs モデルと制約を踏まえて要件として整理し、新しく ToBe モデル化** する

```
①元ToBeモデル ──→ ③新ToBeモデル ← 要件定義で行う作業
      ↓（参考）        ↗
②AsIsモデル ＋ 制約
```
①②の作成までが要件定義の前に行うべき作業、③が要件定義で行う作業。

## まず手始めに…目的の確認

- システム開発には必ず「目的」（何のために作るのか）がある。まずそれを明確にする
- 可能な限りあらゆるドキュメントを収集：エンタープライズ系なら **業務規定集・マニュアル** 必須、コンシューマー向けなら **ビジネス企画書** など。現行システムのドキュメントがあれば参考にする
- ドキュメントに目を通した上で、ステークホルダーとなりうる人・組織トップ・業務責任者・業務担当者に **インタビュー**。最低限聞き出す項目：
  - 「目的」
  - 「対象」
  - 「効果」：期待する定性効果／定量効果と投資回収期間
  - 上記3点を踏まえた新システムイメージ
  - システム以外の組織・役割のイメージ
- 結果は一覧形式でまとめる。これらは新規開発時だけで構わない。保守・修正では大きな方針変更を除きある程度省略可

## 調査

- インタビュー前に最低限、対象「業界」の最近の動向を調査する。ユーザーに明確な考えがない場合は、インタビューする側から業界動向を踏まえた提案を行う必要がある
- インタビュー後も内容の精査目的で追加調査を行うことがある

## 要求の整理

インタビュー・調査結果を踏まえて要求を整理し、新たなビジネスモデルやシステム化企画となりうるかを検証。

## システム化計画

- 新規システムの場合、**目的・対象・効果** の3つを明確にする。A3用紙の中央にシステムを描き、周りに関係のあるインフラ・顧客等を制限なく描き出す（**ラフなポンチ絵**）
- 保守フェーズの修正案件では、今回の開発が新規開発時に策定した目的・方向性とずれていないか確認
- エンタープライズ系では「システム化計画 → 要求 → 要件」を明確にトレースできるよう整理する必要があるが、コンシューマー向けは計画から要求・要件の時間軸が短いため時間をかけてはいけない（アジャイル適用時は特に顕著）
- ポンチ絵で新業務イメージをまず認識し、「目的」「対象」「効果」を明確化。このポンチ絵は現場から要件を抽出する際の大きな武器になる。ラフでよいので目的を理解しやすいよう工夫する
- コンシューマー向けの「効果」はビジネス価値とイコールの場合が多く、「売上増大」等を目指して早期リリースを最優先。エンタープライズ系は数年のシステムライフサイクルで投資回収できれば OK。何を最優先にするかで新システムイメージをどこまで整理するかが変わる

## ToBe モデルの作成

- 新ビジネスモデルを基に ToBe モデルの作成を開始。**プロセスモデルとデータモデルの概要** を描くことから始める。最初はかなりラフ
- この工程に時間をかけて ToBe プロセスモデル・データモデルを実際の業務レベルまで想定可能な状態に落とし込めば、要件定義を含む後工程の工数はかなり軽減される。逆にいい加減に終えると後工程に皺寄せ
- 保守フェーズの修正案件：現行システムの **システム全体図・データモデル・プロセスモデル** があればよい。なければ修正対象を明確にするためシステム全体図を作成し、システム全体の中で修正対象機能の位置づけ、連携の有無が分かるレベルを目指す
- プロセスモデル：開発対象システムに関連する大きな括りのプロセスの **概要フロー図** をラフで作成。一般的なビジネスの階層構造に沿って上位から下位へ階層化。細かい点に気を取られる必要なし。**最上位階層ともう一つ下の階層レベル** まで描く
  - 例（EC）：お客様／社内／仕入先のレーンに、注文 → 注文形態（BtoB／BtoC）→ 販売 → 受注 → 在庫・調達・購買、顧客管理・財務会計・分析調査、といった流れ
- データモデル：「概念データモデル」をラフに作成。概念データモデル ＝ **エンティティ（実体）同士の関係を定義するもの**（属性は表さない）。エンティティはビジネスで把握すべき管理対象。特に今回開発対象システムの **外部接続の有無、他機能との連携、影響範囲** が分かるようにする
  - 例：顧客 —（を行う）— 注文 —（明細として持つ）— 注文明細 —（対象となる）— 商品、注文 —（指定する）— 注文請求先
- 修正案件でモデル作成時、いきなりユーザーに聞き取りする技術者がいるが止めた方がよい。**深みにはまる**。ユーザーは業務視点でしかシステムを見ておらず、今回対象でない問題が表面化して優先順位の整理がつかなくなる

## 現状分析

- AsIs 分析の目的は業務の現状把握。著者の考え：**全くの新規システム開発では現状分析に時間をかけるべきではない**。現状は参考情報。特に AsIs 業務フローの作成に時間をかけるのは無駄
- 要件定義では元 ToBe モデルを前提に、制約としての AsIs モデルを参考にする。AsIs 業務フローよりむしろ **現行システムに関する以下の情報** を押さえる：

### (1) 非機能要件
データ更新・業務処理の頻度、処理速度・応答速度、データ量、ユーザビリティなどを、現行ドキュメントや UI ハードコピー等から洗い出す。現行がない場合は担当者から聞き取り。**非機能要件が要件定義で埋もれると、システムテストまで問題を先送りして後々大問題になる**

### (2) データ構造
概念データモデル、データライフサイクルが把握可能なもの（＝CRUD マトリクス等）。なければドキュメントを基にデータ構造概要が把握できるラフな AsIs 概念データモデルを作成

### (3) コード体系
現状分析で **一番時間を割くべき**。現行コード体系には現行ロジックがたくさん詰まっている。特に **「意味ありコード」**（例：取引先コードの頭3桁が地域を表す）は要注意。コード設計書があれば参照、なければ項目名に「…コード」「…区分」「…フラグ」がついた項目を抽出し、アプリケーションの目星をつけてロジックを調査するしかない

- もう一つ大切なのは「現行システム」以外の部分、ビジネスや業務に近い部分。エンタープライズ系なら **組織図・分掌規程** に目を通す。業務フローからは分からないビジネスルールが浮かび上がることがある

## 現状問題点の認識

- エンタープライズ系の修正では、現行システムの業務上の不具合を基に要件がまとめられることがある。そうした要求が要件になった場合、それが抜本的な経営課題の解決にならないこと、それでも現場として行わなくてはならないことを、**「目的」と「効果」の観点から整理** しておく
- 現場からの「業務要件」「システム要件」の度合いが強く、高い視点での効果がすぐには見えにくいケースは要注意。計画通り完遂しても成功とみなされないことがある
- 現場の声を吸い上げて業務要件・システム要件を定義する際、高次の「ビジネス要件」と食い違いが生じないように、両者がトレースできるよう繋がっていなければならない。そうしておけば経営視点からもシステムの効果を確認できる

## 手順：システム企画／業務分析

1. **目的の確認**
2. **調査（インタビュー）**
3. **要求の整理**
4. **システム化計画の立案**
5. **ToBe モデルの作成**
6. **現状分析 〜 AsIs モデルの作成**

### 実施作業の場合分け

| | 新規 | 修正 |
|---|---|---|
| エンタープライズ系 | ❶ | ❸ |
| コンシューマー向け | ❷ | ❹ |

- ❶ 具体的手順を全て行う
- ❷ 時間をかけずに目的を明確化。エンタープライズ系への影響が低く他システム連動がなければ AsIs 分析は省略し、ビジネス価値に焦点
- ❸ ビジネス要求の変更・サブシステム単位の修正 → システム全体の目的からブレていないか確認し、既存システム連携・外部接続を意識して整理。業務要求の変更・プロセス単位の修正 → システム全体との整合性を意識して追加・修正対象プロセスの位置づけを明確化。システム要求の変更・機能レベルの修正 → 想定機能の位置づけのみ整理
- ❹ プロセス・機能のまとまり単位で大幅修正 → ❸同様。プロセスレベルの修正 → ある程度の規模の場合に限りエンタープライズ系同様。機能レベルの修正 → 想定機能の位置づけのみ整理
