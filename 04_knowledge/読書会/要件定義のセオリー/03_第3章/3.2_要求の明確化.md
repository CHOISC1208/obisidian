# 3.2 要求の明確化

← [[3.1_システム化企画・業務分析]] | ↑ [[要件定義のセオリー_MOC]]

3.1 でまとめた「目的」「対象」「効果」を基に要求を明確化する。新ビジネスモデルと ToBe モデルを参照し、要求を3種類に分類・整理するとともに ToBe モデルをブラッシュアップする。

- **ビジネス要求** ＝ トップダウンの要求
- **業務要求** ＝ 業務レベルの要求
- **システム要求** ＝ システムレベルの要求

新システムイメージから要求を抽出し、3種に分類して **「要求分類一覧表」** にまとめ、併行して ToBe モデルをブラッシュアップする。

### 要求分類一覧表の項目
管理No. ／ 発生部署 ／ 日付 ／ 要求分類（ビ・業・シ）／ 対象業務 ／ 要求（内容・目的）／ 元管理No. ／ ランク（重大・緊急・拡大・総合）／ 状態

## 要求のブレイクダウン

- ①「ビジネス要求」→「業務要求」、②「業務要求」→「システム要求」へブレイクダウンし、それが業務要求・システム要求になりうるかを分析。**①②のトレースが可能な形** でブレイクダウンするのが理想
- 例：
  - ビジネス要求：マルチチャネルによる顧客接点の増加、顧客・売上増加、必要リソース（人・モノ・金）の配置
  - 業務要求：ユーザシナリオの確立、少数精鋭スタッフによる業務フロー・業務プロセスの確立
  - システム要求：必要なデータ要件とプロセス要件の確立、プロセス要件を満たす機能・UI の構築
- **無理にブレイクダウンしない**。ビジネス要求を無理にシステム要求へ落とすのは、本来システムで解決すべきでないビジネス課題を強引にシステム化で解決しようとすること
- どうしてもブレイクダウンできず実現を要する要求は、「ビジネス要求 → ビジネス要件」「業務要求 → 業務要件」の形で **システム要件以外の要件** として整理
- どうしても要件化できない要求は **差し戻し（先送り）**
- この時点で以下3つをきちんと分類することが重要：
  1. システム要求としてブレイクダウンされた要求
  2. システム以外の要件となりうる要求
  3. 差し戻し対象の要求
- エンタープライズ系はやや長めのライフサイクル全体で企業組織として要求がどうあるべきかを考える。コンシューマー向けはビジネス直結の俊敏性が求められ、システム要求にブレイクダウンする比率が高まる。半完成品でも早くお客様に触れさせ評価されることでさらなる要件が生まれる
- 「何がしたいのか」が不明確ならそこから明確に。この時点で詳細に踏み込んで必要以上に時間をかけない。煮詰まったら **「概要でよい」と割り切る**。方向性さえ見失わなければよい
- 業務要求 → システム要求へブレイクダウンする要求には、通常の機能以外に **ユーザビリティ、移行要求** 等がある。ビジネス要求から業務要求を通り越してシステム要求になるものもある

## 要求と現実性

- 現在の技術では実現不可能な要求もある。それを「システム要求」に分類するのは危険
- 例外：経営判断で「業界にかつてない仕組み」「世界最先端の仕組み」を構築する強い意志があれば、システム要求にブレイクダウンして要件化すべき（ビジネス要求をシステム要求として整理）。この場合「人・モノ・金」の経営リソース調達を考える必要
- そこまでの意思がなければ「技術的困難」を理由にこの時点で要求から除外
- 時間・コスト（予算）の制約で除外せざるを得ないものも多い。実施するなら期間やコストを追加する覚悟が必要

## ToBe モデルのブラッシュアップ

要求を満たすモデルとしての ToBe モデルを作成（修正）：
- ビジネス要求 → システム化企画含むビジネスモデル
- 業務要求 → 要求に伴う制約まで明確になったプロセスモデル、データモデル
- システム要求 → UI、機能／非機能

プロセスモデル・データモデルは後述の「プロセスモデルとしての業務フロー」「概念データモデル」の作成を通じて作られる。この時点で明確になった要求が反映されたモデルを目指す。

## 手順：要求明確化

1. **ビジネス要求・業務要求を把握する**：システム化企画・ToBe モデルから「ビジネス要求」となりうるものを改めて抽出。現場をないがしろにしないが **トップダウンの「意思」を優先**。ビジネス要求を整理した上で業務要求へブレイクダウン（この段階で各部署・現場の要求を取り込む）。ブレイクダウンした業務要求を ToBe モデル・プロセスモデル・データモデルに反映
2. **要求の発生源を明確にする**：現場からの要求度合いが強い「業務要求」について発生部門・担当者を明確に。その要求を満たすことが経営課題解決に繋がるものを優先事項としてチェック（業務要求から遡りビジネス要求との整合性を確認し、ビジネス要求たりうるものを優先）
3. **要求の背景にある課題・問題点を明確にする**：ビジネス要求・業務要求について、発生した原因や理由を明らかに
4. **システム要求への落とし込み**：優先順位を参考にビジネス要求・業務要求から「システム要求」へ落とし込む。経営視点・現場視点・システム視点の多方面から検討した後に行う。システム要求を基に必要な UI・機能／非機能への対応を検討
5. **要求のランク付け**：システム要求として洗い出した時点で、以下の評価基準で重要度を5段階（5が最重要）にランク付け。ランク後、優先順位の高い要求の UI・機能／非機能を多面的に検討
   - 経営およびビジネスに与える影響の大きさ
   - 緊急度
   - 課題解決に要する規模など
6. **要求の階層化を整理する**：要求がビジネス／業務／システムにきちんと分類されているか、ブレイクダウンした事項が整合性を保っているか、経緯とともにトレーサビリティ可能になっているか確認。ToBe モデルが各要求を反映しているかも確認

- エンタープライズ系もコンシューマー向けも洗い出し方は変わらないが、コンシューマー向けはリリースまでの時間短縮を求められるため、必要最低限の要求をスピーディに開発まで持っていく
- ビジネス要求は不変で業務要求・システム要求レベルの修正の場合、ビジネス要求との整合性をとりつつ速やかにシステム要求を明確化

### 実施作業の場合分け

| | 新規 | 修正 |
|---|---|---|
| エンタープライズ系 | ❶ | ❸ |
| コンシューマー向け | ❷ | ❹ |

- ❶ 具体的手順を全て行う
- ❷ 時間をかけずに要求の洗い出し。緊急度が高い場合、優先順位付けより **要件化を併行して** 実装までの時間を短縮
- ❸ ビジネス要求でサブシステム単位の修正 → 全体目的からのブレを確認して整理。業務要求でプロセス単位の修正 → 全体整合性を意識して追加・修正対象のプロセス・データの要求を明確化。システム要求で機能レベルの修正 → 想定機能の位置づけのみ整理
- ❹ プロセス・機能のまとまり単位でビジネス要求レベルの大幅修正 → ❸同様。業務要求でプロセスレベルの修正 → ある程度の規模の場合に限りエンタープライズ系同様。システム要求で機能レベル → 想定機能の位置づけのみ整理
