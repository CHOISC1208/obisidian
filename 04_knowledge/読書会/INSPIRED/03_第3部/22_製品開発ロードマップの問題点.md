# 第22章 製品開発ロードマップの問題点

← [[00_第3部の概要]] | ↑ [[INSPIRED_MOC]] | → [[23_ロードマップに代わるもの]]

製品開発ロードマップが残念な結果で終わる理由を、**製品開発に関する2つの不都合な真実**として説明する章。

## 第1の不都合な真実

**製品開発のアイデアの半分以上はうまくいかない。** 成功しない理由は、第9章の4つのリスクに対応している。（→ [[07_リーンとアジャイルを超えて]]）

| 欠けているもの | どうなるか |
|---|---|
| **価値の欠如** | **顧客が開発側ほどそのアイデアに心を動かされず、製品を選んだり買ったりしてくれない。これは最もよくある状況** |
| **ユーザビリティーの欠如** | 顧客が製品を使いたいと思って試してみても、**あまりにも操作が複雑なので製品の価値よりも煩わしさが上回り、ユーザーが使わない** |
| **実現可能性の欠如** | 市場に出ていれば顧客が気に入ったかもしれないのに、**製品の開発が当初の想定よりもはるかに複雑なことがわかり、市場投入するための時間や資金がなくなる** |
| **事業実現性の欠如** | **重大な法律的、金銭的、あるいはビジネス上の制約に直面して、発売早々そのソリューションの提案が阻まれる** |

## 第2の不都合な真実

- **アイデアに価値があり、ユーザビリティーや実現可能性や事業実現性があると証明されたとしても、それだけでは不十分。**
- **通常、そのアイデアを実現し、経営陣が望む事業期待値が得られるレベルまでもっていくには、数回の繰り返しが必要になる。そのための時間はしばしばタイム・トゥ・マネーと呼ばれる。**

> 私の経験では、決してこれらの不都合な真実から逃れることはできない。（中略）そうしたチームがほかと違ったのは、不都合な真実への対処の仕方だった。

## 能力のないチームと有能なチームの違い

| | 不都合な真実への対処 |
|---|---|
| **能力のないチーム** | **与えられたロードマップにしたがって毎月毎月ただこつこつと仕事をする。** やがて不具合が起きたら、**まずその機能を要求したステークホルダーのせいにし、ロードマップにイテレーションを追加するか、今度は問題を解決できるだろうと期待して設計のやり直しや別の機能セットを提案する。** 十分な時間と資金があればやがて目的を達成するだろうが、**経営陣の忍耐力が尽きなければという（まずあり得ない）大前提付き** |
| **有能なチーム** | **不都合な真実を理解し、否定するのではなく受け入れる。（アイデアがどこで生まれたのかに関係なく）即座にリスクに取り組み、有効なソリューションに向けて迅速にイテレーションを実行する** |

> これこそが製品発見のあるべき姿だ。そして、製品発見が製品開発組織の最も重要な行動特性だと私が考える理由である。

- **数週間とか数カ月ではなく数時間か数日のうちに、アイデアのプロトタイプを作り、ユーザー、顧客、エンジニア、ビジネスステークホルダーに向けてテストができるなら、新たな力が生まれ、何よりも重要なことに結果が変わる。**

## 本当の問題は「アイデアのリスト」ではない

- **問題となるのはロードマップに記されたアイデアのリストではない。アイデアだけならば大した害はない。**
- **本当に問題なのは、「ロードマップ」と題された文書にアイデアのリストを書いた途端、どれだけ多くの免責事項が書かれていても、会社中の人々がそれらの項目を約束事項として理解してしまうことである。**
- **問題の核心はそこ。なぜなら、製品が本質的な問題を解決しないにもかかわらず、その製品を作って市場投入することの責任を製品開発チームが負わされてしまうからである。**

## 期日の約束が必要な場合

- **市場投入を指定された日時でおこなう責任が発生する場合も確かにある。そうしたケースをできるだけ減らそうとしても、完全になくすことは難しい。**
- **だから、ハイインテグリティーコミットメント（誠実性の高いコミットメント）と呼ばれるものを作る必要がある。**（→ [[COLUMN_ハイインテグリティーコミットメント]]）
- **今、理解してほしい重要な点は、私たちは本質的な問題を解決する必要があるということだ。ただ機能を提供すればいいのではない。**
