# 製品発見のテクニック早見表

↑ [[INSPIRED_MOC]]

> [!info] **これは深掘りノートである。** 本書は発見のテクニックを第4部の20章以上に分散して書いており、章別ノートのままでは「このリスクを今すぐ確かめたい」ときに探せない。**「どのリスクに、どのテクニックか」を案件中に引くために並べ直したもの**である。
> **横断範囲は第4部の第33〜56章と `COLUMN_倫理…` 〜 `COLUMN_ユーザーテストvs…` に限る**（指示書 7 で許可された範囲）。ほかの部の内容は入れていない。

## 出発点: 4つのリスク

製品発見の目的は、次の4つのリスクに対処すること。**ただしプロダクトマネジャーが意見を述べるだけでは足りず、エビデンスを集める必要がある**（第33章・電子版 p.95）。

| リスク | 問い |
|---|---|
| **価値** | 顧客はこれを買ったり、これを使うことを選んでくれるか |
| **ユーザビリティー** | ユーザーはこれの使い方がわかるか |
| **実現可能性** | 私たちはこれを作れるか |
| **事業実現性** | このソリューションは私たちのビジネスに貢献するか |

- **最も重要かつ一番難しいのは価値の確立**で、**発見に使う時間の大部分をここに注ぐ必要がある**（第33章 原則2・p.95）。
- **多くの開発チームは、最も取り組みやすいリスク（技術・ユーザビリティー）に引き寄せられる**（第4部「発見のフレーミングテクニック」概要・p.101-102）。**価値のリスクとビジネスのリスクを落とさないこと。**
- **著者の見立てでは、製品開発の仕事が直面している最大のリスクのほとんどは価値のリスクである**（`COLUMN_最大のリスク`・p.109-112）。

## 1. リスク → テクニックの早見表

| 確かめたいこと | 使うテクニック | 出典 |
|---|---|---|
| **そもそも需要があるか**（作る前に） | **フェイクドア需要テスト**（UIにボタンを置き、押すと「検討中・相談に乗ってくれる顧客を探している」ページへ）／**ランディングページ需要テスト** | 第52章・p.141-143 |
| **需要があるかの第1段階の現実性チェック** | **顧客発見プログラムで4〜5社すら集まらないなら、それほど重要でない問題を追いかけている** | 第39章・p.113-118 |
| **価値があるか（理由まで知りたい）** | **定性的価値テスト。** お金・評判・時間・アクセス情報のどれかを「代価として払う気になるか」で測る | 第53章・p.145-148 |
| **価値があるか（証拠・証明が要る）** | **定量的価値テスト。** A／Bテスト（発見用は現行99%・プロトタイプ1%以下）／招待制テスト／顧客発見プログラムのメンバー | 第54章・p.148-150 |
| **ユーザーが使い方をわかるか** | **ユーザビリティーテスト**（高忠実度ユーザープロトタイプ＋現実のユーザー） | 第50章・p.136-140 |
| **エンジニアが作れるか** | **実現可能性プロトタイプ。** 聞き方は「できるか」ではなく「**一番いい方法は何で、どれくらいの時間か**」 | 第46章・p.131-132／第55章・p.153-155 |
| **ビジネスが許すか** | **事業実現性テスト。** 8つのステークホルダーごとに、ビルド前に高忠実度プロトタイプで膝を交えて確認 | 第56章・p.156-159 |
| **倫理的に作ってよいか** | **「それを作ってもいいのか？」を明示的に問う。** 重大な倫理的リスクがあれば別のソリューションを探る | `COLUMN_倫理…`・p.97-98 |
| **顧客の仕事そのものを知りたい** | **コンシェルジュテスト**（顧客の仕事を自分が代行する）／**顧客インタビュー**（毎週2、3時間） | 第42章・p.124-125／第41章・p.122-124 |
| **アイデアの数が足りない** | **方向性のあるハッカソン**（問題か目標を示し、やり方はチームが決める） | 第44章・p.127-130 |
| **予期しない使い方に機会がないか** | **顧客による不適切な使用の観察**（eBayの「Everything else」）／**パブリックAPIで開発者に開く** | 第43章・p.125-126／`COLUMN_開発者による…`・p.126-127 |

## 2. テストの順序（原文が示す論理）

**決まった手順はないが、多くのチームは次の論理にしたがう**（第4部「発見のテストテクニック」概要・p.135-136）。

1. **価値を評価する。** 最も難しく最も重要で、**価値がないとなったらほかの問いはもはや問題にならない。**
2. **ただしユーザーが価値を理解する前にユーザビリティーへの対処が必要になることがある。** その場合は**同じユーザーを対象に、ユーザビリティーと価値を同時に評価する。**
   - **価値テストは常にユーザビリティーテストのあと。それも時間を空けてはならない**（第53章・p.145）。**使い方を学ぶ機会を与えずに価値を聞くと、フォーカスグループになってしまう。**
3. **エンジニアと一緒にアプローチを再検討し、技術的な実現可能性を確認する。**
4. **最後にビジネスのリスク**（法務・マーケティング・販売・CEOなど）。**やってみる価値があるという自信がないかぎり組織を混乱させたくないから、これが大概最後になる。**

- **多くの仕事ではこれらの答えはほぼ明快でリスクが少ない。** 発見の時間と検証テクニックは、**重大なリスクがあるとわかっている状況や、チームの意見が一致しない状況**で使う（p.101-102）。

## 3. プロトタイプの選び方

**すべてのプロトタイプは、最終的な製品より少なくとも1桁少ない時間と労力で実行できなければならない**（第45章・p.130-131）。

| プロトタイプ | 誰が作るか | 何に向くか | 向かないこと | 出典 |
|---|---|---|---|---|
| **実現可能性プロトタイプ** | **エンジニア**（コードだから） | 技術リスク（アルゴリズム・性能・拡張性・未使用の技術やレガシー・依存）。**使い捨て前提で1〜2日** | 顧客に見せること | 第46章・p.131-132 |
| **ユーザープロトタイプ（低忠実度）** | デザイナー | **情報とワークフロー**の検討。インタラクティブなワイヤーフレーム | ビジュアルの効果・実データの影響 | 第47章・p.132-133 |
| **ユーザープロトタイプ（高忠実度）** | デザイナー | **ユーザビリティーテストと価値テストの標準装備。** ステークホルダーへのウォークスルーにも | **何かを証明すること**（10〜15人が気に入っても立証にならない） | 第47章・p.132-133 |
| **ライブデータプロトタイプ** | **エンジニア** | **実際の利用データの収集**（検索結果の精度・ゲームの挙動・ファネル分析）。**製品化作業の5〜10%** | **ピーク時に耐えないのでビジネスには使えない** | 第48章・p.133-134 |
| **ハイブリッド（オズの魔法使い）** | PM＋エンジニア | **裏側を人間が手作業でやる。** 素早く作れて、ユーザーには本物に見える | 大量のトラフィック | 第49章・p.134-136 |

- **忠実度に最適値はない。目的に合ったレベルにし、必要なときだけ高忠実度を使う**（第45章 原則4）。
- **プロトタイプを作る行為そのものが、作らなければずっとあとまで見つからない問題を顕在化させる**（第45章 原則2）。

## 4. 規模別のフレーミング

**発見の仕事の大半はフレーミングを必要としない。** 大規模なプロジェクトやイニシアチブが例外（p.101）。

| 仕事の規模 | テクニック | 中身 | 出典 |
|---|---|---|---|
| **簡単な最適化〜中規模の機能** | **市場機会評価** | **4つの質問**（①どのビジネスの目標か ②何をもって成功とするか ③顧客のどんな問題を解決するか ④どんな顧客をターゲットにするか）。**答えは2、3分で出るが、チームとステークホルダーで共有すること**が本体 | 第35章・p.104-106 |
| **大きなプロジェクト・構想**（デザインの見直しなど） | **カスタマーレター** | **顧客がCEOに送った感謝の手紙＋CEOからチームへの祝いのメッセージ**を先に書く。Amazonの仮想プレスリリースの発展形 | 第36章・p.106-108 |
| **まったく新しい製品ライン・新規事業** | **スタートアップキャンバス** | 旧式な事業計画書の代わり。**ただしキャンバスにはソリューションがほとんど表現されないので、安心して扱えるリスクだけに注目してしまう罠がある** | 第37章・p.108-109／`COLUMN_最大のリスク` |

- **複数併用してよい**（市場機会評価とカスタマーレターの両方など）。
- **どのフレーミングでも、根底にある問題よりソリューションから考えたがるのが人間の性質**である。**ソリューションではなく問題に恋をする**（`COLUMN_問題vsソリューション`・p.103-104）。

## 5. プランニング（発見の進め方を計画する）

| テクニック | 使いどころ | 出典 |
|---|---|---|
| **ストーリーマップ** | **バックログに文脈を与える。** 水平軸＝主要なユーザーアクティビティーを時間順、垂直軸＝詳細さのレベル。**どこでリリースを切るかを考えられる。** プロトタイプのフレーミングにも、発見後のバックログ移行にも使える | 第38章・p.112-113 |
| **顧客発見プログラム** | **1つのターゲット市場で6つ（候補は6〜8）のリファレンスカスタマーを開拓する。** 著者は**どちらか1つを選ぶならこれを推奨**し、**将来の成功の最良の先行指標**と位置づける | 第39章・p.113-118 |

- **6つのリファレンスカスタマーを獲得するまで製品を市場に出さない**（第39章）。**それが達成されれば、その市場のプロダクト・マーケット・フィットを達成したと言える**（`COLUMN_プロダクト・マーケット・フィットを定義する`・p.118-119）。
  - **コンシューマー向けなら、ショーン・エリス・テスト**（「製品が使えなくなったらどう感じるか」で「非常に残念」が40%超）。**ビジネス向けには著者は使わない。**

## 6. 速さの基準（原文が挙げている数値）

| 何を | どれくらい | 出典 |
|---|---|---|
| 発見のイテレーション | **週10〜20回。市場投入のイテレーションより少なくとも1桁少ない労力** | `COLUMN_製品発見のイテレーション`・p.98-99 |
| 顧客インタビュー | **最低限、毎週2、3時間** | 第41章・p.122 |
| 定性的価値テスト | **少なくとも週2、3回** | 第53章・p.145 |
| 実現可能性プロトタイプ | **1〜2日**（新技術の評価ならもっとかかる） | 第46章・p.131 |
| ライブデータプロトタイプ | **2日〜1週間** | 第48章・p.134 |
| 市場投入の質問への対応 | **1日30分〜1時間** | 第4部の導入・p.92 |

## 7. 大企業で使うときの制約

**発見のテクニックはスタートアップ専用ではない**（`COLUMN_リスクを嫌う企業での製品発見テスト`・p.143-145）。ただし2つを守る。

- **収益とブランドを守る** — **把握している顧客の1%以下を対象にしたA／Bテスト**が多くの場合有効。もっと慎重にすべきときは**招待制のライブデータテスト**か**機密保持契約をした顧客発見プログラムの顧客**を使う。
- **従業員と顧客を守る** — **顧客への影響の評価を考慮した穏やかなデプロイテクニック。継続的デプロイは適切に使えば顧客を守るツールになる。**
- **計装がなければ新機能を公開しない**（`COLUMN_計器飛行する`・p.152-153）。**データは何が起こっているかを示すが、なぜ起きているかは説明しない。定量の結果を説明するには定性のテクニックが要る**（`COLUMN_分析の役割`・p.150-152）。

## 8. 見せ方を混同しない

**プロトタイプを見せる行為には3種類ある**（`COLUMN_ユーザーテストvs製品デモvsウォークスルー`・p.159-160）。

| | 誰が操作するか | 目的 |
|---|---|---|
| **ユーザーテスト** | ユーザー | ユーザビリティーと価値をテストする |
| **製品デモ** | PMまたはプロダクトマーケティングマネジャー | **説得**（販売・社内への普及） |
| **ウォークスルー** | PM（ステークホルダーが望めば本人） | **ステークホルダーに問題を見つける機会を与える。何も隠さない** |
