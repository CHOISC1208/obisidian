# 第6章 製品開発が失敗する根本的原因

← [[05_エンタープライズ成熟期企業_常に製品のイノベーションを図る]] | ↑ [[INSPIRED_MOC]] | → [[07_リーンとアジャイルを超えて]]

**本書全体の出発点となる章。** 圧倒的多数の企業が同じ仕事のやり方をしており、それは最も優れた企業の実際のやり方とはまったく別物である、という指摘から始まる。どんな規模の企業でも、地球のどこにある企業でも変わりはない。

## ほとんどの企業がいまだに使っているプロセス（図1）

> 図1 製品開発が失敗する根本的原因

原文の図1は、次の一方向のフローを示している。

```
アイデア → ビジネスケース → ロードマップ（工程表） → 要求事項
  → デザイン（設計） → ビルド（製造） → テスト → デプロイ（展開）
```

1. **アイデア**は内部（経営幹部、重要なステークホルダー、企業のオーナーなど）か外部（現在あるいは将来の顧客）からもたらされる。
2. **ロードマップを作る理由は2つ。** 第1に企業は製品開発チームに最も重要なことを真っ先にさせようとする。第2にいつすべての準備が整うのかを知りたがる。
3. 四半期あるいは年間の**計画会議**でリーダーたちがアイデアを検討しロードマップを決める。優先順位を付けるために個々の製品の**ビジネスケース**が必要になる。
   - 公式か非公式かを問わず、知る必要があるのは2つ。**（1）それはどれくらいの利益や価値を生み出すのか（2）それはどれくらいの時間と費用がかかるのか。**
   - 原文の脚注: ビジネスケースとは**事業投資をおこなう合理的根拠を示し、見込まれる利益やリスクを記した書類**。
4. アイデアがリストの1位になると、プロダクトマネジャーがステークホルダーに話をしてアイデアを具体化し、一連の「**要求事項**」を考え出す。ユーザーストーリーや機能仕様書の形をとる。
5. 要求事項が集まると**ユーザーエクスペリエンスデザインチーム**にインタラクションデザイン・ビジュアルデザイン・（形のある製品なら）インダストリアルデザインが依頼される。
6. 最後に要求仕様とUI／UX仕様がエンジニアに届く。**一般的にはここでようやくアジャイル開発が関わってくる。** 仕事はスクラムプロセスで「スプリント」に分割され、1つのアイデアに1〜3スプリントかかる。
7. QA（品質保証）テスト。スプリントに入れるのが望ましいが、無理ならQAチームが後からテストし、意図したとおり機能し新しい問題が生じないこと（**リグレッション**）を確認する。
8. QAチームのゴーサインで、新しいアイデアはついに実際の顧客に提供される。

> アジャイル開発に言及し、今日ほとんどの人々が素早さを求めているにもかかわらず、今、説明したのはウォーターフォールプロセスそのものである。

## この手法の10の大きな問題点

**どれ1つを取っても開発チームを失敗させる可能性がある。それなのに多くの企業は2つ以上の、場合によってはすべての問題を抱えている。**

1. **アイデアのソース。** ウォーターフォールプロセスは販売主導の製品やステークホルダー主導の製品につながる。**ここからは最良の製品のアイデアは生まれない。** もう1つの結果は**開発チームへの権限委譲がおこなわれないこと**で、開発チームはただの道具・機能にすぎなくなる。
2. **ビジネスケースの致命的な欠陥。** 著者自身はビジネスケースの作成には賛成（少なくとも大きな投資が必要なアイデアについて）だが、**この段階で優先するロードマップを考えるためにビジネスケースを作成するのは実にばかげている**。
   - **どれだけの利益が得られるかわからない。** ソリューションの出来にすべてがかかっている。多くの製品のアイデアは結局何も生み出さない（A／Bテストをすればわかる）。
   - **ビルドにどれだけのコストがかかるかもわからない。** 実際のソリューションがわからなければエンジニアがコストを予測するのは非常に難しい。**経験豊富なエンジニアならばこの段階で見積もりを出すのを断る。** ただし「Tシャツのサイズ（S・M・L・XL）」のような古典的な妥協を強いられるエンジニアもいる。
   - **製品開発に関する最も重要な教訓の1つは、何が知り得ないかを知ることである。**
3. **企業が自分たちの製品開発ロードマップに夢中になる。** ほとんどのロードマップの実態は機能やプロジェクトの優先順位が付いたリストである。ここで**製品に関する2つの不都合な真実**が生じる。
   - **第1の真実: 少なくとも私たちのアイデアの半分はうまくいかない。** 理由は、顧客が私たちほど心を躍らせず使わない／使いたくても操作が複雑で価値より面倒くささが勝る／気に入られても製造が面倒で商品化する時間や資金が足りない、など。**ロードマップにあるアイデアの少なくとも半分は意図したものの販売につながらない**（特に優秀な開発チームは**少なくとも4分の3**は望んだような成果を生まないと考えている）。
   - **第2の真実: 可能性があることが証明されたアイデアでさえ、ビジネス上必要な価値を持つところまで実装を進めるには通常いくつかのイテレーションが必要。** これを**タイム・トゥ・マネー**と呼ぶ。
   - **どんなに頭のいい人でもこれらの不都合な真実から逃れられない。** 飛び抜けて優れた開発チームが本質的に違うのは、**不都合な真実への対応の仕方**である。
4. **プロダクトマネジメントの役割が、プロダクトマネジメントと呼べない。** 実際は**プロジェクトマネジメントの1形態**で、エンジニアのために要求事項を集めて文書化することが中心になっている。**現代のITプロダクトマネジメントの実像とは180度違う。**
5. **デザインの真の価値を取り入れるのが遅すぎる。** おこなわれていることのほとんどが「**豚に口紅**」モデル。すでにダメージを受けているのにガラクタにペンキを塗ろうとしているだけである。
6. **エンジニアの仕事を導入するのが遅すぎる。** プログラムを書かせるだけのためにエンジニアを使っているなら、**エンジニアの価値の半分ほどしか生かせていない**。製品開発の小さな秘密は**エンジニアはいつも最も優れたイノベーションの源**だということ。それなのにエンジニアは議論プロセスのパーティーに招かれることすらない。
7. **アジャイル開発の原理や主要な利点を取り入れるのも遅すぎる。** こんなふうにアジャイルを使っている開発チームは**アジャイル手法の実際の価値や可能性の20%ぐらいしか享受していない**。目にするのは市場投入の俊敏さだけである。
8. **プロセス全体が非常にプロジェクト中心になっている。** **プロジェクト自体がアウトプット（出力）であり、製品はアウトカム（成果）である。** このプロセスはプロジェクトを当初のアイデアから切り離し、最終的に何かがリリースされるがそれは目的に合致したものではない。
9. **すべてのリスクが最後に来る。つまり顧客実証がおこなわれるのが遅すぎる。** リーン手法の鍵となる原則は無駄を減らすことであり、**その無駄の最たるものが、ある機能や製品をデザインし、ビルドし、テストし、デプロイしたあげく、それが必要とされていなかったとわかること**である。多くの開発チームが自分たちはリーンの原則を採用していると信じているが、実際は**知り得るかぎり最も費用と時間がかかる方法でアイデアを試している**。
10. **本当の一番大きな損失は機会損失である。** 組織がその代わりに選択できたはずであり選択すべきだったことを失っている。**失った時間と費用は取り戻せない。**

## 章の締め

> もちろん希望もある。最も優れた開発チームは今述べたような仕事の仕方はしないとはっきりと言っておこう。
