# burhan-platform - コードリーディング

親: [[burhan-platform]] ／ [[リポジトリ調査 MOC]]

Nuxt 4 ＋ Supabase の**マルチテナントSaaS**。読んだのは `supabase/migrations/`（22本のうち 00001〜00003、00008、00011、00015〜00019）と `server/utils/`（`crypto.ts`、`auth.ts`、`supabase.ts`）、`server/api/org/ai-credentials.post.ts`、`server/api/auth/register-tenant.post.ts`。フロント（Vue）と AI 推論まわりは読んでいない。

> [!warning] AGPL-3.0
> コードは持ち込まない。ここに書くのは**設計の考え方**で、SQL／TypeScript の転記はしていない。

## 全体像

| 層 | 中身 |
|---|---|
| テーブル | `organizations`（テナント）→ `branches` → `entities`（コンテンツ）。`profiles` が `auth.users` を拡張し、`role` と `organization_id` を持つ |
| 権限 | `user_role` の enum 4段階（`super_admin`／`owner`／`manager`／`member`）。**ユーザーは1組織・1ロール** |
| 保護の3層 | ① RLS ポリシー ② SECURITY DEFINER のヘルパー関数とトリガー ③ サーバー（Nitro）側の API での再チェック |
| 秘密の扱い | 暗号化した上で、`service_role` 専用のテーブルに保管 |
| テスト | `tests/`（BYOK、購読、XSS、AI バックエンド）。RLS 自体のテストは見当たらなかった |

## 学び1：RLS は一度で正しく書けない（マイグレーションが証拠）

22本のうち少なくとも **5本（00002・00003・00008・00011・00017）が RLS の修正**で、失敗の型がそのまま並んでいる（00001 は原因側）。

| マイグレーション | 起きたこと | 教訓 |
|---|---|---|
| 00001 | `profiles` のポリシーが `profiles` 自身を副問い合わせ | **自己参照ポリシーは無限再帰**する |
| 00002 | 匿名ユーザーが `branches` を読めず、公開フィードが壊れた。「全員読める」ポリシーを足して解決 | 匿名アクセスの経路を先に洗い出す |
| 00003 | 再帰を、`SECURITY DEFINER` のヘルパー関数（現在ユーザーのロールと組織ID を返す）で解消 | ロール解決は関数に切り出し、RLS を迂回して読む |
| 00008 | Supabase の linter 警告を受けてヘルパー関数の実行権限を `anon` から剥奪 | linter（[[database-sentinel]]、[[pgrls]] の同類）を早く回す |
| 00011 | **00008 の剥奪で、匿名ユーザーの公開読み取りが全部エラーになった（回帰）**。原因は、`TO` 句のないポリシーが全ロールに適用され、匿名でも述語が評価されて権限エラーになること。特権ポリシーに `TO authenticated` を付けて解決 | **ポリシーには必ず `TO ロール` を付ける**。権限を絞ると別の経路が壊れる |
| 00017 | 初期の `profiles_update_own` は、**自分の `role` と `organization_id` も書き換えられた**（権限昇格の穴）。RLS の `WITH CHECK` とトリガーで塞いだ | 「自分の行を更新できる」ポリシーは、更新できる**列**まで考える |

## 学び2：権限昇格はトリガーで塞ぐ（00017）

RLS の `WITH CHECK` だけでなく、`profiles` の **BEFORE UPDATE トリガー**で二重に守っている。

- 呼び出し元が**バックエンドの信頼された文脈**（`service_role`、`postgres` など）かどうかを判別し、そうならほとんどの検査を通す。組織登録の初期化のための抜け道
- 本人による更新は、`full_name` などは許すが、**`role` と `organization_id` の変更は拒否**
- `owner` は自組織のメンバーの `role` を変えられるが、**他組織へは動かせず、`super_admin` も付与できない**
- `super_admin` は動かせるが、**移動先の組織に有効な購読がなければ全員拒否**（`service_role` も例外にしない）
- 想定外の更新は**最後に一律で拒否**（fail-closed）
- トリガー関数の実行権限は、`PUBLIC`／`anon`／`authenticated`／`service_role` の全員から剥奪

## 学び3：秘密は暗号化し、クライアントから完全に隔離する（00018、`crypto.ts`）

**モールのAPIキー保管（[[各モール API認証情報の取得手順]]）に直接当てはまる。**

- `tenant_ai_credentials` テーブルは、暗号文・IV・認証タグ・鍵バージョン・表示用の末尾4文字だけを持ち、**平文はDBに置かない**
- **RLS を有効にした上で、`anon`／`authenticated` の権限を全剥奪し、`service_role` だけに付与**。PostgREST 経由ではクライアントから一切触れない
- 暗号は AES-256-GCM。**保存のたびに12バイトのランダムIV**を生成し、認証タグで改ざんを検出。マスター鍵は環境変数で、**64桁の16進（32バイト）でなければ起動時に例外**（fail-closed）
- `key_version` 列で、将来の**鍵ローテーション**に備える
- `(organization_id, provider)` を一意にし、同じ組み合わせへの保存は**上書き（ローテーション）**として扱う
- APIキー自体は、画面には末尾4文字しか返さない

## 学び4：API ハンドラの認可パターン（`ai-credentials.post.ts`）

`service_role` でDBを触る Route Handler の書き方の実例。緑茶園の EC 側（supabase-js＋service_role＋Route Handlers）と**同じ構造**。

1. リクエストからアクセストークンを取り出す（`Authorization: Bearer` が優先、なければボディ）
2. トークンを **Supabase 側で検証**して `userId` を得る（クライアントが申告した ID は信じない）
3. `userId` から **`profiles` を引き、組織とロールをサーバー側で確定**（リクエストに組織IDを持たせない）
4. **ロールで許可を判定**（`owner` か `super_admin` のみ）
5. 入力を検証（provider は許可リスト、エンドポイントは SSRF ポリシーで検査）
6. 暗号化して保存

> [!note] 注意点
> ボディのトークンも受け付ける実装は、ログやプロキシにトークンが残りうる。`Authorization` ヘッダーに一本化した方が安全。また「service_role を使う以上、RLS は効かない」ので、**認可はこの層が全責任を負う**。

## 学び5：作成処理は1つのDB関数に閉じる（00019、`register-tenant`）

組織の作成〜購読〜メインブランチ〜所有者昇格を、**1つのトランザクションの関数**にしている。

- 入力を検証（名前2文字以上、スラッグは英数字とハイフン）
- 該当ユーザーの `profiles` 行を `FOR UPDATE` で**ロック**し、二重実行を防ぐ
- 既に組織があるときは、**完全なら同じ結果を返し（冪等）、片方だけ欠けていれば「状態が壊れている」と例外**にする。中途半端な状態を許さない
- API 側は **メール確認済みか**を先に見て（多層防御）、それから関数を呼ぶ

## 学び6：上限や状態をDBで強制する（00015、00016）

- プランごとの上限（`plans.limits` の JSON の `max_branches`）を、**INSERT 時のトリガー**が検査する。API を迂回してもすり抜けられない
- 検査中は対象の組織行をロック（`FOR NO KEY UPDATE`）して、同時実行による上限超過を防ぐ
- 上限値は `-1`（無制限）か整数の範囲であることを**厳密に検証**し、不正な設定は拒否（fail-closed）
- 購読が切れた組織は**読み取り専用**に落とし、公開閲覧は残す

## 緑茶園への当てはめ（私の推定。実スキーマは未確認）

[[platform - 00 概要]] の障害「権限モデルが無い」「`inventory` は PostgREST から見えず `pg` 直結」に対して。

| burhan の型 | 緑茶園での使いどころ |
|---|---|
| ロール enum ＋ `profiles` | 現在の Supabase Auth の3名（うち1件は検証用ボット）に、`profiles` でロールを持たせる。例：閲覧のみ／受注取り込み担当／支払明細書の発行者／管理者 |
| `service_role` 専用テーブル ＋ 全権限剥奪 | **モールの認証情報テーブル**（[[各モール API認証情報の取得手順]]）。DDL がどこにも無いという現状（[[05 統合方針（決定事項と設計）]]）を解消しつつ、クライアントから見えないことを明文化できる |
| AES-256-GCM ＋ IV ＋ タグ ＋ 鍵バージョン | モールのAPIキーの暗号化保管。鍵ローテーションの余地も確保 |
| Route Handler の認可パターン | EC 側の Route Handlers に、**ロール判定を1関数にまとめて**適用する。今は「ログインできれば誰でも全機能」 |
| ロール変更を塞ぐトリガー | ロールを持たせた瞬間に、**自分で自分を管理者にできる穴**ができる。`role` 列の更新は本人に許さない |
| 作成処理を1つのDB関数に | 支払明細書の発行など、複数テーブルにまたがる処理の冪等化 |

**`inventory` スキーマ側**は `pg` 直結の Server Actions なので RLS は効かない。同じ考え方を**アプリ層のロール判定**で実装することになる（RLS 相当の保証は得られない）。

## そのまま真似できない点

- burhan は**マルチテナント**（複数の組織が1つのDBを共有）で、緑茶園は**単一組織のグループ内利用**。`organization_id` による分離は、ほぼ不要
- ユーザーが1組織・1ロールに固定されている。緑茶園で「複数ロールを兼ねる」ことがあるなら、別テーブルに切る必要がある
- フロント（Nuxt）と AI 推論は関係がない
