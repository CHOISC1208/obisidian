# 2026-08-27 年休・慶弔・昼食の変更依頼

親: [[00 MOC|ケーテック株式会社 MOC]]

出典: `docs/hearing/2026-08-27_leave-keicho-lunch-changes.md`。
先方からの依頼（チャット貼り付け）＋ **デプロイ後のユーザー確認フィードバック**（同日）。

> [!important] 「作ったものへの注文」フェーズの始まり
> この日、`config` を先方環境に書き直して適用した。先方が実際に触ってのフィードバックが
> 初めて出た回。同時に **旅費の保留・付与基準の取り下げ**も確定した。

## 先方の依頼（そのまま）

### 慶弔連絡
- 件名は「慶弔区分＋氏名」の自動反映とする（入力できなくして、計算したものをタイトルにする案）
- **雇用形態および勤続年数は入力不要とし、システムで管理する**
- **慶弔金額はマスタ情報を基に自動算出・表示する**
- 代理申請機能を設ける（代理申請時は対象者を入力できるようにする）

### 年休申請
- 取得日（開始）・取得日（終了）から取得日数を自動計算する（**土日を除外**）
- 休暇区分が「AM休」「PM休」のときは取得日（終了）を選択できない仕様とする
- 毎月20日締めの申請データを総務がExcel/CSVで出力できるようにする（Excel×Power Query で対応想定）
- **承認者は上長情報から自動設定したい。ただしM365の上長情報は異動のたびに手入力が必要で
  運用負荷が高いため、上長マスタを別リストで管理する案を検討したい**
- 休暇区分が「早退」「遅刻」のときは時間入力を可能とする
- 休暇区分「外出」は利用実績が無いため削除する
- 件名は「休暇区分＋氏名」の自動反映とする（慶弔と同じ考え方）
- 申請状態は申請者と承認者のみが確認できるようにする
- 年休カレンダーの公開可否を選択制にする（既定＝公開、非公開も選べるように）
- 特別休暇はシステム上「年休」と表示する
- 取得理由はカレンダー上には表示しない

### 昼食申込
- 「当日申込」「期間まとめ申込」の2種類から選べるようにする
- 申込取消に対応するため、取消欄を設ける
- 申込締切は当日**8:30**とし、それ以降は入力不可とする
- 【検討事項】申込漏れの救済措置（総務によるデータ修正 or 総務用の代理申請機能）
- 【検討事項】出力データに注文者一覧・ご飯普通盛り数量・ご飯小盛り数量・各数量集計結果を含める

### 旅費申請
- **結論: 保留。** 理由: 旅費申請経路・**工番管理との親和性**を考えると、現状は紙運用の方が
  申請者負担を抑えられるため

### 付与基準確認
- **取り下げ。**

## 実装したこと

上長マスタ・従業員マスタの是非が未確定のため、**それらに依存しない範囲**で実装した。

| 対象 | 実装内容 |
|---|---|
| 年休 | 件名を「申請日(yyyymmdd)_休暇区分_氏名」で自動反映し常時グレーアウト |
| 年休 | AM休/PM休のとき取得日(終了)を開始日に固定し選択不可 |
| 年休 | 取得日数の計算を**土日除外**に変更（**祝日・会社休日は未対応**） |
| 年休 | 遅刻/早退のときだけ時刻（開始・終了）の自由入力欄を追加 |
| 年休 | 「外出」を選択肢から削除 |
| 慶弔 | 件名を「申請日(yyyymmdd)_制度種別_対象者氏名」で自動反映し常時グレーアウト |
| 慶弔 | **代理申請機能を追加**（`InitiatorType` に「代理申請」、選択時のみ対象者 Person 列を入力可能。件名の氏名も対象者側へ） |
| 昼食 | `SubmissionMode`（当日申込/期間まとめ申込）を追加 |
| 昼食 | 当日申込は8:30締切を SPFx 側でチェックし、超過時は送信不可 |
| 昼食 | 共通 `Status` に「取消」を追加（**値のみ。UI/フローは未実装**） |
| 共通基盤 | 「他フィールドから自動計算して編集不可表示にする」仕組みを `text`/`date` にも拡張（従来は `number`/`currency` のみ） |
| 共通基盤 | **`readOnly` 属性を新設**し、「計算条件が揃うまで空欄グレーアウトで手入力不可」（件名）と「計算できないときは手入力できる」（取得日数）を区別 |
| 共通基盤 | PersonPicker が選択と同時に表示名も保持するよう拡張（件名に氏名を使うため） |
| 全体 | 旅費・付与基準を `enabled:false` にし、SPFx からタイル自体を削除 |

> [!info] 件名フォーマットを依頼と変えた
> 依頼は「休暇区分＋氏名」「慶弔区分＋氏名」だったが、**それだけでは件名が被りやすい**という
> フィードバックを受けて申請日を頭に付けた。

## あえて未対応にしたこと

> [!important] マスタ新設の是非が決まらないと動けない2件
> - **慶弔**: 雇用形態・勤続年数の入力不要化、慶弔金額の自動表示
> - **年休**: 承認者の自動設定（上長からの自動決定）
>
> どちらも上長マスタ・従業員マスタの新設が前提。**こちらは両方に反対の立場でメール文案を
> 作成済み・先方回答待ち。** → [[テーマ4 - マスタを増やすか]]

## 既存の設計とのズレ（技術的な説明が必要だった件）

先方の「申請状態は申請者と承認者のみ確認できるように」という要望に対し、
現状のリストは `ReadSecurity=2` のため**承認者もリスト上は見えない**（承認カード/出力Excel経由で
確認する設計）と説明。ユーザーからは「これで十分」と回答。

総務の20日締め全件出力については「**専用のリストビューを作成すれば対応できるはず**」という
コメントを受けたが、これには技術的な補足が必要だった。

> [!warning] ビューでは回避できない
> SharePoint の `ReadSecurity=2` はビューでは回避できない。回避できるのは
> 「アイテムの承認（Manage Lists）」権限を持つグループだけで、これは **Design 以上の権限レベル**。
> ところがこの権限は**書き込み制限（`WriteSecurity=2`）も同時に解除する**ため、
> 総務は閲覧だけでなく**編集・削除もできてしまう**。
>
> 対応案は2つ（Design権限を付与 / フローで項目単位に付与）。**要判断のまま。**
> → [[テーマ3 - 総務の全件閲覧をどう成立させるか]]

## 実装が難しいと判断したもの

- **年休カレンダーの公開可否（選択制・非公開時に事由非表示等）** — どのような画面・仕組みを
  指しているのかイメージが掴めておらず、現時点での実装は難しいと判断。
  **先方へ要件を確認する予定**（カレンダーではなくリスト表示になる可能性が高いことも含めて）

## 運用で吸収すると決めたもの

| 依頼 | 対応 |
|---|---|
| 毎月20日締めのExcel/CSV出力 | **開発せず Excel の Power Query で対応**（総務のExcelブックだけで完結）。ただし権限整備が前提 |
| 昼食の申込漏れ救済 | **総務が標準のリストフォームから直接入力**（専用UIは作らない）。ただし `Applicant` に総務の名前が入る点は先方説明が必要 |
| 昼食の出力データ項目・用語対応 | **先方がメニューマスタ管理画面を直接整備**する運用（名称をそのまま出力に使う） |
| 昼食8:30締切の迂回 | SPFx側チェックのみで運用。**「悪意を持って迂回する社員は想定しない」**と割り切り |

## スコープ外にしたもの（合意済みだが未実装）

- 昼食の取消の**実操作**（誰が・いつまで取消せるか）— `Status` に値を足しただけ
- 昼食「期間まとめ申込」を1日単位の申込行へ展開する処理 — 列は追加、**展開ロジックはフロー側の対応待ち**
