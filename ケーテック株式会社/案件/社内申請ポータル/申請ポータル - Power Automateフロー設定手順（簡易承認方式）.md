# 申請ポータル - Power Automateフロー設定手順（簡易承認方式）

親: [[申請ポータル - 00 概要]] ／ [[00 MOC|ケーテック株式会社 MOC]]

> [!info] このノートの位置づけ
> **「何を作るか」（設計判断）** は [[申請ポータル - 承認方式（簡易承認への転換）]] に書いた。
> このノートは**「実際にPower AutomateのGUIで何をクリックするか」の手順書**。
> 2026-09-07時点でフローは1本も実装されていない（[[申請ポータル - 00 概要]]の到達点表参照）。
> フロー本体はこのリポジトリではコードとして管理せず GUI で作る方針（CLAUDE.md）のため、
> このノートの手順に沿って**GUIで**組み立て、できたらソリューションごとエクスポートして
> `flows/solution/` へ commit する。

## 前提

- **どのAPPのフローも構造は同じ3ステップ＋フォールバック。** 差分は「どのリストか」「承認を何回呼ぶか」
  「後処理で何を追加するか」だけ（CLAUDE.md §0）。中央の共通フローは存在しないので、APPごとに
  下記手順をまるごと繰り返す（複製すること自体はこの方式では問題ない）。
- 作業前に確認すること
  - [ ] Power Automate（make.powerautomate.com）に、対象SharePointサイトと同じテナントでサインインできるか
  - [ ] 対象リストがテナントに適用済みか（`provision.ps1` 実行済みか。[[申請ポータル - デプロイ経路]]）
  - [ ] このフローを入れる**ソリューション**を先に作る（個別フローのまま放置しない。あとでエクスポートする前提）
- 使う共通列は7つだけ（申請者は入力しない・フローが設定する列）。列の内部名は
  [[申請ポータル - 共通列とコンテンツタイプ]] 参照。特に以下を押さえておく。

| 内部名 | 表示名 | 型 | 備考 |
|---|---|---|---|
| `Applicant` | 申請者 | Person | フローが作成者(Author)から設定 |
| `ApplicantDepartment` | 所属部署 | 選択肢 | フローがEntra IDの部署属性から設定 |
| `Status` | ステータス | 選択肢 | 既定値`申請中`。選択肢: `申請中`/`承認済`/`却下`/`要手動対応`/`精算済`/`取消` |
| `Approver` | 承認者 | Person | **申請者が申請時に選択済み**。フローは読むだけ |
| `ApprovedAt` | 承認日時 | 日時 | フローが記録 |
| `ApproverComment` | 承認コメント | 複数行テキスト | フローが記録 |

## 全APP共通の型（3ステップ＋フォールバック）

### 0. ソリューションとフローの作成

1. Power Automate → 左メニュー「ソリューション」→ 対象ソリューションを開く
   （無ければ新規作成。名前は `ApprovalFlows` 等、パブリッシャーは会社のものを使う）
2. ソリューション内で「＋ 新規」→「オートメーション」→「クラウドフロー」→「自動化したクラウドフロー」
3. フロー名は `{リスト内部名}_Submit`（例: `LeaveRequests_Submit`）
4. トリガー: `SharePoint`「項目が作成されたとき」。サイトアドレス・リスト名(内部名/URL)を指定

### 1. 共通前処理（申請者情報の補完）

1. アクション追加: `SharePoint`「項目の更新」（対象: 同じ項目ID＝トリガーのID）
   - `Applicant`: トリガーの動的コンテンツ「作成者」を渡す
2. アクション追加: `Office 365 Users`「ユーザー プロフィールの取得 (V2)」
   - ユーザー(UPN): トリガーの動的コンテンツ「作成者の電子メール」
3. 直前の「項目の更新」に戻り、`ApplicantDepartment` に上記結果の `department` を設定
   - 部署名がSharePoint側の選択肢文言と一致しないと、この列だけ空のまま失敗せず素通りする。
     **握りつぶさないこと**（要確認事項として記録する）。

### 2. 権限ロック（申請受付時に申請者を読み取り専用へ）

CLAUDE.mdの承認整合性ルール「申請受付時に項目を申請者読み取り専用へ権限変更」に対応する。

1. アクション追加: `SharePoint`「HTTP要求の送信」を3回連続で呼ぶ
   1. `breakroleinheritance`（権限継承の解除）
      - メソッド: `POST`
      - URI: `_api/web/lists/getbytitle('{リスト内部名}')/items({ID})/breakroleinheritance(copyRoleAssignments=false,clearSubscopes=true)`
   2. サービスアカウントへフルコントロール付与
      - URI: `_api/web/lists/getbytitle('{リスト内部名}')/items({ID})/roleassignments/addroleassignment(principalid={サービスアカウントのID},roleDefId={フルコントロールのロール定義ID})`
   3. 申請者へ読み取り権限付与
      - URI: 同上の `principalid={Applicantのユーザー ID}, roleDefId={読み取り専用のロール定義ID}`
   - ロール定義IDはサイトごとに異なる実測値。環境変数化する（下記「環境変数」参照）
   - 実行アカウントはサイトのオーナー権限を持つ接続を使う（サービスアカウント推奨。個人アカウントの接続をそのまま使い回さない）
2. 「実行後の構成」でこの3アクションを**失敗した場合は先に進まない**設定にする
   （ロックが中途半端な状態で承認に進まないようにする）

### 3. 承認の開始と待機

1. アクション追加: `Approvals`「承認の開始と待機」
   - 承認の種類: `承認/拒否 - 最初の応答者が対象`（承認者は1名のみ渡す。複数名を渡さない）
   - タイトル: 下記テンプレート参照
   - 割り当て先: `Approver`（トリガーの動的コンテンツ、メールアドレス値）
   - 詳細: 申請内容のスナップショット。**列の値を本文にすべて埋め込む**
     （CLAUDE.mdの「スナップショット承認」。承認者が原本を見なくても承認カードだけで判断できるようにする）
2. 「実行後の構成」で成功/失敗を分岐する
   - 成功 → ステップ4（結果の書き戻し）
   - 失敗（ユーザーが見つからない・退職者等）→ ステップ5（フォールバック）へ

### 4. 結果の書き戻し

1. 条件分岐:「承認の開始と待機」の結果が「承認」か「却下」か
   - 承認: `SharePoint`「項目の更新」→ `Status=承認済` / `ApprovedAt=utcNow()` / `ApproverComment=`結果のコメント
   - 却下: `Status=却下` / `ApproverComment=`結果のコメント
2. 通知: `Teams`または`Outlook`で申請者へ結果を通知（承認者コメント付き）
3. APP固有の後処理があればここに追加する（下記「APPごとの追加ポイント」参照）

### 5. フォールバック（承認者に到達できない場合）— 全APP共通で必須

CLAUDE.md「承認者に到達できなくても申請を却下にしない」に対応する。

1. `Teams`「チャネルにメッセージを投稿する」→ 管理者チャネルへアラート
   - 本文例: `{リスト表示名} の項目 #{ID} で承認者 {Approver} に到達できませんでした。要手動対応。`
2. `SharePoint`「項目の更新」→ `Status=要手動対応`
3. **`Status=却下`にはしない**

## 承認カードのタイトルテンプレート

`【{リスト表示名}】{申請者}さんからの承認依頼 - {件名}` の形式を基本とする。
差し込みトークンはトリガーの動的コンテンツから拾えるものだけを使う
（旧・中央承認エンジン方式の `ApprovalTransactions` 依存トークンは③方式では使えない。
[[申請ポータル - 承認方式（簡易承認への転換）]]の「②の設計資産の扱い」参照）。

## 環境変数にすべきもの

個人名・個人メールのハードコード禁止（CLAUDE.md）。ソリューションの環境変数として持つ。

| 環境変数 | 用途 |
|---|---|
| `PortalSiteUrl` | 申請ポータルサイトURL |
| `AdminTeamId` / `AdminChannelId` | フォールバック時の管理者チャネル通知先 |
| `ReadOnlyRoleDefinitionId` / `ServiceAccountRoleDefinitionId` | 権限ロックで使うロール定義ID（サイトごとに実測が必要） |
| （No.03のみ）社長のUPNを持つ環境変数 | `FinalApprover`にフローが固定値を書き込むため。名前は未決定（下記「未確定」参照） |

## エクスポートとcommit

1. 動作確認できたら、ソリューション全体を「エクスポート」→ zipでダウンロード
2. `flows/solution/` に配置してcommit（[[申請ポータル - デプロイ経路]]参照）
3. `flows/README.md` は中央承認エンジン方式の記述のまま古い
   （[[06 リポジトリ内ドキュメントの現状差分]]）。1本でも実際にフローができたら、
   このノートの内容に合わせて書き直すこと（Flow-A〜Fの表を差し替える）。
