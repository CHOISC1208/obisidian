# 申請ポータル - SPFx申請ポータル（画面側）

親: [[申請ポータル - 00 概要]] ／ [[00 MOC|ケーテック株式会社 MOC]]

出典: `spfx/request-portal-app/`（SPFx Webパーツ `request-portal-app` v0.0.1）。

## なぜ独自フォームを作ったか

当初の方針は「Microsoft Lists の標準フォーム（必要に応じ JSON カスタマイズ）」だった。
実際には JSON では組めない要件が積み上がり、SPFx の Webパーツを作ることになった。

| 要件 | Lists標準フォーム | JSONカスタマイズ | SPFx |
|---|---|---|---|
| 条件による項目の出し分け（結婚祝金のときだけ「挙式あり」を出す） | ✕ | △ | ○ |
| 他項目からの自動計算（開始日・終了日 → 取得日数） | ✕ | ✕ | ○ |
| 件名の自動生成とグレーアウト | ✕ | ✕ | ○ |
| 締切時刻を過ぎたら送信不可（昼食8:30） | ✕ | ✕ | ○ |
| 日付範囲の妥当性チェック（帰国日 < 出発日を弾く） | ✕ | △ | ○ |
| マスタの GUI 編集画面 | ✕ | ✕ | ○ |

## 構成

```
spfx/request-portal-app/src/
├── webparts/requestPortal/
│   ├── RequestPortalWebPart.ts
│   └── components/
│       ├── RequestPortal.tsx        ← 左ナビ（申請／マスタ管理）と画面切り替え
│       └── requestTypes.ts          ← ★申請種別ごとの設定。ここが実質の仕様書
├── shared/requestEngine/            ← 申請フォームの汎用エンジン
│   ├── RequestForm.tsx              ← 入力フォーム
│   ├── RequestList.tsx              ← 自分の申請一覧
│   ├── RequestDetailPanel.tsx       ← 詳細パネル
│   ├── PersonPicker.tsx             ← Person列の選択（表示名も保持する）
│   ├── fieldSelect.ts / types.ts
├── shared/masterEngine/             ← マスタ管理の汎用エンジン
│   ├── MasterEditor.tsx
│   └── masterTypes.ts               ← マスタごとの列定義
└── shared/access/useIsAdmin.ts      ← マスタ管理ナビの表示可否判定
```

> [!important] `requestTypes.ts` が実質の仕様書
> 申請種別ごとの入力項目・型・選択肢・条件表示・自動計算がすべてここに集まっている。
> **`template/20_requests/*.xml`（列定義）と `requestTypes.ts`（画面）は必ず対で更新する。**
> 片方だけ変えると、列はあるのに入力できない／入力できるのに列が無い、という状態になる。

## 申請エンジンの機能

`IFormFieldDef` が持てる属性で、画面の振る舞いが決まる。

| 属性 | 意味 | 使用例 |
|---|---|---|
| `type` | `text` / `note` / `choice` / `date` / `number` / `currency` / `person` / `lookup` / `boolean` | — |
| `required` | 必須 | ほぼ全項目 |
| `visibleWhen` | 条件を満たすときだけ表示 | 慶弔の「挙式あり」は制度種別＝結婚祝金のときだけ |
| `hiddenInNewForm` | 常時非表示（**フローが設定する列**） | 慶弔の `PlannedAmount`、海外保険の `FinalApprover` |
| `readOnly` | 常に直接編集不可（グレーアウト） | 件名（`Title`） |
| `lookupListUrlSegment` / `lookupDisplayField` | 参照先マスタ | 昼食の `MenuItem` → `MenuMaster`、海外保険の `Destination` → `DestinationMaster` |
| `computeFields` | 他項目から値を自動算出 | 件名生成、取得日数、終了日の固定 |
| `dateRangeRules` | 日付の前後関係チェック | 帰国日 < 出発日、期間終了 < 期間開始 |
| `submitGuard` | 送信可否のチェック | 昼食の当日8:30締切 |

### `readOnly` と「自動計算」の使い分け（2026-08-27 に追加した区別）

当初は「他フィールドから自動計算して編集不可表示にする」仕組みが `number` / `currency` にしか無かった。
08-27 の依頼（件名の自動反映）に対応するため `text` / `date` にも拡張し、さらに2種類を区別できるようにした。

| 種類 | 挙動 | 例 |
|---|---|---|
| `readOnly: true` | **計算条件が揃うまで空欄のままグレーアウトし、手入力を一切許さない** | 件名（休暇区分が決まるまで空欄） |
| 指定なし（自動計算のみ） | 計算できるときは自動で入り、計算できないときは通常通り手入力できる | 取得日数（遅刻・早退は自動計算しないので手入力） |

## 自動計算のロジック（`requestTypes.ts` 内）

| 関数 | 何をするか |
|---|---|
| `computeLeaveFields` | 年休の件名生成、AM休/PM休のときの終了日固定、土日除外の日数計算（半休は0.5換算、遅刻/早退は計算しない） |
| `computeKeichoFields` | 慶弔の件名生成（代理申請時は対象者の氏名を使う） |
| `lunchSubmitGuard` | 昼食「当日申込」の8:30締切チェック |
| `businessDaysInclusive` | 開始日・終了日を含む土日除外の日数 |

### 件名フォーマット

```
申請日(yyyymmdd)_区分_氏名
```

先方の依頼は「休暇区分＋氏名」「慶弔区分＋氏名」だったが、**それだけでは件名が被りやすい**という
フィードバックを受けて申請日を頭に付けた（2026-08-27）。年休・慶弔で共通。

氏名は `RequestForm` が注入する `__ApplicantDisplayName` を使う。
これを実現するため、`PersonPicker` が選択と同時に表示名も保持するよう拡張した。

> [!warning] 祝日・会社休日は日数計算に入っていない
> 土日除外までは実装したが、`BusinessCalendar`（営業日カレンダー）には接続していない。
> **祝日を含めるかどうか自体が未確認。** → [[05 要確認事項]]

## マスタ管理画面

`AdminGroupName` メンバー限定。**継続的なマスタ更新はこの画面が正**（2026-08-10 に運用変更）。

| 対象マスタ | 編集する人 |
|---|---|
| `KeichoMaster`（慶弔マスタ） | 総務人事（規程改定時） |
| `MenuMaster`（メニューマスタ） | 総務（価格改定時） |
| `BusinessCalendar`（営業日カレンダー） | 総務 |

`ApproverMaster` / `RequestTypeSettings` は対象外（そもそも存在しない）。

### 管理者判定の実装が特殊

**SharePointグループ名の文字列一致ではなく、対象リストへの実際の編集権限（`EditListItems`）で判定**している。

> [!info] なぜそうなったか（2026-08-10 実機確認）
> M365グループ連携サイトでは「所有者」グループへの所属がAAD側のクレームで解決されており、
> `currentUser.groups()` にそのグループが**現れない（空配列が返る）**。
> 一方 `effectivebasepermissions` は解決方式によらず実際の権限を返すため、こちらは正しく動く。
>
> なお、これは**表示の出し分けにすぎない**。実際の書き込み可否は
> `configure-list-permissions.ps1` が設定する SharePoint 側のアクセス許可がそのまま担保する。

## ナビゲーションに出る申請種別

`requestTypes.ts` の `REQUEST_TYPE_CONFIGS` に含まれるものだけがタイルとして出る。

| 状態 | 扱い |
|---|---|
| 稼働中（年休・仮払金・慶弔・海外保険・昼食） | 配列に含める |
| 取り下げ・保留（実印・勤怠・旅費・付与基準） | **配列から項目自体を削除**。`enabled:false` で残すと「（準備中）」タイルが出てしまい、取り下げ・保留の実態と合わないため |
| 仮組み（許可申請） | 配列に含めていない（コメントで理由を明記） |

## 既知の弱点

| 弱点 | 内容 |
|---|---|
| **標準リストフォームから迂回できる** | 8:30締切チェック・件名の自動生成・条件表示はすべて SPFx 側のみ。`list.aspx` から直接投稿すれば素通りする。**「悪意を持って迂回する社員は想定しない」と割り切り済み**（締切超過分は総務の救済運用で拾う） |
| **列定義との二重管理** | `template/*.xml` と `requestTypes.ts` を対で更新する規律に依存している |
| **総務の代理入力で申請者名がずれる** | 昼食の申込漏れ救済は総務が標準フォームから入力する運用。`Applicant` にはフローが作成者（＝総務）を入れるため、**実際に注文した本人の名前が残らない**。先方への説明が必要 |
