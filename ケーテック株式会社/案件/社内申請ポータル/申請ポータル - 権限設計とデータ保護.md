# 申請ポータル - 権限設計とデータ保護

親: [[申請ポータル - 00 概要]] ／ [[00 MOC|ケーテック株式会社 MOC]]

出典: `scripts/configure-list-permissions.ps1`、`docs/conventions.md` §5/§6、`config/*.sample.json`。

## 基本方針

**申請リストは「自分が作成した項目しか見えない・編集できない」。**

| 設定 | 意味 |
|---|---|
| `ReadSecurity=2` | 自分が作成した項目のみ**閲覧**可 |
| `WriteSecurity=2` | 自分が作成した項目のみ**編集**可 |

これが慶弔連絡（No.2）のようなプライバシー要件の高いデータを守る基盤になっている。
一方で**総務が全件を見られない**という現在の最大の詰まりも、ここから来ている。
→ [[テーマ3 - 総務の全件閲覧をどう成立させるか]]

## 権限マトリクス（現行・簡易承認方式）

`configure-list-permissions.ps1` が適用する。グループ名・サービスアカウント名は
`config/{env}.json` の `Permissions` セクションで指定する（**リポジトリに個人名・実グループ名を書かない**）。

| リスト | 一般社員 | 総務人事 | 管理者 | サービスアカウント |
|---|---|---|---|---|
| 各申請リスト | 自分の項目のみ | — | — | フルコントロール |
| `KeichoReports`（慶弔） | 自分の項目のみ | **このリストのみ閲覧可** | — | フルコントロール |
| `KeichoMaster` / `MenuMaster` / `BusinessCalendar` | 読み取り | 読み取り | **編集可（投稿）** | フルコントロール |
| `DestinationMaster` | 読み取り | 読み取り | 〔管理者の編集権限の有無は要確認〕 | フルコントロール |

`config` の `Permissions` に入るキー:
`ServiceAccountLogin` / `AllUsersGroupName` / `AdminGroupName` / `StaffGroupName` /
`KeichoViewerGroupName` / `AuditLogAppendOnlyRoleName`

> [!info] 3つのマスタだけ管理者に編集権限がある理由
> SPFx申請ポータルの「マスタ管理」画面から先方が直接編集する運用にしたため（2026-08-10）。
> `seed-masters.ps1` は新規環境への初期投入専用に位置づけが変わっている。
> → [[申請ポータル - SPFx申請ポータル（画面側）]]

### 実装上の工夫

ロール定義名（「フル コントロール」「閲覧」等）は**テナントのロケールで変わる**ため、
名前ではなく `RoleTypeKind` から実行時に解決している。
XML（`pnp:Security`）ではなくスクリプトで権限を持っているのはこの理由。

`Permissions` の項目が空のものは警告を出してスキップする（dev で全グループを作らない運用を許容）。

> [!warning] `docs/conventions.md` §6 の表は古い
> `ApprovalTransactions` / `AuditLog` / `RequestTypeSettings` / `ApproverMaster` の行が残っているが、
> **これらのリストは存在しない**。スクリプト側のコメントには正しく「本ブランチには中央承認エンジン
> 専用リストが存在しないため権限設定は行わない」と明記されている。
> → [[06 リポジトリ内ドキュメントの現状差分]]

## 承認整合性のための3点セット

簡易承認方式でも**全APPのフローで必須**としている（中央承認エンジン方式から引き継いだ最小限）。

| # | 設計 | 状態 |
|---|---|---|
| 1 | **スナップショット承認** — 申請時点の全項目値を承認カードの文面に埋め込む | ❌ 未実装（フローが無い） |
| 2 | **申請受付時に項目を申請者読み取り専用へ権限変更**（`breakroleinheritance`） | ❌ 未実装 |
| 3 | **削除は物理禁止・論理削除**（`Status` 列で管理） | 🟨 `Status` に「取消」を追加済み。**操作UI・権限は未実装** |

加えて、`Approver` 列は `ShowInEditForm="false"` で編集フォームから隠している
（提出後に承認者を差し替えられると承認整合性が崩れるため）。

## 中央承認エンジン方式から捨てたもの

| 捨てたもの | 何だったか |
|---|---|
| `AuditLog`（追記専用の監査ログ） | サービスアカウントは追記のみ・人間は読み取りのみのカスタムロール定義。全分岐で記録する設計だった |
| ハッシュチェーン（`PrevHash` / `Hash`） | 前エントリのハッシュを含めて改ざんを検知。**当初から第2フェーズ扱いで未実装**（Power Automate に SHA-256 の式が無く、Office Scripts 実装が必要で複雑度に見合わないと判断） |
| Flow-F（削除監視） | ソースリストの項目削除を検知してアラート |
| 「修正＝取下げ→再申請」パターン | `WithdrawnAt` / `OriginItemId` 列 |

> [!important] 改ざん耐性についての当初の整理（今も有効な考え方）
> 「Lists は権限があれば書き換え・削除して無かったことにできる」という懸念に対し、
> **これはデータストアの種類（Lists / RDB）によらず本質的に同じ問題**であり、
> 追記専用の監査ログを別に持つことで対応する、という整理をしていた。
>
> そして重要な但し書きがある：**サイトコレクション管理者は依然としてすべてを変更できる。**
> 追記専用ログは「一般利用者・承認者・担当部署による改ざん」を防ぐものであり、
> **管理者権限の最小化と Purview 監査ログとセットで初めて意味を持つ**。
>
> 簡易承認方式ではこの層をまるごとスコープ外にした。**改ざん耐性の要求が先方から出てきたら、
> この整理から議論を再開すること。** → `docs/conventions.md` §5

## 残っている保護策

監査ログを捨てた後も、以下は生きている。

| 保護策 | 状態 |
|---|---|
| バージョン履歴の有効化（`EnableVersioning="true"`） | ✅ 各リストで有効 |
| 項目レベル権限（`ReadSecurity=2` / `WriteSecurity=2`） | ✅ 適用済み |
| 慶弔リストの閲覧を総務人事に限定 | ✅ 権限マトリクスに定義済み |
| 組み込みの `Author`（作成者）を既定ビューに表示 | ✅ SharePoint が必ず設定し書き換え不可のため、誰が起票したかは常に追える |
| Microsoft Purview 監査ログの有効化 | ❓ 先方への依頼事項として `setup-prod.md` に記載。実施状況は未確認 |
| サイトコレクション管理者の最小化 | ❓ 同上 |

### 総務の全件閲覧（最大の詰まり）

年休の20日締め出力・慶弔の総務閲覧が、`ReadSecurity=2` の仕様上そのままでは成立しない。
**ビューを作っても回避できない。** 詳細と2つの対応案は
→ [[テーマ3 - 総務の全件閲覧をどう成立させるか]]

### 「申請状態は申請者と承認者のみ確認できるように」（2026-08-27 の依頼）

現状は `ReadSecurity=2` のため、**承認者もリスト上は他人の申請を見られない**。
承認カード／出力Excel経由で確認する設計になっている。
ユーザーからは「これで十分」と回答済みだが、**フローが動き始めたときに再度問題になる可能性がある**。

### 昼食の取消権限

`Status` に「取消」を追加しただけで、「誰が・いつまで取消せるか」が未定義。
`WriteSecurity=2` のため申請者本人は編集できるが、締切後の取消をどう止めるかは未設計。
